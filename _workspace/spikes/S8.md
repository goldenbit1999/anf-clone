## Q1: knfsd 통계의 범위

### 줄별 범위

볼륨 하나에만 I/O를 건 11개 경우(`q123.jsonl`)와 시작 직후 값(`cat`)에서 판정했다.

| 줄 | 범위 | 근거 (실측) |
| --- | --- | --- |
| `io` | 인스턴스 netns별 | A에 256 MiB 쓰기: A `io_w` +268,435,456, B +0, 호스트 netns +0. 11개 경우 모두 쉬는 볼륨 0 |
| `rpc` | netns별 | A 쓰기: A +260, B +1(v4.1 lease 갱신 SEQUENCE), 호스트 +0. 시작 직후 A 7, B 20, 호스트 0 |
| `rc` | netns별 | A v3 쓰기: A `[0, 256, 4]`, B `[0, 0, 1]` |
| `proc3` | **전역** | A v3 쓰기: A·B·호스트 모두 WRITE +256. A v3 4 KiB 임의 읽기: 셋 다 READ +62,955. 시작 직후 세 파일이 똑같이 `proc3 22 1 2 0 … 2 1 0`(A의 v3 마운트가 만든 NULL·GETATTR·FSINFO·PATHCONF) |
| `proc4` | **전역** | B v4.1 쓰기: A·B 모두 COMPOUND +260. 시작 직후 세 파일 모두 `proc4 2 1 19`(B의 v4.1 마운트) |
| `proc4ops` | netns별 | B 쓰기: B WRITE +256, A·호스트 0. 시작 직후 A는 모두 0, B만 값이 있다 |
| `th` | 확인 안 함 | 세 파일 모두 `th 16`. 인스턴스 둘과 호스트 knfsd의 스레드 수로 나눠 보지 않았다 |

- 호스트(root)에서 `/proc/<인스턴스 pid>/net/rpc/nfsd`를 그대로 읽을 수 있다. `nsenter`나 `docker exec`가 필요 없다.
- 브리프의 결론(소스 추론)과 같다: `io`·`rpc`·`proc4ops`는 netns별, `proc3`·`proc4`는 정적 `svc_version`의 per-cpu `vs_count`라 전역이다.
- 인스턴스를 다시 띄우면 볼륨별 카운터가 0부터 시작한다. `docker restart`(0.8 s) 뒤 A의 pid가 1058 → 8090으로 바뀌고 `io 1063170048 1634509200` → `io 0 0`, `rpc 69942` → `rpc 0`이 됐다. netns가 새로 생기기 때문이다. 같은 때 tc도 사라졌다(`Cannot find device "ifb0"`, S7 M5와 같음).
- 카운터 폭: `io`, `rc`, `proc4ops`는 64비트(`%lld`)이고 `rpc` 줄은 `unsigned int`(32비트)다(K1 `stats.c`, K9 `svc_seq_show`). `rpc` 호출 수는 2^32에서 돈다.

### v3 볼륨별 읽기·쓰기 연산 수를 얻는 다른 길

| 후보 | 결과 |
| --- | --- |
| `export_stats` (nfsd 파일시스템, `/proc/<pid>/root/proc/fs/nfsd/export_stats`) | netns별로 읽힌다. export·클라이언트 도메인마다 `fh_stale`, `io_read`, `io_write`(바이트)뿐이고 연산 수는 없다. 값은 `io` 줄과 같았다. **`exportfs -ra`와 `exportfs -f` 뒤에는 항목이 모두 사라졌다가** 다음 접근에서 새 시작 시각(86 → 352)과 0으로 다시 생긴다(같은 때 `io` 줄은 그대로 늘었다: `io 1063170048 619487632` → `… 627876240`). agent는 스냅샷을 만들거나 지울 때 `exportfs -ra`, 되돌리기 창에서 `exportfs -f`를 하므로 그때마다 초기화된다 |
| `rpc` 줄 | 볼륨별 전체 RPC 수다. NFSACL(GETACL) 호출도 들어간다(아래 meta200: `rpc` 810, `proc3` 합 608). 4 KiB 고부하에서 다른 카운터보다 조금 적다: v4.1 임의 읽기 61,236 vs COMPOUND 61,249(−13), v3 임의 읽기 62,951 vs `proc3` 합 62,959(−8). 순차 1 MiB에서는 같았다 |
| **`rc` 줄 (응답 캐시: hits, misses, nocache)** | per-cpu 카운터라 연산 수와 정확히 맞았다. v3에서 **misses = 변경 연산, nocache = 그 밖**으로 나뉜다(아래 표). v4.1에서는 모든 COMPOUND가 nocache라 새 정보가 없다(B 쓰기 `[0, 0, 260]`) |

v3 (A) `rc` 줄과 같은 시간의 `proc3`(그동안 v3 I/O는 A에만 있었다):

| 경우 | `rc` hits / misses / nocache | `proc3` 증가 | fio |
| --- | --- | --- | --- |
| 순차 쓰기 1 MiB × 256 | 0 / 256 / 4 | WRITE 256, GETATTR 2, ACCESS 2 | 256회 |
| 순차 읽기 1 MiB × 256 | 0 / 0 / 260 | READ 256, GETATTR 1, LOOKUP 1, ACCESS 2 | 256회 |
| 4 KiB 임의 읽기 10 s | 0 / 0 / 62,959 | READ 62,955 + 4 | 62,955회 |
| 4 KiB 임의 쓰기 10 s | 0 / 3,786 / 3 | WRITE 3,786 + 3 | 3,786회 |
| 버퍼 쓰기 64 MiB + fsync | 0 / 65 / 5 | WRITE 64, CREATE 1 / GETATTR 1, LOOKUP 1, ACCESS 2, COMMIT 1 | 64회 |
| 파일 200개 만들기·`ls -l`·`rm -rf` | 0 / 602 / 208 | WRITE 200, CREATE 200, REMOVE 200, MKDIR 1, RMDIR 1 / GETATTR 2, ACCESS 2, READDIRPLUS 1, FSSTAT 1. `rpc`는 810 | — |

- meta200의 nocache 208 = `proc3`의 6 + 202이고, `rpc` 810 − `proc3` 합 608 = 202다. `ls -l`이 파일마다 ACL을 묻는 NFSACL GETACL로 본다 [추정: 프로그램별 수를 따로 보지 않았다]. 그래서 `rc` 합(hits + misses + nocache)은 NFS와 NFSACL을 합한 볼륨별 전체 연산 수다.
- COMMIT은 nocache 쪽이다. ANF 문서도 COMMIT을 Other로 센다(브리프 D3).
- 결론: v3 볼륨에서 볼륨별로 정확한 것은 전체 연산 수다. misses는 "WRITE + 메타데이터 변경"이고 nocache는 "READ + 메타데이터 읽기 + COMMIT"이라, 데이터 부하에서는 쓰기·읽기 연산 수에 가깝지만 메타데이터 부하가 섞이면 어긋난다(meta200: WRITE 200인데 misses 602).

- **knfsd `io`는 모든 경우 fio 바이트와 같다**(바이트 단위로 일치, 예: 268,435,456 = 268,435,456). 읽기는 `io` 첫째 값, 쓰기는 둘째 값만 늘었다. 헤더와 메타데이터가 없다.
- **페이지 캐시에서 나간 읽기도 `io`에 잡힌다.** warm 읽기에서 thin LV 디스크 읽기가 0인데 `io` 읽기는 268,435,456 B였다. `io`는 "READ 응답으로 돌려준 바이트"라 서버 캐시 적중과 상관없다. ANF 처리량 정의("across the wire between ANF and the client", 브리프 D3)와 같은 방향이다. 클라이언트 쪽 캐시 적중(버퍼 읽기를 두 번)은 서버에 오지 않으므로 어느 출처에도 잡히지 않는다 [추론, 시험 안 함].
- **`eth0`는 방향을 나눈다.** 쓰기 = `eth0` 수신, 읽기 = `eth0` 송신. 데이터 방향의 값은 1 MiB에서 데이터의 1.0016~1.0038배, 4 KiB에서 1.044~1.098배다. 반대 방향에는 응답·ACK가 1 MiB에서 0.1~0.2%, 4 KiB에서 4.8~8.8% 흐른다. 인스턴스 안 `eth0`(veth의 netns 쪽)라 호스트 쪽 veth 이름을 찾을 필요가 없다.
- **`ifb0` 송신은 양방향 합**이다. 11개 경우 중 9개에서 `eth0` 수신 + 송신과 바이트까지 같았고, 1 MiB 순차 쓰기 둘만 0.12%(A)·0.22%(B) 작았다. `eth0` 수신은 tc ingress 앞에서 세므로 `fq_codel`이 버린 패킷과 그 재전송을 함께 센다 [추론: Q4에서 포화 쓰기의 `fq_codel` 드롭이 20 s에 32개였다]. 방향을 나누지 못한다. HTB Sent는 GSO 묶음을 세그먼트로 나눈 wire 바이트라 1 MiB에서 1.047~1.050배, 4 KiB에서 1.15~1.16배다(ADR §8의 "4.2~4.4% 큼"과 같은 계열).
- 쉬는 볼륨: 11개 경우 모두 `io` 0, `eth0` ≤ 326 B, HTB ≤ 546 B(v4.1 lease 갱신).
- 디스크 바이트는 쓰기에서 데이터보다 크다(1 MiB 1.01배, 4 KiB 2.35~2.50배: `sync` export의 저널·메타데이터 쓰기 [추정]). 처리량 출처로는 맞지 않는다.

- v4.1 `proc4ops` READ/WRITE는 서버가 받은 READ/WRITE 연산 수와 정확히 같다(클라이언트 mountstats와 1의 자리까지 같다). fio 연산 수와는 블록이 rsize/wsize(1 MiB) 이하일 때만 같다. 4 MiB는 1 MiB 네 개로 쪼개져 fio 64회가 READ 256이 됐다. 서버가 세는 것은 wire 연산이다.
- COMPOUND 하나에 SEQUENCE + PUTFH + READ(또는 WRITE)가 들어가 `proc4ops` 합은 COMPOUND 수의 약 3배다. 메타데이터 부하(파일 200개)에서는 COMPOUND 1,011에 GETATTR 809, OPEN 200, CLOSE 200, ACCESS 202, WRITE 200 등 연산이 여럿씩 들어갔다. 그래서 "Other/Total IOPS"를 COMPOUND 수로 셀지 개별 연산 합으로 셀지에 따라 값이 2~3배 다르다(ANF 문서도 목록에 COMPOUND와 개별 연산을 함께 적어 판단할 수 없다, 브리프 미확인 목록).
- v3는 Q1대로다: 볼륨별 전체 연산 수는 `rc` 합(정확), 데이터 부하에서는 misses ≈ WRITE, nocache ≈ READ + 메타데이터. `proc3`의 READ/WRITE는 전역이라 볼륨별로 쓸 수 없다.
- `rpc` 줄은 4 KiB 고부하에서 다른 카운터보다 1~13 적었다(0.01~0.02%). `rc`·`proc4ops`(per-cpu)는 맞았다. `rpc` 필드가 원자적이지 않은 `unsigned int`라 동시 증가를 잃는 것으로 본다 [추정: `net/sunrpc/svc.c`의 증가 위치는 브리프도 받지 못했다].

- burst를 256k로 키워도(`tc class change … burst 256k cburst 256k`) 50% 부하에서 초당 227로 그대로 늘었다. 1 MiB 요청 16개가 한꺼번에 나가는 순간 버킷을 넘기 때문으로 본다 [추론]. 시험 뒤 agent와 같은 인자(burst 기본값)로 되돌렸다. burst 256k에서는 포화 사용률이 1.000으로 올랐다(기본 burst는 0.951~0.979). 이것은 FR-08 정확도 쪽 관찰이다(데이터 처리량은 이번에 보정 기준으로 재지 않았다).
- 다른 후보: `fq_codel` 드롭은 81% 부하부터 나와 포화와 가르지 못한다. backlog는 50% 부하에서도 0~225 KB로 흔들린다. `tokens`는 50% 부하에서도 중앙값이 음수였다(B 쓰기 −29,640). `lended`는 패킷 수에 비례한다. 어느 것도 이진 신호가 아니다.
- **사용률은 부하와 맞는다**: 50% → 0.50, 81% → 0.81, 91% → 0.906, 포화 → 0.951~0.979(기본 burst). 포화와 91% 부하의 간격은 쓰기 0.07, 읽기 0.045다. 임계값 0.95면 이번 포화 창의 중앙값은 모두 넘고 91% 부하의 p90(0.911)은 넘지 않는다. 다만 읽기 포화의 p10이 0.936이라 1초 창 하나로 판정하면 놓친다. 그래서 창 길이(예: 15 s, 1 m)와 "창 안의 최댓값/평균" 중 무엇을 쓸지가 결과를 바꾼다. 한도를 바꾼 볼륨은 HTB rate도 함께 알아야 한다(한도 gauge 또는 `htb_rate_bits(한도)`).
- ANF `ThroughputLimitReached`는 "직전 5분 안에 한도에 닿았으면 1"이다(브리프 D3). 클론에서 그와 같은 뜻을 만들려면 사용률 임계값이 필요하다.

## 설계에 주는 선택지

설계는 정하지 않는다. 관찰에서 나온 선택지와 근거만 적는다.

- **처리량 출처 (ADR §8이 FR-12로 미룬 결정).**
  - (가) knfsd `io`: 데이터 바이트와 정확히 같고 읽기·쓰기가 나뉜다. 캐시 적중 읽기도 센다. 메타데이터 바이트(ANF Other throughput)는 없다. `/proc` 파일 하나라 싸다.
  - (나) `eth0` 수신·송신: 방향이 나뉘고 wire 바이트다. 데이터보다 0.2~10% 크고, 쓰기 중에도 송신에 응답 바이트가 흐른다(읽기 처리량이 0이 아니게 보인다).
  - (다) `ifb0` 송신 / HTB Sent: 한도와 같은 기준이지만 합만 있다. HTB Sent는 tc 호출이 필요하다.
  - 한도 도달 신호(사용률)는 (다)가 필요하다. 처리량은 (가), 사용률은 (다)로 둘을 함께 낼 수 있다.
- **v3 IOPS (브리프 선택지 4).** (가) Total만(`rc` 합, 정확), Read/Write는 비움. (나) `rc` misses/nocache를 Write/Read로 근사하고 차이를 문서화(데이터 부하에서는 맞고 메타데이터 부하에서 어긋남, Q1 표). (다) 비움. `proc3`를 볼륨별로 쓰면 틀린 값이다.
- **v4.1 Other/Total의 단위.** COMPOUND 수(= `rc` nocache = 연산 요청 수)인지 개별 연산 합(약 3배)인지. v3와 같은 뜻으로 맞추려면 COMPOUND 단위가 가깝다 [추론].
- **IOPS 수치의 뜻.** 서버 카운터는 wire 연산이라 rsize/wsize보다 큰 앱 I/O는 여러 개로 센다(4 MiB → 4). ANF도 서버 쪽에서 센다면 같은 성질이다 [추론].
- **한도 도달.** HTB `overlimits`는 쓸 수 없다(50% 부하에서도 늘어남). 사용률(HTB Sent 속도 ÷ HTB rate, 또는 데이터 처리량 ÷ 한도)의 임계값과 창을 정해야 한다. 이번 값: 91% 부하 p90 0.911, 포화 p10 0.936~0.967, 중앙값 0.951~0.979. burst를 바꾸는 것은 FR-08 동작을 바꾸므로 이 결정과 따로 봐야 한다(256k에서 포화 사용률 1.000, `overlimits`는 여전히 늘어남).
- **pid 찾기.** `docker inspect` CLI(약 150 ms/호출)를 스크레이프마다 볼륨 수만큼 부르면 안 된다. Docker Engine API 소켓(약 0.9 ms/볼륨), 이름 여럿을 한 번에(153 ms), 또는 pid 캐시(인스턴스가 다시 뜨면 pid가 바뀌므로 무효화 필요) 중에서 고른다.
- **카운터 재시작.** 인스턴스가 다시 뜨면(재시작, 시작 복구) 볼륨별 카운터가 0부터 다시 시작한다. Prometheus `rate()`는 카운터 리셋을 처리하지만 리셋 사이의 증가분 일부는 잃는다. `export_stats`는 스냅샷 생성·삭제(`exportfs -ra`)와 되돌리기 창(`exportfs -f`)마다 사라지므로 카운터로 쓰기 어렵다. `rpc` 줄은 32비트이고 고부하에서 조금 덜 센다.
- **사용량.** "Volume Consumed Size"를 `statvfs` used(스냅샷 제외, 클라이언트 `df`와 같음)로 낼지, 이름을 바꿔 차이를 드러낼지(브리프 선택지 5). 풀 사용량은 `dmsetup status` 블록 수(정확, 6 ms)와 `lvs` 백분율(55 ms, 0.01% 단위) 중에서. thin LV `data_percent`는 지운 파일을 계속 세므로 사용량으로 쓰지 않는 쪽이 맞다 [추론].
- **Prometheus 운영.** 버전 태그(v3.15.1 또는 3.13 계열), 띄우는 방법(준비 스크립트, 검증 스크립트, `docker run` 명령), 저장소(익명 볼륨이면 `docker rm -v`로 사라짐, 이름 있는 볼륨이면 남음), 스크레이프 간격(5 s에서 문제 없음)과 대시보드 창(`irate` 약 5 s, `rate[15s]` 약 10 s), ANF 5분 평균과의 차이를 어떻게 문서화할지.

## 정리

ARM API로 볼륨 `avol`·`bvol`, 풀, 계정을 지웠다(모두 `Succeeded`). 스냅샷 `s8snap`은 Q5 안에서 지웠다. 클라이언트 `s8-cli`(마운트를 먼저 풀고), Prometheus 컨테이너 `s8-prom`(익명 볼륨 포함, `docker rm -f -v`), 임시 exporter 프로세스를 지웠다. anf-api와 agent를 멈췄다(포트 8080·8090·9090·9101 비어 있음). 시작할 때의 상태(막 부팅한 WSL)로 돌리려고 `ns` 바인드를 풀고 VG `anf`를 비활성화하고 loop 장치를 떼었고, 스파이크 중 올라간 모듈(`act_mirred`, `cls_matchall`, `sch_ingress`, `sch_htb`, `ifb`)을 내렸다. agent가 시작할 때 이것들을 다시 한다. `/var/tmp/s8`(DB, 로그, Prometheus 설정)는 원자료를 scratchpad `s8/results/`로 복사한 뒤 지웠다. 정리 뒤 `anf-nfs-*`·`s8-*` 컨테이너 없음, Docker 볼륨 0개, VG `anf` 미연결, `/var/lib/anf-clone/{ns,exports}` 비어 있음, IFB 0개, `fs.leases-enable = 0`, uvicorn·exporter 프로세스 없음을 확인했다. **이미지 `prom/prometheus:v3.15.1`(114 MB)은 남겼다.** 이미지 `anf-nfs-server`·`anf-nfs-client`, 네트워크 `anf-vnet`, `/var/lib/anf-clone/aggr0.img`는 그대로다. WSL 유휴 종료 방지용 `sleep`도 끝냈다. 제품 코드는 바꾸지 않았다.
