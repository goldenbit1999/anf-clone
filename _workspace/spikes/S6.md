# S6 — 볼륨 인스턴스 구조에서 스냅샷으로 새 볼륨 만들기 (FR-07)

| 항목 | 내용 |
| --- | --- |
| 실행일 | 2026-11-08 |
| 실행 | feature-implementer 서브에이전트 (`wsl -d Ubuntu -u root -e bash <스크립트>`). 스크립트는 세션 scratchpad `s6/`(`lib.sh`, `p1.sh`~`p8.sh`, `cleanup.sh`), 전체 출력은 `s6/logs/s6-p1.log`~`s6-p8.log`에 두었고, 판정에 쓴 출력은 아래에 옮겼다. 복구 시험(R)은 agent 코드(`storage_agent.flexvol.FlexVolManager`)를 고치지 않고 불러 VG·풀 이름과 컨테이너 이름만 바꿔 돌렸다 |
| 왜 | S1 #9(쓰기 가능한 thin 스냅샷으로 새 볼륨을 즉시 만든다)는 볼륨 인스턴스 구조(D-12)와 `.snapshot` export(S4) 전의 측정이다. `anf-feature-cycle`의 "기능별 선행 확인" FR-07 행: S1의 "같은 파일시스템 UUID" 주의와 export `fsid`, 원본 스냅샷이나 볼륨을 지운 뒤에도 새 볼륨이 남는지, ADR R-09 |
| 전체 판정 | **조건부 통과.** 원본 볼륨 V의 읽기 전용 스냅샷 LV에서 `lvcreate -s -kn -p rw`(볼륨 태그를 만들 때 붙임)로 만든 새 볼륨 N은 0.15 s 안팎에 생기고, 저널 재생 없이 rw로 마운트되며(0.016 s), 스냅샷 시점 내용을 갖고(체크섬 같음), 자기 인스턴스에서 v3·v4.1로 서비스된다. N에 쓴 것은 V와 스냅샷에 보이지 않고 그 반대도 같다. N을 쓰는 동안 원본 스냅샷 삭제, V 되돌리기(교체 방식), V와 스냅샷 전부 삭제를 해도 **LVM은 거절하지 않고**, N의 마운트·쓰기·열린 fd가 오류 없이 이어진다. agent의 `_report()`·`recover()`는 코드 수정 없이 N을 일반 볼륨으로 다룬다(원본이 있을 때와 지운 뒤 모두). 조건 넷: (1) N의 `.snapshot`에 원본 스냅샷의 빈 마운트 지점이 남아 정리해야 한다. (2) N의 ext4 UUID가 원본과 같다. export `fsid`가 볼륨 uuid라서 NFS에는 영향이 없었다. 바꾸려면 `tune2fs -U`가 "갓 검사한 파일시스템"을 요구한다(`e2fsck -f`가 `lost+found`를 만든다). `-O metadata_csum_seed`를 함께 주면 검사 없이 0.02~0.03 s다. (3) 만들 때 크기를 줄 수 없다. 키우기는 `lvextend` + `resize2fs`(온라인 가능), 줄이기는 오프라인뿐이다. (4) 되돌리기는 LV 크기까지 스냅샷 시점으로 돌린다(B2) |

## 환경

- 커널 `6.18.54.1-microsoft-standard-WSL2`, LVM 2.03.16, e2fsprogs 1.47.0(mke2fs 기본 기능에 `metadata_csum`, `metadata_csum_seed` 없음). 이미지 `anf-nfs-server`는 지금 저장소의 `entrypoint.sh`·`nfs.conf`와 같은 내용이다(sha256 비교). 클라이언트 `anf-nfs-client`(privileged, 기본 hard 마운트, v3는 `nolock`). `fs.leases-enable = 0`(되돌리기 결정 1).
- 스파이크 전용 자원: VG `anfs6`(8 GiB 희소 파일 `/var/lib/anf-clone/spike-s6/aggr0.img`), 씬 풀 `aggr0`(chunk 64 KiB), 루트 `/var/lib/anf-clone/spike-s6`(`ns`를 rshared로 바인드). agent의 VG `anf`는 활성화돼 있지 않았고 건드리지 않았다. 포트 8080·8090과 `anf-nfs-*` 컨테이너는 시작할 때 비어 있었다.
- 모양은 agent와 같다: LV `vol_<uuid32>`·`snap_<uuid32>`, 볼륨 태그 `anf_path/anf_uuid/anf_ip/anf_proto`, 스냅샷 태그 `anf_snap_uuid/name/vol/time`, ext4 `mkfs -U <uuid> -m 0`, `nodelalloc`, 루트 `.snapshot`에 `chattr +i`, export 파일 `exports/<uuid32>/volume.exports`(볼륨 `fsid=<볼륨 uuid>`, 스냅샷 `fsid=<스냅샷 uuid>`), 인스턴스는 agent의 `docker run` 인자 그대로(이름만 `s6-nfs-<uuid32>`). 스냅샷은 `lvcreate -s -kn -p r` 뒤 `.snapshot/<이름>`에 `ro,noload`. 되돌리기는 `flexvol._resume_restore`와 같은 교체 방식(S5 L2, 입력 차단 창).
- 볼륨: V `s6v`(nfs3, .250, 1 GiB), N `s6n`(V의 S_b에서, nfs4.1, .251), N3 `s6n3`(V의 S_b에서, nfs3, .252, ext4 UUID 바꿈), N_d `s6nd`(V의 S_d에서, nfs3, .253), 그 밖에 인스턴스 없는 시험용 볼륨(.254 태그, 쓰고 바로 지움).
- 데이터: V에 `f1=one, keep, d/e=e1, big`(64 MiB 무작위), `small/1..200` → **S_a** → `f1=two`, `keep` 삭제, `g=g2`, `big2`(32 MiB) → **S_b** → `f1=three, h=h3`, `d/e` 삭제. 체크섬 "manifest"는 `.snapshot`과 `loop/`를 뺀 모든 파일의 경로 + sha256을 묶은 값(앞 16자리)과 파일 수다.
- WSL 배포판 유휴 종료를 막으려고 `wsl -d Ubuntu -u root -e sleep 86400`을 백그라운드로 띄워 두었다 (S4 환경 주의).

## 설계에 주는 선택지

설계는 정하지 않는다. 관찰에서 나온 선택지와 그 근거만 적는다.

- **새 볼륨 LV.** 원본 스냅샷 LV의 `lvcreate -s -kn -p rw`에 볼륨 태그를 만들 때 붙이면, 되돌리기의 `_new` LV와 같은 방식이고 `_report()`가 바로 볼륨으로 본다(C1·C2·R3). 다만 지금 `_ensure_lv`는 uuid가 없으면 빈 thin LV를 새로 만들고, 있으면 (경로, 크기, 프로토콜)이 요청과 같은지 비교한다. 그래서 (가) 복원 LV를 `_ensure_lv`보다 먼저 만들지, (나) `_ensure_lv`에 원본 스냅샷 인자를 더할지, 그리고 요청 크기가 원본과 다를 때 비교를 어떻게 할지가 갈림길이다. `lvcreate`가 끝난 뒤 멈추면 태그가 이미 있으므로 같은 요청을 다시 보내면 이어서 끝낼 수 있다 [추론, 시험 안 함].
- **ext4 UUID.** 셋 중에서 고른다.
  - (가) 그대로 둔다: NFS 동작에는 영향이 없었다(Ua4·Ua5, export `fsid`가 볼륨 uuid). 대신 `blkid -U`·`/dev/disk/by-uuid`가 여러 장치 중 하나만 가리키고(Ua2), 볼륨 uuid와 ext4 UUID가 같다는 지금 볼륨의 성질(`mkfs -U <uuid>`)이 새 볼륨에서는 깨진다.
  - (나) `e2fsck -f` + `tune2fs -U`: 4 GiB·2만 파일에서 차가운 캐시로 0.2 s 안쪽. `e2fsck`가 rc 1로 끝나고 `lost+found`를 만든다(Ub3). 지금 `create()`는 `lost+found`가 있으면 "mkfs 직후"로 보고 루트 권한을 요청의 `unixPermissions`로 바꾼 뒤 지우므로, 이 방식은 우연히 권한 초기화를 일으킨다. 메타데이터를 모두 다시 써서 그만큼 풀에서 나간다(4 GiB에서 7 MB).
  - (다) `tune2fs -O metadata_csum_seed -U`: 검사 없이 0.02~0.03 s, `lost+found` 없음, 새로 쓰는 양 0.5 MB. 대신 새 볼륨의 ext4 기능이 새로 만든 볼륨(`mkfs` 기본값)과 달라진다. `mkfs`에 같은 기능을 주면 모든 볼륨이 같아진다.
  - `tune2fs -T now -U`(Ub5)는 검사를 건너뛰는 우회라 후보로 두지 않는다.
- **`.snapshot` 정리.** 새 볼륨의 `.snapshot`에는 원본 스냅샷 시점의 마운트 지점(빈 디렉터리)이 남는다(D4). 정리하지 않으면 클라이언트 목록에 빈 디렉터리로 보인다 [추론, S4 E3b와 같은 구조]. 되돌리기의 stray 정리(`_resume_restore`)와 같은 방법(D5)이 된다. base 스냅샷을 만든다면 정리를 먼저 해야 base에 남지 않는다.
- **크기.** 만들 때 크기를 줄 수 없다(Z1). 원본보다 크게: `lvextend` 뒤 마운트하고 온라인 `resize2fs`(검사 요구 없음, Z2), 또는 마운트 전 `resize2fs -f`(Z5). 원본보다 작게: 오프라인 검사·축소·`lvreduce -f`가 되지만(Z6) 쓰는 데이터보다 작게는 안 되고 `lost+found`가 생긴다. 작게 만드는 요청을 받을지 거절할지는 ANF 규칙(브리프)에 따른다.
- **base 스냅샷.** 만들 수 있고, 그 thin_id가 뒤의 스냅샷보다 작아 지금 되돌리기 코드의 "더 새 스냅샷" 판단이 그대로 맞는다(B1~B3). 크기를 바꾼다면 base는 크기를 바꾼 뒤에 찍어야 base로 되돌릴 때 크기가 줄지 않는다(B2 관찰). 같은 이유로, 볼륨 크기 변경(뒤 FR)이 생기면 되돌리기 일반이 크기를 스냅샷 시점으로 돌린다. 이는 FR-06 코드의 성질이다.
- **원본 스냅샷·볼륨 삭제.** LVM이 막지 않고 새 볼륨이 그대로다(I3~I6). 원본 스냅샷이 새 볼륨의 원본이라는 이유로 삭제를 거절할지는 ANF 동작(브리프의 "in the process of being cloned", `[미확인]`)과 anf-api 규칙으로 정할 일이다. 클론에는 "복제 중" 기간이 없다.
- **복구.** `_report()`·`recover()`를 바꿀 필요가 없었다(R1~R3). 새 볼륨도 IP를 `VOLUME_IPS`에서 새로 골라야 한다. 같은 IP 태그가 둘이면 `recover()`가 같은 IP로 인스턴스 둘을 띄우게 된다(이번에는 그 경우를 만들지 않았다).
- **풀 사용량 (R-09).** 새 볼륨은 쓴 만큼만 풀에서 나가고, agent의 남은 공간 계산은 새 볼륨을 볼륨 크기 전체로 센다. ext4가 discard 없이 마운트돼서 지운 공간은 `fstrim` 전까지 풀로 돌아오지 않는다(Z4). 이것은 FR-07만의 성질이 아니다.
- **루트 권한.** 새 볼륨의 루트 모드는 원본의 것을 물려받는다(D3). 요청의 `unixPermissions`를 적용할지는 설계에서 정한다(위 (나)의 우연한 초기화와 별개로).
