# S9 — 구성요소를 컨테이너로 띄우기 (FR-13)

| 항목 | 내용 |
| --- | --- |
| 실행일 | 2026-11-10 |
| 실행 | feature-implementer 서브에이전트. 실험 이미지 넷(storage agent, anf-api, 대시보드 nginx, 대시보드 vite preview)을 WSL Docker Engine에서 빌드하고, 저장소 코드(`feature/metrics`, 수정 없음)를 그 안에서 돌렸다. compose가 없어 같은 구성을 `docker run` 스크립트로 흉내 냈다. ARM 요청과 데모 대본은 일반 사용자 `mkimhome1`(docker 그룹, sudo 없음)이 e2e 도우미(`backend/tests/e2e/live_api.py` 등)로 보냈다. 스크립트는 세션 scratchpad `s9/`(목록은 끝의 "재현"), 원자료는 `s9/results/`다. 판정에 쓴 출력은 아래에 옮겼다. 제품 코드와 저장소 파일은 바꾸지 않았다 |

| 전체 판정 | **조건부 통과.** agent·anf-api·Prometheus·대시보드를 모두 컨테이너로 띄워 데모 대본 1~6단계가 호스트 프로세스 때와 같게 돌았다(62.1 s, sudo 없이). 볼륨 생성·마운트(v3·v4.1)·스냅샷·되돌리기·새 볼륨 복원·처리량 제한(31.09 → 15.64 MiB/s)·삭제·`/metrics`·시작 복구가 모두 됐다. 조건 둘: (1) **이 기기에 compose가 없다**(`docker compose` 플러그인도 `docker-compose`도 없음, buildx도 없음). FR-13 문구대로 하려면 설치를 사용자가 정해야 한다. GitHub `ubuntu-24.04` 러너에는 Compose 2.38.2가 있다. (2) **agent 컨테이너는 다섯 설정이 모두 있어야 한다.** 하나라도 빠지면 시작이 실패하거나(LVM 잠금, `--pid host`), 볼륨 인스턴스가 뜨지 않거나(호스트 `ns` 전파), 재시작 뒤 되돌리기가 실패하고 호스트 디렉터리를 더럽히거나(재귀 바인드), LVM 명령이 영원히 멈춘다(`/run/udev`만 바인드) |

## Q2: storage agent를 컨테이너로

### 되는 최소 설정 (마지막 형태)

```bash
# 호스트 준비 (컨테이너보다 먼저): ns를 자기 자신에 바인드해 rshared로. 지금 agent의 ensure_shared_ns와 같은 일
findmnt --mountpoint /var/lib/anf-clone/ns >/dev/null || {
  mount --bind /var/lib/anf-clone/ns /var/lib/anf-clone/ns; mount --make-private /var/lib/anf-clone/ns; }
mount --make-rshared /var/lib/anf-clone/ns

docker run -d --name s9-agent --privileged --network host --pid host \
  -v /dev:/dev -v /lib/modules:/lib/modules:ro -v /var/run/docker.sock:/var/run/docker.sock \
  --mount type=bind,src=/var/lib/anf-clone,dst=/var/lib/anf-clone,bind-recursive=disabled \
  -v /var/lib/anf-clone/ns:/var/lib/anf-clone/ns:rshared \
  -v /run/lock/lvm:/run/lock/lvm \
  s9-agent
```

- `/var/lib/anf-clone`은 컨테이너 안에서도 같은 경로여야 한다. agent가 `docker run --mount src=/var/lib/anf-clone/ns,…`로 인스턴스를 띄우면 dockerd가 그 경로를 **호스트**에서 읽기 때문이다.
- `/run/udev`는 바인드하지 않는다(아래 L3). `--ipc host`는 필요 없다.

### 빠지면 생기는 일 (실측)

| # | 설정 | 빠졌을 때 | 근거 |
| --- | --- | --- | --- |
| P1 | 호스트 `ns`를 먼저 rshared 바인드 | `-v ns:ns:rshared`가 거절된다: `docker: Error response from daemon: path /var/lib/anf-clone/ns is mounted on / but it is not a shared mount`. rshared 없이 띄우면 agent가 뜨고 `ensure_shared_ns`가 **컨테이너 안에서만** 바인드한다(컨테이너 `ns shared`, 호스트 "not a mountpoint"). 볼륨 POST가 0.64 s 만에 실패한다: `docker run … --mount type=bind,src=/var/lib/anf-clone/ns,dst=/export,bind-propagation=rslave … exited 125: … path /var/lib/anf-clone/ns is mounted on / but it is not a shared or slave mount`. 컨테이너 `anf-nfs-<uuid>`가 `Created`로 남는다(볼륨 DELETE가 지웠다) | WSL `/`는 private다. agent 안의 마운트가 호스트와 인스턴스로 가려면 호스트 쪽이 먼저 공유 마운트여야 하고, 컨테이너가 시작된 뒤에는 자기 바인드를 바꿀 수 없다 |
| P2 | `/run/lock/lvm` 공유 | agent가 시작하지 못했다: `vgchange -ay anf exited 5: Activation of logical volume anf/aggr0 is prohibited while logical volume anf/aggr0_tmeta is active.` 같은 순간 호스트 journal: `PV /dev/loop0 online, VG anf is complete.` → `Started lvm-activate-anf.service - /usr/sbin/lvm vgchange -aay --autoactivation event anf.` → `1 logical volume(s) … now active`. 공유한 뒤에는 같은 자동 활성화가 일어나도 agent가 2.5 s에 떴다 | agent가 loop를 붙이면 호스트 udev(`69-lvm.rules`)가 VG 자동 활성화를 돌린다. 호스트 프로세스 agent는 같은 `/run/lock/lvm`으로 줄을 서지만, 컨테이너는 자기 `/run`의 잠금을 써서 둘이 동시에 활성화한다 |
| P3 | `/var/lib/anf-clone` 바인드를 재귀하지 않음 (`bind-recursive=disabled`) | 볼륨이 있는 채 agent 컨테이너를 다시 띄우면, 재귀 바인드가 호스트의 `ns`와 그 아래 볼륨·스냅샷 마운트를 **private 복사본**으로 가져오고 그 위에 rshared `ns`가 얹힌다(컨테이너 mountinfo에 `ns`가 private·shared 두 번, `s9a` 등이 각각 두 번). 이 상태에서 A 되돌리기가 `Failed`: `docker exec anf-nfs-… exportfs -ra exited 1: exportfs: Failed to stat /export/s9a/.snapshot/snapA: No such file or directory`. agent가 보이는 `s9a`를 내린 뒤 `findmnt`가 숨은 복사본을 보여 줘 "아직 마운트됨"으로 보고 새 LV를 마운트하지 않았고, 호스트의 빈 디렉터리 `ns/s9a`에 `.snapshot`(`chattr +i`)을 만들었다. 나중에 볼륨 DELETE가 `OSError: [Errno 39] Directory not empty: '/var/lib/anf-clone/ns/s9a'`로 실패했다(손으로 `chattr -i` 후 지우고 다시 DELETE). `bind-recursive=disabled`로 다시 띄우자 `ns` 하나(shared)만 보였고 시작 복구가 미완료 되돌리기를 끝냈다(3.0 s). 볼륨 re-PUT으로 `Succeeded`가 된 뒤 되돌리기 `Succeeded`(3.1 s), C 삭제 `Succeeded`(2.1 s) | 컨테이너 첫 시작 때는 `ns` 아래 마운트가 없어 드러나지 않는다. agent 컨테이너 재시작(업데이트, `down`/`up`) 때마다 생긴다. 숨은 복사본은 LV도 잡고 있다 [추론: lvremove "in use"는 이번에 보지 않았다. 되돌리기가 먼저 실패했다] |
| P4 | `--pid host` | 시작 복구가 실패한다: `nsenter -t 6623 -n ip link add ifb0 type ifb exited 1: nsenter: cannot open /proc/6623/ns/net: No such file or directory` | Docker가 알려 주는 인스턴스 pid는 호스트 pid다. tc·iptables(`nsenter -t <pid> -n`)와 `/metrics`(`/proc/<pid>/net/rpc/nfsd`)가 모두 호스트 pid 공간을 본다 |
| P5 | `/dev` 바인드 | 시험하지 않았다. `losetup --find --show`가 만든 새 loop 장치와 dm 노드(`/dev/mapper/anf-*`, `/dev/anf/*`)는 호스트 udev가 호스트 `/dev`에 만든다 [추론: 컨테이너의 기본 `/dev`는 시작 때의 복사라 새 노드가 보이지 않는다] | — |

## Q3: anf-api를 컨테이너로

```bash
docker run -d --name s9-api --network host -v s9-api-data:/data -e ANF_MIN_VOLUME_SIZE_GIB=1 s9-api
# 이미지: ENV ANF_API_DB=/data/anf-api.db, USER anf(uid 1000), uvicorn --host 127.0.0.1 --port 8080
```

- 준비 1.0~1.4 s. `/data/anf-api.db`가 `anf:anf`로 생긴다(이미지에서 `/data`를 `anf` 소유로 만들어 두면 새 이름 있는 볼륨이 그 소유를 받는다). `ss`: `127.0.0.1:8080`에만 연다.
- `ANF_STORAGE_AGENT_URL`은 주지 않았다. host 네트워크라 기본값 `http://127.0.0.1:8090`이 agent 컨테이너(Q2)와 호스트 프로세스 agent(R6) 모두에 닿았다.
- R4 (작업 중 죽이기): `ANF_FAULT_INJECTION='{"netAppAccounts/create": {"delaySeconds": 15}}'`로 띄우고 계정 PUT(`201`) 3 s 뒤 `docker kill` → `docker start`. 같은 작업 상태 URL이 폴링 15.2 s 만에 `Succeeded`, 계정 목록에 `s9-acct:Succeeded`, `s9-acct2:Succeeded`(SQLite가 볼륨에 남았다).
- R5 (agent보다 먼저): anf-api만 떠 있는 동안 볼륨 PUT(`201`), 20 s 뒤 agent 시작(2.0 s 준비). 작업이 agent 준비 뒤 3.2 s 만에 `Succeeded`(storage client의 60 s 연결 재시도 안). 삭제 1.1 s.
- 메모리 37~47 MiB.

## Q5: 한 번에 띄우기 (compose 없이 `docker run`으로 흉내)

`s9/stack.sh up|down`, `mkimhome1`(docker 그룹)로 실행:

| 단계 | 시간 |
| --- | --- |
| init: 특권 컨테이너에서 `modprobe nfsd dm_thin_pool`, `sysctl -qw fs.leases-enable=0`, `nsenter -t 1 -m`으로 호스트 `ns` rshared 바인드 | 0.68 s |
| agent·anf-api·Prometheus·대시보드 `docker run -d` | 누적 2.9 s |
| 준비 (agent `GET /api/storage/volumes`, anf-api 목록 GET, Prometheus `/-/ready`, nginx `/`) | 누적 3.07 s / 두 번째 3.01 s |
| down: `docker stop` dash 0.48, prom 0.28, api 0.64, agent 0.43 s + `rm -v` | 2.22 s |

- **down 뒤 남는 것**: 볼륨 인스턴스 `anf-nfs-*`(돌고 있음), 클라이언트, 이름 있는 볼륨 `s9-api-data`, 호스트 마운트(`ns` 바인드, 볼륨·스냅샷), VG·loop 활성. Prometheus의 익명 볼륨은 `rm -v`로 지워졌다. 포트 8080·8081·8090·9090은 비었다. **down 중에도 클라이언트 I/O가 됐다**: A에 32 MiB 쓰기 28.4 MB/s, B 읽기 md5 같음.
- **시작 순서**: 의존이 필요 없다. anf-api가 agent보다 먼저 떠도 된다(Q3 R5). agent의 HTTP는 시작 복구(lifespan)가 끝난 뒤에 열리므로 HTTP 검사 = 복구 완료다.
- **healthcheck 후보** (컨테이너 안에서 실행해 봄): agent·anf-api 이미지에는 curl·wget이 없다. agent `/venv/bin/python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8090/api/storage/volumes', timeout=3)"` 0.45 s, anf-api 같은 방식으로 목록 GET 0.50 s, Prometheus `wget -q -O /dev/null http://127.0.0.1:9090/-/ready`, nginx `wget -q -O /dev/null http://127.0.0.1:8081/` 모두 성공.
- **준비 스크립트를 컨테이너로**: `mkimhome1`이 sudo 없이 다음을 했다. 특권 컨테이너 + `--pid host` + `nsenter -t 1 -m`으로 호스트 디렉터리를 rshared 바인드(호스트 `findmnt`: `shared`, 그 뒤 `bind-propagation=rshared` 바인드가 받아들여짐, 같은 방법으로 해제), `sysctl -w fs.leases-enable=0`(전역 값이라 컨테이너에서 바뀐다), `-v /lib/modules:/lib/modules:ro`로 `modprobe nfsd`·`dm_thin_pool`. `nsenter -t 1 -a`로 들어가면 호스트 root로 호스트 도구(`/usr/sbin/lvcreate`)가 그대로 보인다: 지금의 `setup-wsl-dataplane.sh`를 그대로 돌릴 수 있다 [추론: 스크립트 전체는 돌리지 않았다]. 시험하지 않은 것: compose에서 `anf-vnet`을 `name:`·`ipam`(subnet, ip_range)으로 선언하기, `anf-nfs-server`·`anf-nfs-client`를 compose `build`로 만들기, `/etc/sysctl.d/90-anf-clone.conf`를 호스트에 쓰기(호스트 파일시스템이 필요하다).
- docker 그룹 사용자가 특권 컨테이너로 호스트 root가 되는 것은 원래 그렇다(docker 그룹 = root와 같은 권한).

| 1~6 합 | **62.1 s** |

- 7단계(대시보드 메트릭)는 이번 대본에 넣지 않았다. S8 P7대로 5 s 스크레이프에서 `rate(…[20s])`가 부하를 약 10~15 s 뒤에 보인다.
- 데모 스크립트 하나의 길이 추정: 스택 기동 3 s(이미지가 있을 때) + 1~6단계 약 62 s + 7단계 약 15 s + 지우기 약 10 s = **약 1.5분**. 처음에는 이미지 빌드(agent 46.8 + api 14.7 + 대시보드 25.0 s, pull 포함)와 `anf-nfs-*` 이미지가 더해져 **약 3분** [추정: 한 번에 이어서 재지 않았다].
- **root 없이**: 모든 구성요소가 컨테이너이고 호스트 준비를 특권 컨테이너로 하면 데모·기동·내리기가 docker 그룹만으로 됐다. 지금 구조(호스트 프로세스 agent, root 준비 스크립트)는 root가 필요하다.

## 설계에 주는 선택지

설계는 정하지 않는다. 관찰에서 나온 선택지와 근거만 적는다.

- **compose.** (가) WSL에 `docker-compose-v2`(필요하면 `docker-buildx`)를 설치하고 FR-13대로 compose 파일 하나. 러너에는 이미 있다(2.38.2). (나) 설치하지 않고 `docker run` 스크립트 하나(`stack.sh`처럼, 기동 3 s)로 바꾸고 PRD 문구를 고친다. (다) 둘 다(compose 파일 + 같은 일을 하는 스크립트). legacy builder는 deprecated 경고가 나오지만 이번 이미지들은 모두 빌드됐다.
- **agent를 어디서 돌릴지.** (가) 컨테이너: P1~P4의 설정 넷과 L2(`/run/udev` 없음)가 모두 필요하다. 재시작마다 P3가 드러나므로 `bind-recursive=disabled`(또는 `aggr0.img`·`exports`만 따로 바인드)는 필수다. (나) 호스트 프로세스로 두고 나머지만 컨테이너: anf-api 컨테이너와 그대로 동작했다(R6). 대신 "명령 하나"에 root 프로세스 기동이 들어간다. 지금의 데이터 플레인 테스트(`run-dataplane-tests.sh`, e2e의 `Agent` 픽스처)는 호스트 프로세스 agent를 직접 띄우고 8080·8090이 비었는지 확인하므로, 스택이 떠 있으면 테스트와 겹친다.
- **호스트 준비(`ns` rshared 바인드, 모듈, sysctl, `anf-vnet`, NFS 이미지).** (가) 지금처럼 root 스크립트에 `ns` 바인드를 더한다. (나) compose의 one-shot init 서비스(특권 + `--pid host` + `nsenter -t 1 -m`)가 한다. agent가 그것을 기다려야 한다(compose `depends_on: condition: service_completed_successfully` [미확인: compose가 없어 시험 안 함]). (다) agent 컨테이너의 진입점이 `nsenter -t 1 -m`으로 호스트 `ns`를 바인드한 뒤 … 는 안 된다: 컨테이너의 바인드는 시작 때 정해지므로 P1이 먼저 실패한다. `/etc/sysctl.d` 파일은 호스트 파일시스템 쓰기가 필요하다.
- **compose 밖의 볼륨 인스턴스(`anf-nfs-*`)와 `down`.** (가) 남긴다: 데이터 서비스가 이어진다(down 중 클라이언트 I/O 확인). ONTAP에서 관리 프로세스를 멈춰도 데이터 경로가 서는 것과 비슷하다 [추론]. 다음 `up`의 agent가 그대로 이어받는다(R1'). (나) 인스턴스에 라벨을 붙이고 내리기 스크립트가 라벨로 멈춘다. (다) agent가 SIGTERM에서 인스턴스를 멈춘다(그러면 agent 업데이트만으로도 데이터가 끊긴다). compose가 `anf-vnet`을 만들면 `down`이 인스턴스가 붙은 네트워크를 지우려 할 수 있다 [추론, 시험 안 함]. 준비 단계가 만들고 compose는 `external`로 쓰는 쪽이 이 문제를 피한다 [추론].
- **이미지.** agent는 `ubuntu:24.04`(호스트와 같은 LVM·iptables)와 `docker:29.1.3-cli`의 CLI 복사, anf-api는 `python:3.12-slim`. 의존성 고정(`pip freeze` 값 또는 `pyproject.toml` 하한)과 빌드 컨텍스트(루트 275 MB → `.dockerignore` 또는 하위 폴더 컨텍스트)를 정해야 한다. agent·anf-api를 한 이미지로 합칠지도 선택이다(합치면 anf-api도 311 MB).
- **대시보드.** nginx 다단계(74 MB, 설정 파일 하나) 대 vite preview(534 MB, 설정 없음). 포트(이번 8081).
- **LVM 백업.** 컨테이너의 `/etc/lvm/archive`·`backup`은 컨테이너와 함께 사라진다. 호스트 경로를 바인드할지, 그대로 둘지. 호스트 archive는 이미 17,5xx개로 `lvcreate`마다 경고를 찍는다(이번 스파이크와 상관없는 기존 상태).
- **`ensure_shared_ns`의 판정.** 재귀 바인드에서는 `findmnt -no PROPAGATION --mountpoint ns`가 `private`·`shared` 두 줄을 돌려줘 `split(",")` 판정이 "shared 아님"으로 읽고 `--make-rshared`를 다시 했다(위쪽 마운트라 해가 없었다). 비재귀 바인드에서는 한 줄 `shared`다.

## 사용자에게 물을 것

- WSL Ubuntu에 `docker-compose-v2`(와 `docker-buildx`)를 apt로 설치할지. FR-13 수락 기준이 docker compose를 말한다. 설치하지 않으면 PRD 문구를 스크립트로 바꿀지.
- 스택을 내릴 때 볼륨 인스턴스(데이터 서비스)도 멈출지, 남길지.
- agent를 특권 컨테이너로 둘지(docker 그룹만으로 전부 뜬다, docker 그룹 = root 권한) 호스트 root 프로세스로 남길지.

## 정리

ARM API로 볼륨 `avol`·`bvol`·`cvol`, 풀, 계정 `s9-acct`·`s9-acct2`를 지웠다(`avol`은 P3가 남긴 `ns/s9a/.snapshot`을 `chattr -i` 후 지우고 다시 DELETE해서 `Succeeded`). 클라이언트 `s9-cli1`·`s9-cli2`(마운트를 먼저 풀고), 스택 컨테이너 `s9-agent`·`s9-api`·`s9-prom`·`s9-dash`·`s9-dashp`(익명 볼륨 포함), 이름 있는 볼륨 `s9-api-data`, 멈춘 실험 컨테이너를 지웠다. 시작 상태(막 부팅한 WSL)로 돌리려고 호스트 `ns` 바인드를 풀고 VG `anf`를 비활성화하고 loop를 떼고, 스파이크 중 올라간 모듈(`act_mirred`, `cls_matchall`, `sch_ingress`, `sch_htb`, `ifb`, `dm_thin_pool`)을 내렸다. 실험 이미지 `s9-agent`·`s9-api`·`s9-dash`·`s9-dash-preview`와 이번에 pull한 바탕 이미지 `ubuntu:24.04`·`python:3.12-slim`·`node:22-alpine`·`nginx:1.28.0-alpine`·`docker:29.1.3-cli`를 지웠다(digest는 `s9/results/base-images.txt`). `/var/tmp/s9`는 원자료를 scratchpad `s9/results/`로 복사한 뒤 지웠다. 정리 뒤 포트 8080·8081·8090·9090·4173 비어 있음, `anf-nfs-*`·`s9-*` 컨테이너 없음, Docker 볼륨 0개, `anf-clone` 마운트 없음, loop·dm 장치 없음, `/var/lib/anf-clone/{ns,exports}` 비어 있음, 모듈은 `nfsd`만, `fs.leases-enable = 0`을 확인했다. 이미지 `anf-nfs-server`·`anf-nfs-client`·`prom/prometheus:v3.15.1`(과 원래 있던 `anf-s2-client:spike`, `anf-nfs-client:spike`, `alpine:3.20`), 네트워크 `anf-vnet`, `/var/lib/anf-clone/aggr0.img`는 그대로다. 원래 있던 dangling 이미지 5개(45시간~2일 전)는 건드리지 않았다. WSL 유휴 종료 방지용 `sleep`도 끝냈다. 제품 코드와 저장소 파일은 바꾸지 않았다(이 파일만 새로 썼다, 커밋 안 함).
