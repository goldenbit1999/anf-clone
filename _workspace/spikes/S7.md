## Q1: veth 찾기, IFB 이름, 모듈 (P1)

| # | 시험 | 결과 |
| --- | --- | --- |
| V1 | 인스턴스 쪽 `eth0`의 짝 ifindex | 두 방법이 같은 값을 준다. (a) `docker exec <인스턴스> cat /sys/class/net/eth0/iflink`(S2 방식) → 5·6·7. (b) `nsenter -t <docker inspect .State.Pid> -n ip -j link show eth0`의 `link_index` → 5·6·7(`eth0@if5` 등). (b)는 컨테이너 이미지·exec에 기대지 않고, agent가 되돌리기 창에서 이미 쓰는 pid + `nsenter` 경로와 같다(`nfs_instance._pid`, `_iptables`) |
| V2 | ifindex → 호스트 이름 | `ip -j link show`에서 `ifindex`가 같은 항목: `vethd43a5fd`(A), `veth7801a86`(B), `vethec31f38`(C). 셋 다 `anf-vnet` 브리지 `br-8a66a434fa15`의 포트다. 이름은 Docker가 무작위로 짓는다(`veth` + 7자리 hex) |
| V3 | 호스트 쪽에서만 찾기 | `ip -o link show type veth`는 `vethd43a5fd@if2 … link-netnsid 0`처럼 짝이 모두 `if2`(컨테이너 안 `eth0`의 index)라 짝 index로는 구분되지 않는다. `link-netnsid`(0·1·2)는 호스트 기준 netns id라 컨테이너와 이어 주려면 다시 그 netns를 열어야 한다. 그래서 컨테이너 쪽에서 출발하는 V1이 간단하다 |
| V4 | 재시작 뒤 (P5a·P5b) | `docker stop/start`, `docker rm` + agent의 `docker run` 모두 veth가 새로 생기고 이름과 ifindex가 바뀐다(아래 Q5). 그래서 veth 이름이나 ifindex를 저장해 두면 안 되고, tc를 걸 때마다 V1로 다시 찾아야 한다 |
| N1 | `ifb` 모듈 자동 로드 | `ifb`가 없을 때 `ip link add ifb-s7probe type ifb`가 모듈을 자동으로 올리면서(`rtnl-link-ifb` 별칭) **`ifb0`·`ifb1`도 만든다**(모듈 기본값 `numifbs=2`). 지우고 `rmmod ifb` 뒤 `modprobe ifb numifbs=0`으로 올리면 기본 장치가 생기지 않는다. 다른 모듈(`sch_htb`, `cls_matchall`, `act_mirred`, `sch_fq_codel`)은 `tc`가 필요할 때 자동으로 올렸다 |
| N2 | 이름 길이 | 16자 `anf-q-0123456789`는 `Error: Attribute failed policy validation.`(rc 2), 15자는 된다(IFNAMSIZ 16, NUL 포함). uuid 32자리는 들어가지 않는다 |
| N3 | altname | `ip link property add dev anf-q-012345678 altname anfq-<uuid32>`(rc 0)는 되고 `ip link show anfq-<uuid32>`도 찾는다. 그러나 **`tc qdisc add dev anfq-<uuid32>`는 `Cannot find device "anfq-5700000000"`**(iproute2 6.1의 tc가 이름을 15자로 자른다). tc에는 altname을 쓸 수 없다 |
| N4 | 인스턴스 netns 안의 IFB | `nsenter -t <pid> -n ip link add ifb0 type ifb` rc 0. netns 안에는 `lo, eth0@if5, ifb0`이 보이고 호스트의 IFB 목록에는 없다. 이름은 netns마다 따로라 모든 인스턴스가 `ifb0`을 쓸 수 있다(P8에서 측정과 수명 확인) |
| N5 | 인스턴스 이미지의 도구 | `anf-nfs-server`(alpine)에는 `tc`, `ip`, `iptables`가 없다. 호스트의 `tc`를 `nsenter -n`으로 쓰면 이미지를 바꾸지 않아도 된다(되돌리기 결정 13의 iptables와 같은 방식) |
| N6 | tc JSON | iproute2 6.1의 `tc -s -j class show`는 HTB 클래스를 JSON으로 내지 않고 텍스트를 낸다(qdisc는 `-j`가 된다). 카운터를 읽으려면 텍스트의 `class htb 1:1 … Sent N bytes`를 읽거나 qdisc JSON의 `bytes`를 쓴다 |
| N7 | HTB 경고 | 10 MiB/s 이상의 클래스를 만들거나 바꿀 때마다 `Warning: sch_htb: quantum of class 10001 is big. Consider r2q change.`가 stderr로 나온다(rc 0). 클래스가 하나라 quantum은 동작에 영향이 없다 [추론]. `quantum`을 주거나 `r2q`를 키우면 사라진다 [시험 안 함] |
| N8 | 다시 걸기의 멱등성 (P6b) | 이미 있는 HTB 루트에 `tc qdisc replace dev <ifb> root handle 1: htb default 1`은 **`Error: Change operation not supported by specified qdisc.`(rc 2)**. 클래스 `tc class replace`(rc 0)와 leaf `tc qdisc replace … fq_codel`(rc 0)은 된다. leaf 종류를 바꾸는 replace(fq_codel → pfifo)는 `Invalid qdisc name: must match existing qdisc`라서 지우고 다시 만들어야 했다(P2c). 그래서 "있으면 건너뛰고 없으면 만든다"나 "지우고 다시 만든다"로 써야 한다 |

## Q2: 정확도 (P2a·P2b, 보정 없음)

S2 T1n과 같은 구성이다: 인스턴스의 호스트 쪽 veth에 `clsact`, `ingress`·`egress` 모두 `matchall action mirred egress redirect dev <ifb>`, IFB에 `htb default 1` + 클래스 `1:1 rate = ceil = 설정값` + leaf `fq_codel`. A는 `ifb-s7a`, B는 `ifb-s7b`. 클라이언트 `s7-c1` 하나가 A(v4.1), B(v3), C(v4.1)를 마운트했다.

| 조건 | 데이터 중앙값 MiB/s (범위, 5회) | 설정 대비 | wire 중앙값 | 데이터/wire |
| --- | --- | --- | --- | --- |
| 10, v4.1 쓰기 | 9.424 (9.401~9.431) | 94.2% | 9.884 | 0.9534 |
| 10, v4.1 읽기 | 9.438 (9.428~9.471) | 94.4% | 9.892 | 0.9542 |
| 10, v3 쓰기 | 9.475 (9.439~9.477) | 94.7% | 9.937 | 0.9535 |
| 10, v3 읽기 | 9.401 (9.392~9.436) | 94.0% | 9.853 | 0.9542 |
| 30, v4.1 쓰기 | **22.44** (17.72~28.01): 27.95·28.01 / 20.58·22.44·17.72 | 저하 없는 회 93.2~93.4% | 23.50 | 0.9550 |
| 30, v4.1 읽기 | 27.66 (27.55~27.81) | 92.2% | 28.96 | 0.9551 |
| 30, v3 쓰기 | 28.03 (19.64~28.14), 저하 1회 | 93.4% | 29.35 | 0.9548 |
| 30, v3 읽기 | 27.62 (27.58~27.90) | 92.1% | 28.92 | 0.9551 |

읽기+쓰기 동시 (15 s, 같은 볼륨에 읽기 job 하나와 쓰기 job 하나):

| 조건 | 회별 읽기 + 쓰기 = 합 MiB/s |
| --- | --- |
| 10, v4.1 ×3 | 5.59 + 3.85 = 9.44 / 4.93 + 4.49 = 9.42 / 4.89 + 4.56 = 9.44 |
| 10, v3 ×2 | 5.99 + 3.46 = 9.44 / 6.09 + 3.37 = 9.47 |

- 합이 단독 측정과 같은 9.44 MiB/s다. 읽기와 쓰기가 한 버킷을 나눠 쓴다(S2와 같음). 각 첫 회는 fio가 파일을 `--size=1024M`으로 늘리느라 wire 바이트가 데이터의 7.6배였다(데이터/wire 0.13). 합산 값은 fio가 잰 구간이라 영향이 없다.
- 비율이 S2(약 95%)보다 조금 낮다: 10 MiB/s 94.0~94.7%, 30 MiB/s 92.1~93.4%. 두 가지가 곱해진다.
  - 데이터/wire 0.953~0.955: 헤더 비율(Q7).
  - wire/설정 0.985~0.994(10 MiB/s), 0.964~0.978(30 MiB/s): fio의 측정 구간(시작·끝의 램프 포함) 동안 HTB가 내보낸 양이다. 1초 창으로 보면 10 MiB/s에서 9.88~9.96, 30 MiB/s에서 29.0~29.7이라(Q3) 대부분은 구간 끝 처리다 [추론]. 30 MiB/s에서 조금 더 낮은 것은 HTB의 기본 burst가 1541 B로 작고 GSO 패킷이 최대 68,130 B라서일 수 있다 [추정, 시험 안 함].
- **쓰기에서 가끔 저하가 난다 (30 MiB/s).** 30 MiB/s v4.1 쓰기 5회 중 3회, v3 5회 중 1회, P2c·P7에서도 6회 중 1회꼴로 17~22 MiB/s가 나왔다. 읽기는 한 번도 없었다(30 MiB/s 읽기 24회). 10 MiB/s에서는 없었다. S2 관찰 3의 "첫 회 저하"와 같은 현상으로 본다. 원인을 좁힌 것(P2c·P2d·P2e):
  - leaf가 `fq_codel`이면 450 MiB 쓰기마다 leaf 드롭 25~35개(GSO 패킷), 클라이언트 TCP 재전송 830~1,120 세그먼트, RTO 0이다. 드롭이 많은 회와 저하 회가 맞지 않았다(저하 회는 드롭 14~15개로 오히려 적었다).
  - leaf를 `pfifo limit 1000`으로 바꾸면 드롭·재전송이 0인데도 6회 중 1회 22.38 MiB/s가 나왔다. 그래서 AQM 드롭은 원인이 아니다.
  - 90 s 연속 쓰기(P2e)의 1초 표본: 6~17 s 구간에 wire가 11~15 MiB/s로 떨어졌는데 그동안 **HTB backlog가 대부분 0**(제한기가 기다리게 하지 않음)이고 `/proc/pressure/io`의 `some avg10`이 3.9 → 46%로 올랐다. 그 뒤 81 s 동안은 29.0~29.7을 유지했다.
  - 같은 볼륨 ext4에 NFS·tc 없이(컨테이너에 바인드) `--rate=30m` 직접 쓰기 8회는 모두 30.06 MiB/s, 버퍼 쓰기 + fsync 3회는 29.5였다.
  - 그래서 제한기가 아니라 서버 쪽 쓰기 경로가 몇 초씩 막히는 것이다 [추정]. NFS를 거칠 때만 보인 이유(knfsd의 `sync` export, COMMIT, 쓰기 순서)는 확인하지 못했다.
- 시계: 이번 측정에서 게스트/호스트는 0.9948(120 s), 1.0009(300 s, 호출 지연 0.58 s)였다. S2의 0.908과 달리 지금은 게스트 단조 시계가 호스트와 거의 같다. 그래서 이번에는 게스트 값을 실시간 값으로 읽어도 1% 안쪽이다. 시계 비율이 바뀌는 원인은 확인하지 못했다(WSL 재시작마다 다를 수 있다).

WRITE 하나(1 MiB)가 연결을 차지하는 시간은 1 MiB / 0.0625 MiB/s ≈ 16 s(헤더 포함 17 s)라, 그 사이의 다른 RPC가 그만큼 기다린다 [추론]. 그래서 이 구성(wsize 1 MiB, lease 30 s)에서는 한도가 1 MiB/30 s ≈ 0.035 MiB/s 밑으로 가면 갱신 간격이 lease를 넘을 수 있다 [추론, 시험 안 함]. 넘더라도 6.18 knfsd는 courteous server라 충돌이 없으면 상태를 지우지 않는다 [추론, 확인 안 함].
- **0.0625 MiB/s에서는 RPC 시간 초과(timeo=600 = 60 s)가 난다.** 대기열 16 MiB가 빠지는 데 약 256 s가 걸려 WRITE 완료 지연이 평균 266 s, 최대 448 s였다. mountstats의 WRITE timeouts가 16·19이고 dmesg에 "not responding, still trying" ↔ "OK"가 번갈아 나왔다. 그래도 trans = ops(재전송 없음), connect_count 그대로(연결을 끊지 않음), fio 오류 0이다. hard 마운트라 앱에는 오류가 가지 않았다. soft 마운트라면 이 시간 초과가 EIO가 된다 [추론, 시험 안 함]. 1 MiB/s의 최대 31.4 s는 60 s 안쪽이라 메시지가 없었다.
- **같은 TCP 연결의 작은 요청은 큰 쓰기 뒤에서 기다린다.** 같은 마운트의 `ls`가 3.125 MiB/s에서 약 1 s, 1 MiB/s에서 6~9 s, 0.0625 MiB/s에서 47~76 s였다. 대기열 전체(16 MiB)를 기다리지는 않는다(0.0625 MiB/s에서 256 s보다 짧다). 클라이언트 RPC 계층이 요청 단위로 번갈아 보내고, 소켓 버퍼에 들어간 WRITE만 앞선다 [추론].
- **다른 연결은 거의 영향이 없다.** 같은 인스턴스의 다른 클라이언트는 0.0625 MiB/s에서도 `ls` 0.6 s, 4 KiB 쓰기 1.8 s 안쪽이고 새 마운트가 1.3 s 안에 됐다. leaf `fq_codel`이 흐름(5-tuple)마다 대기열을 나눠 큰 흐름 뒤에 줄 세우지 않기 때문이다 [추론]. P2c의 `pfifo limit 1000`이면 GSO 패킷 1,000개(최대 64 KB씩)가 한 줄로 쌓이므로 이 이점이 없다 [추론, 낮은 한도에서 시험 안 함].
- **실용 하한 (관찰에서 나온 것).**
  - 동작(마운트, 읽기·쓰기, lease, 오류 없음)은 0.0625 MiB/s까지 됐다.
  - 대기열 바이트 / 한도가 60 s를 넘으면(iodepth 16 × 1 MiB이면 약 0.27 MiB/s 미만) 커널 로그에 "not responding"이 나온다 [추론, 0.0625와 1 사이는 재지 않음]. 버퍼 쓰기(`cp`)는 클라이언트가 더 많이 쌓을 수 있어 더 높은 한도에서도 나올 수 있다 [추론, 시험 안 함].
  - 같은 연결의 메타데이터 지연이 대략 "대기열이 비는 시간의 일부"만큼 늘어 0.0625 MiB/s에서는 1분을 넘는다. 검증 스크립트의 제한 시간과 `wait_ready`·`docker exec` 탐침이 이 지연에 걸리지 않게 해야 한다.
  - `rsize/wsize=262144` 같은 작은 블록이 이 지연을 줄이는지는 재지 않았다.

S5의 "스냅샷 뒤에 만든 파일의 fd는 ESTALE"과 같은 현상이다. 크기가 이미 맞는 파일로 다시 한 P5c2는 오류가 없었다. tc 상태(같은 veth, 필터 1/1, HTB 10 MiB/s, iptables 정리)는 P5c에서도 같았다.
- `docker stop`, `docker rm`, WSL 재시작 흉내(L5) 모두 **veth가 새로 생겨 tc를 다시 걸어야 한다**. 호스트 IFB는 남아 있어 재사용할 수 있지만, 지우지 않으면 볼륨 삭제 뒤에도 남는다(L7). agent 자체의 재시작은 커널의 tc 상태를 건드리지 않는다(L4).
- 진짜 WSL 재시작은 하지 않았다. 그때는 IFB와 tc가 모두 사라지고 `recover()`가 인스턴스를 `docker start`로 띄운다(L5와 같은 경로) [추론].
- L6의 첫 측정(P5e)은 fio의 초당 로그로 봐서 "제한 없이 흘렀다"로 잘못 읽었다. fio의 `--write_bw_log`는 완료가 없는 초를 건너뛰어 멈춘 구간이 보이지 않는다. 호스트 veth의 rx+tx 카운터(`s7/vsample.py`)로 다시 잰 P9a가 위 값이다. 그래서 지울 때는 **clsact(필터)를 먼저, IFB를 나중에** 지워야 한다. 이 문서의 다른 멈춤 판정(L3, P8·P9b)은 HTB나 veth 카운터로 봤다.
- L1·L2·L5 뒤 다시 걸 때 `Error: Change operation not supported by specified qdisc.`가 났다. IFB가 남아 있어 `tc qdisc replace … root htb`가 실패한 것이고(Q1 N8), 클래스·leaf·필터는 걸렸다.
- 다시 걸기 전(L1·L2·L5)에는 **제한이 없다**. 인스턴스를 띄운 뒤 tc를 걸면 그 사이에 클라이언트가 제한 없이 쓸 수 있다. L5에서 dmesg에 `vethb85b6ec: Caught tx_queue_len zero misconfig`가 한 줄 나왔다(Docker veth의 txqueuelen 0에 qdisc를 붙일 때의 커널 알림, 동작 영향 없음 [추론]).

| M3 | 같은 netns에서 iptables `INPUT -i eth0 -j DROP` 5 s (되돌리기 창과 같은 규칙, P9b, B) | 호스트 veth 카운터: 9.47~9.58 → 1.54, 0.0 ×5 → 2.22 → 9.44~9.58. 막는 동안 멈추고 풀자마자 한도로 돌아온다. fio 오류 0, clat max 8.39 s. tc ingress가 먼저 패킷을 `ifb0`으로 보내고, `ifb0`이 패킷을 `eth0`의 입력으로 되돌린 뒤 netfilter `INPUT -i eth0`가 버린다 [추론: 결과가 그렇게 보인다] |
| M4 | `docker stop` | 호스트의 IFB 목록에 새 장치가 없다. netns가 사라지면서 `ifb0`도 사라졌다 |
| M5 | `docker start` (준비 0 s) | 새 netns: `lo, eth0@if52`만, clsact 없음 → 제한 없음(185.9 MiB/s. 이때 2 GiB 볼륨이 차서 `No space left on device`가 났다. 시험 파일 크기 탓이고 tc와 무관). 다시 걸면 9.45 |
| M6 | agent 되돌리기 (`PATCH restore_to`, 2.85 s) | 쓰는 중 2~3 s 멈춘 뒤(fio 초당 `… 10.0, 3.0, 4.0, 10.0, …`, 빈 초는 로그에서 빠짐) 한도로 이어 감, 오류 0. 끝난 뒤 netns의 clsact·`ifb0`·HTB 10 MiB/s 그대로 |
| M7 | agent `DELETE` (1.23 s) | 호스트에 남는 IFB가 없다(정리할 것 없음) |

- 수명이 인스턴스 netns와 같다: 인스턴스를 멈추거나 지우면 tc도 사라지고, 띄울 때마다 다시 걸어야 하는 것은 호스트 쪽 방식과 같다. 다른 점은 남는 장치가 없다는 것과, 다시 걸기가 veth 찾기 없이 "pid → nsenter"뿐이라는 것이다.
- 측정 카운터도 netns 안에서 읽어야 한다(`nsenter … tc -s class show dev ifb0`). 메트릭(ADR §8, IFB의 Sent bytes)을 읽는 쪽도 pid를 알아야 한다.

## Q7: 헤더 보정 (P7)

rate = 목표 / 0.9534(P2의 10 MiB/s 쓰기 데이터/wire)로 걸었다: 10 → 10.4888 MiB/s(87,986,239 bit/s), 30 → 31.4663 MiB/s(263,958,716 bit/s). 첫 회 워밍업 + 3회.

| --- | --- | --- | --- |
| 10 | v4.1 쓰기 | 9.890 (9.883~9.891) | 98.9% |
| 10 | v4.1 읽기 | 9.878 (9.780~9.884) | 98.8% |

| 10 | v4.1 읽기+쓰기 합 ×3 | 9.904 (9.852~9.907) | 99.1% |
| 10 | v4.1 쓰기 `bs=64k` ×1 | 9.927 | 99.3% |
| 10 | v4.1 쓰기 `bs=4k` ×1 | 1.476 (지연이 한계, 대역폭 아님) | — |
| 10 | v4.1 임의 읽기 `bs=4k` 15 s ×1 | 9.048 (2,316 IOPS) | 90.5% |

| 30 | v3 읽기 | 29.143 (28.85~29.245) | 97.5% |

- 보정해도 **모든 회가 목표 이하**다(최대 99.3%). 남은 1~3%는 HTB가 fio 구간 동안 rate보다 덜 내보낸 몫(Q2)이다.
- 데이터/wire의 이론 상한 [추론]: `anf-vnet` MTU 1500, TCP 타임스탬프 사용 → MSS 1448. 데이터 세그먼트 하나의 L2 길이는 1448 + 32(TCP) + 20(IP) + 14(Ethernet) = 1514 B라 1448/1514 = **0.9564**가 상한이다. 반대 방향 ACK와 RPC 헤더도 같은 클래스에서 세므로 실제 값은 그보다 낮다(측정 0.9532~0.9551). 요청이 작을수록 RPC 헤더 비율이 커져 더 낮아진다. 그래서 보정 계수를 1/0.9564 = 1.0456 이하로 두면 I/O 모양과 상관없이 데이터가 rate를 넘지 않는다 [추론]. MTU가 바뀌면 이 값도 바뀐다.
- 보정 없이 쓰면 허용 오차를 "설정값의 -10% ~ 0%"로 잡아야 한다(Q2의 92.1~94.7%). 보정하면 "-3% ~ 0%" 안에 들어온다(저하 회 제외).

## 설계에 주는 선택지

설계는 정하지 않는다. 관찰에서 나온 선택지와 그 근거만 적는다.

- **tc를 어디에 거나.** 두 방식 모두 정확도(Q2·M1), 실시간 변경(Q3·M2), 되돌리기 창과의 공존(L3·M3·M6)이 같았다. 차이는 이름, 정리, 카운터 읽기다.
  - (가) 호스트 쪽 veth + 호스트 IFB (S2 T1n, ADR §7.3에 적힌 방식). veth 이름과 ifindex가 시작마다 바뀌어 걸 때마다 pid → `link_index` → `ip -j link`로 찾아야 한다(V1·V4). IFB 이름은 15자라 uuid를 못 쓰므로 규칙이 필요하다. 예: 볼륨 IP 끝자리(`anf-q-129`: IP는 agent가 172.30.0.128/25에서 살아 있는 볼륨마다 하나 고르므로 동시에는 겹치지 않는다 [추론]. 다만 지운 볼륨의 IP를 새 볼륨이 다시 받으므로(P8의 D가 C의 .131을 받음) 지울 때 IFB를 지우지 않으면 새 볼륨이 남은 IFB와 그 HTB 값을 물려받는다) 또는 uuid 앞부분(겹칠 수 있다). IFB는 인스턴스보다 오래 살아서 볼륨 삭제 뒤에도 남고(L7), 지울 때 clsact를 먼저 지워야 하며(L6), 남은 IFB에 다시 걸 때 `qdisc replace … root htb`가 실패한다(N8). 대신 카운터를 호스트에서 IFB 이름만으로 읽을 수 있고, 인스턴스가 멈춰 있어도 HTB 설정이 남는다.
  - (나) 인스턴스 netns 안 `eth0` + netns 안 `ifb0` (P8). 이름이 모두 `ifb0`이고 veth를 찾지 않는다. 인스턴스를 멈추거나 지우면 함께 사라져 남는 것이 없다(M4·M7). 되돌리기 창이 이미 쓰는 `_pid()` + `nsenter -n` 경로와 같다. 대신 카운터를 읽을 때마다 pid가 필요하고(`nsenter … tc -s class show dev ifb0`), 인스턴스가 멈춘 동안에는 읽을 것이 없다.
- **언제 거나.** 인스턴스를 띄우는 모든 경로가 `NfsInstances.start()` 하나를 지난다(`ensure()`와 `FlexVolumes.recover()`의 루프, `flexvol.py:178`). 볼륨 생성, 같은 요청의 재전송, 되돌리기 뒤 재전송, 시작 복구가 모두 이 경로다.
  - (가) `start()` 바로 뒤, `wait_ready()` 전에 건다. `docker run -d`·`docker start`는 컨테이너가 시작된 뒤 돌아오고 knfsd는 그 뒤 진입점이 띄우므로, 서비스 전에 제한이 걸린다 [추론, 시험 안 함: 스파이크는 준비가 끝난 뒤에 걸어서 L1·L2·L5의 제한 없는 창을 봤다]. 진입점이 nfsdcld의 클라이언트 때문에 유예 기간을 기다리는 경우(L1 14 s, L5 20 s)에도 그 전에 걸린다. `start()`는 인스턴스가 이미 돌고 있으면 아무것도 하지 않으므로, 그 뒤에 거는 코드는 이미 tc가 있는 인스턴스에서도 불린다(아래 멱등성).
  - (나) 진입점이 직접 건다. 이미지에 iproute2가 없어(N5) 이미지를 바꾸고 한도를 환경 변수로 넘겨야 한다. 실시간 변경은 여전히 밖에서 해야 해서 두 곳이 tc를 다루게 된다.
  - 이미 도는 인스턴스의 한도 변경은 `tc class change` 하나다(Q3). 다시 걸기를 멱등으로 하려면 "없으면 만들고 있으면 `class change`" 또는 "지우고 다시 만들기"로 써야 하고, HTB 루트에 `qdisc replace`를 쓰면 안 된다(N8).
- **한도를 어디에 기억하나.** agent는 DB 없이 LVM 태그에 볼륨 속성(경로, uuid, IP, 프로토콜)을 둔다. `recover()`가 인스턴스를 다시 띄울 때 tc를 다시 걸려면 한도를 알아야 한다(L5: 복구 뒤 제한 없이 78.67 MiB/s).
  - (가) 다른 속성처럼 LVM 태그로 둔다. agent 혼자 복구할 수 있다.
  - (나) anf-api가 다시 보낸다. anf-api는 agent나 WSL이 다시 시작한 것을 모르므로 그 사이 제한이 없다 [추론].
  - ONTAP REST에서 볼륨에 상한을 주는 자리는 `qos.policy.max_throughput_mbps`(볼륨 POST·PATCH) 또는 별도 정책 `/api/storage/qos/policies`다(조사 브리프 [ONTAP O1]). 단위(Mbps/MB/s vs MiB/s)는 브리프에서 `[미확인]`이다.
- **헤더 보정.**
  - (가) 보정하지 않는다: 데이터가 설정의 92~95%(Q2). wire 바이트(헤더 포함)는 설정에 가깝다.
  - (나) rate = 목표 / 0.9564(MTU 1500의 이론 상한): 어떤 I/O 모양에서도 데이터가 목표를 넘지 않는다 [추론]. 측정한 0.9534보다 0.3% 덜 보정하므로 98% 안팎이 예상된다 [추론, 이 값으로는 재지 않음].
  - (다) rate = 목표 / 0.9534(측정값, P7): 98.0~99.3%로 모든 회가 목표 이하였다. 다만 30 MiB/s 읽기의 데이터/wire가 0.9551이라 HTB가 rate를 꽉 채우면 목표의 100.2%가 될 수 있다 [추론, 관찰되지는 않음].
  - 메트릭(ADR §8, IFB의 Sent bytes)은 헤더와 양방향을 함께 세므로 보정 여부와 상관없이 데이터 처리량보다 4.5% 남짓 크게 나온다(Q2의 데이터/wire).
- **leaf qdisc.** `fq_codel`(S2의 선택)은 낮은 한도에서 다른 연결의 지연을 작게 지켰다(Q4: 0.0625 MiB/s에서 ≤ 1.8 s). 30 MiB/s 쓰기에서 450 MiB마다 드롭 25~35개와 재전송 약 900개가 생겼지만 처리량은 pfifo와 같았다(P2c). `pfifo`는 드롭이 없지만 한 줄 대기열이라 그 이점이 없다 [추론, 낮은 한도에서 시험 안 함].
- **HTB 경고.** 10 MiB/s 이상에서 `quantum … is big` 경고가 stderr에 나온다(rc 0, N7). `Runner.run`은 종료 코드만 보므로(`runner.py:44`) 동작에는 상관없다. 없애려면 `quantum`이나 `r2q`를 준다 [시험 안 함].
- **작은 검증 볼륨의 낮은 Auto 한도 (브리프 열린 질문 2).** 공식대로 두면(브리프 (b)) 1 GiB Premium = 0.0625 MiB/s에서도 마운트·읽기·쓰기·lease가 됐다(Q4). 대신 같은 연결의 `ls`가 47~76 s, 큰 쓰기의 대기열 비우기가 268 s, dmesg에 RPC 시간 초과가 나온다. 실서비스의 최저인 Standard 50 GiB(0.78 MiB/s, 브리프)는 이번 1 MiB/s 결과(같은 연결 `ls` 6~9 s, 시간 초과 없음)와 비슷한 범위로 본다 [추론]. Manual QoS(최소 1 MiB/s)나 큰 sparse 볼륨으로 검증하면(브리프 (a)) 이 지연을 피한다. agent의 `wait_ready`는 `docker exec`로 파일을 볼 뿐 NFS를 지나지 않아 영향이 없다 [추론].
- **검증 방법 (verifier에게 넘길 관찰).**
  - 판정은 HTB나 veth 카운터의 1초 창으로 한다. fio의 초당 로그는 완료가 없는 초를 건너뛰어 멈춤을 숨긴다(L6, Q3).
  - 30 MiB/s 쓰기는 서버 쪽 저하(Q2) 때문에 중앙값이 흔들린다. 10 MiB/s, 읽기, 또는 회 수를 늘리고 저하 회를 따로 보는 방법이 있다.
  - fio의 첫 회는 파일을 늘리는 쓰기가 섞여 버린다(Q2). 되돌리기와 함께 시험할 때는 스냅샷 전에 파일을 fio `--size`대로 만들어 둔다(P5c).
  - 인스턴스를 다시 띄운 직후(재시작, 복구)에 제한이 있는지를 따로 본다(L1·L2·L5).
  - 이번에는 게스트 시계가 호스트와 1% 안쪽이었다. S2에서는 0.908이었으므로 검증 때 다시 잰다.

## 정리

agent API로 스파이크 볼륨 A·B(정리 단계), C(P5 L7), D(P8 M7)를 지웠다. 클라이언트 컨테이너 `s7-c1`, `s7-l1`~`s7-l4`를 지웠다. 호스트 IFB(`ifb-s7a`·`ifb-s7b`·`ifb-s7c`)와 시험용 IFB를 지웠고, 스파이크가 올린 모듈(`ifb`, `sch_htb`, `sch_ingress`, `cls_matchall`, `act_mirred`)을 내렸다. `sch_fq_codel`은 시작 전부터 올라와 있어 그대로 두었다. agent를 멈췄다(포트 8080·8090 비어 있음). 시작할 때의 상태(막 부팅한 WSL)로 돌리려고 `ns` 바인드를 풀고 VG `anf`를 비활성화하고 루프 장치를 떼었다. agent가 시작할 때 이것들을 다시 한다. 정리 뒤 `anf-nfs-*`·`s7-*` 컨테이너 없음, IFB 0개, `/var/lib/anf-clone/{ns,exports}` 비어 있음, `fs.leases-enable = 0`을 확인했다. 이미지 `anf-nfs-server`·`anf-nfs-client`, 네트워크 `anf-vnet`, `/var/lib/anf-clone/aggr0.img`는 그대로다. 측정 클라이언트 이미지 `anf-s2-client:spike`는 S2 뒤부터 있던 것이라 남겼다. 유휴 종료 방지용 `sleep`도 끝냈다. 제품 코드는 바꾸지 않았다.
