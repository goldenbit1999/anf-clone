## 환경 (Q1)

1회차와 2회차의 세 VM이 같은 이미지·커널이었다.

- 이미지 `ubuntu24 20261101.360.1`, `Ubuntu 24.04.5 LTS`, 커널 `7.0.0-1017-azure #17~24.04.1-Ubuntu SMP PREEMPT`(WSL은 6.18). 하이퍼바이저 Microsoft, 시계 소스 `tsc`.
- CPU 4개, 메모리 total 15,983 MiB(시작 때 used 899 / available 15,084), swap 3,071 MiB. WSL(약 7 GB)의 두 배다.
- 디스크: `nvme0n1` 150 G, `/dev/root` 145 G 중 59 G 사용, 86 G 여유. `/mnt`·`/var/tmp`·`/tmp`도 같은 `/`다. `/`는 ext4 `rw,discard,journal_async_commit,nobarrier,commit=30,data=writeback`이다(WSL과 다른 마운트 옵션 [WSL 값은 이번에 보지 않음]).
- cgroup: `cgroup2fs`, 컨트롤러 `cpuset cpu io memory hugetlb pids rdma misc dmem`.
- 사용자: `runner`(uid 1001, groups `adm users docker systemd-journal`), `(ALL) NOPASSWD: ALL`. 작업 폴더 `/home/runner/work/anf-clone/anf-clone`은 `runner` 소유다.
- Docker: Client·Server 28.0.4, containerd v2.4.2, runc 1.5.2, overlay2, Cgroup Driver `systemd`, Cgroup Version 2, Security Options `apparmor` `seccomp`. `/etc/docker/daemon.json`은 없다.
- AppArmor: 로드됨, 프로필 123개(enforce 28). 세 실행의 dmesg에 `apparmor="DENIED"`가 0줄이다(privileged 컨테이너는 unconfined).
- sysctl 시작값: `fs.leases-enable = 1`, `kernel.dmesg_restrict = 1`(dmesg를 읽으려면 sudo가 필요하다).
- 도구: `lvcreate thin_check mkfs.ext4 docker iptables nsenter ip tc setpriv ss findmnt chattr lsattr resize2fs blkid e2fsck dmsetup fallocate losetup modprobe`가 모두 있다. `iptables v1.8.10 (nf_tables)`, `iproute2-6.1.0`(WSL과 같은 버전), 시스템 `python3` 3.12.3.

## 전체 묶음 (Q5, 2회차)

두 job 모두 `sudo env ANF_TEST_OUT=/var/tmp/anf-clone-tests/run bash scripts/run-dataplane-tests.sh`(인자 없음)를 돌렸다. 실행기는 13개 파일에서 113개를 수집했다. 실행 전 데이터 플레인은 비어 있었다(기준선 LV·컨테이너 없음). 두 job은 서로 다른 VM에서 동시에 돌았다.

## 설계에 주는 선택지

설계는 정하지 않는다. 관찰에서 나온 선택지와 그 근거만 적는다.

- **러너.** 호스트 러너 `ubuntu-24.04`로 묶음 전체가 된다(`private` 113/113). self-hosted 러너는 필요 없다. 다만 커널이 WSL(6.18)과 다르고(7.0 azure), 러너 이미지가 갱신되면 바뀐다. 이미지·커널 버전을 작업 로그에 남기면 회귀 원인을 가르기 쉽다.
- **필요한 워크플로 단계 (2회차 `private`에서 그대로 동작한 것).**
  1. `actions/checkout`
  2. `actions/setup-python@v6` 3.12 → `python -m venv ~/.venvs/anf-clone` → `pip install -e ".[dev]"`(backend 작업과 같은 명령, sudo에서도 돈다)
  3. `sudo bash scripts/setup-wsl-dataplane.sh`(6~8 s. 모듈 로드, 이미지, 네트워크, sysctl을 모두 한다)
  4. ns 전파 처리(아래 선택지 중 하나)
  5. `sudo env ANF_TEST_OUT=<폴더> bash scripts/run-dataplane-tests.sh [경로·옵션]`(`ANF_CLONE_VENV`·`ANF_E2E_USER`는 기본값)
  6. `if: always()`: `sudo chmod -R a+rX <폴더>`, 필요하면 `sudo dmesg`와 pytest tmp(`/tmp/pytest-of-root/**/agent.log`) 복사, `actions/upload-artifact`

  - 모듈 설치(`linux-modules-extra`)와 패키지 설치는 이 이미지에서 필요 없다. 이미지가 바뀔 때를 대비해 `apt-get install -y lvm2 thin-provisioning-tools`를 두면 update 포함 약 5 s다.
  - 준비(1~3)는 job 시작부터 테스트 시작까지 28~32 s였다.
  - `timeout-minutes`는 전체 묶음 73분에 여유를 두어야 한다(스파이크는 180).
- **ns 전파 (as-is 실패 8개).**
  - (가) **제품**: `NfsInstances.ensure_shared_ns()`가 자기 바인드 뒤 `mount --make-private ns`를 한 번 하고 `--make-rshared ns`를 한다. `private` job이 정확히 이 상태(바인드 → private → rshared)로 전체 113개를 통과했다. WSL에서는 이미 private이라 결과가 같다 [추론]. shared `/`의 일반 Linux 호스트에서도 마운트가 한 벌이 된다. 바꿀 곳은 storage agent 한 함수다. 이미 shared인 ns 바인드(예: 이전 버전 agent가 만든 것)를 다시 떼어 낼지는 정해야 한다.
  - (나) **워크플로**: CI 단계에서 agent보다 먼저 ns를 private → rshared로 만든다(2회차 `private` job 그대로, 한 줄). 제품 코드는 바뀌지 않지만, CI가 WSL을 흉내 내는 셈이고 다른 Linux 호스트에서는 두 벌 마운트가 그대로 남는다.
  - (다) **시험**: `snap_mounts()`가 대상 경로의 중복을 없앤다(또는 `findmnt`를 보이는 쪽 하나로 좁힌다). 테스트 하나만 바꾸면 되지만 제품의 두 벌 마운트는 남는다. 실패 8개의 단언이 모두 이 함수의 결과를 쓴다.
- **PR마다 전체를 돌릴지 (시간 자료).**
  - 전체 113개는 4,378 s(73분)다. 처리량 데이터 한 파일이 2,141 s(35.7분, 49%)이고, 나머지 12개 파일이 2,227 s(37.1분)다. job 전체는 73.6분이다.
  - 파일별 시간은 위 표에 있다. 긴 것은 처리량 데이터 2,141, 되돌리기 계약 400, 새 볼륨 계약 295, 통합 256, 스냅샷 복구 219, 처리량 계약 190 s다.
  - 선택지 예:
    - (a) PR마다 전체(약 75분).
    - (b) PR마다 처리량 데이터를 뺀 12개 파일(약 37분, 실행기에 경로나 `--deselect=` 인자를 준다)과 main push·야간에 전체.
    - (c) 파일 단위 matrix로 나눠 동시에 돌린다. VM마다 데이터 플레인이 따로이고(2회차의 두 job이 서로 영향 없이 같은 시간에 끝났다), 가장 긴 job은 처리량 데이터 약 36분 + 준비 0.5분이다. 대신 job마다 준비 30 s가 붙고, 실행기 출력과 판정이 job마다 나뉜다.
  - 실행기의 skip 판정(skip = 실패)은 러너에서도 그대로 쓸 수 있다. 두 job 모두 skip 0이었다.
- **산출물.** 실행기 출력은 root 소유라 업로드 전에 읽기 권한을 열어야 한다. 전체 묶음의 압축본은 488~500 KB(원본 5.5 MB, `.jsonl`이 대부분, dmesg 309 KB)이고 업로드에 2 s 걸렸다. 보관 기간은 `retention-days`로 정한다(스파이크는 14).
- **디스크.** 전체 묶음 뒤 `aggr0.img`가 21~22 GB, 디스크 사용이 21 GB 늘었다. 러너 여유(86 GB)에는 문제가 없지만, 한 job에서 전체를 여러 번 돌리면(예: 반복 실행) 쌓인다. 씬 풀은 비어 있으므로(Data 0.00%) 블록이 희소 파일로 돌아가지 않는 것이 원인이다 [추론: discard를 내려보내지 않음].
- **처리량 판정 범위.** 러너는 WSL보다 한도에 0.2~0.7%p 가깝다. 상한 1.01까지의 남은 폭은 중앙값 기준 최소 0.84%p, 창 기준 최소 0.16%p(5 MiB/s 창 1.0084, WSL과 같음)다. 이번 두 job에서는 넘지 않았다. 판정 범위를 바꿀 근거는 이번 관찰에 없다.

## 리더가 사용자에게 물을 것

- ns 전파를 (가) 제품 수정, (나) 워크플로 단계, (다) 시험 수정 중 무엇으로 처리할지. (가)는 storage agent 코드 변경이고, `private` job이 그 상태로 전체를 통과했다.
- PR마다 전체 묶음(약 75분)을 돌릴지, 일부(처리량 데이터를 빼면 약 37분)만 돌리고 main·야간에 전체를 돌릴지, 파일 단위 matrix로 나눌지.
