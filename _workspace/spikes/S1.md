# S1 — 볼륨·스냅샷 저장 방식 비교 (D-11)

| 항목 | 내용 |
| --- | --- |
| 실행일 | 2026-11-07 |
| 실행 | 메인 세션 (`wsl -d Ubuntu -u root -e bash -c ...`). 스크립트와 전체 로그는 세션 scratchpad에 두었고, 판정에 쓴 출력은 아래에 옮겼다 |
| 근거 | [ADR §7.2](../../docs/ADR.md#72-볼륨스냅샷-저장-방식-보류-d-11), R-02, R-03 |
| 전체 판정 | **C(dm-thin 풀 + 볼륨마다 thin LV + ext4) 통과, A 실패, B 조건부.** A는 NFSv3로 읽기 전용 스냅샷이 수정된다. B는 C보다 나은 점이 없고 새 볼륨 복원에 복사가 필요하다. C에는 조건이 셋 있다: export마다 명시적 `fsid`, 스냅샷은 별도 마운트와 export, 언마운트 전에 knfsd 상태 해제 |

## 환경

- 커널 `6.18.54.1-microsoft-standard-WSL2`, Ubuntu 24.04. 이번에 `lvm2`(2.03.16)와 `thin-provisioning-tools`를 설치했다.
- 클라이언트: 이미지 `anf-nfs-client:spike`(`alpine:3.20` + `nfs-utils` + `coreutils`, GNU `dd`), privileged 컨테이너 `s1-c1`, 네트워크 `anf-vnet`(172.30.0.0/24). 서버 주소는 브리지 게이트웨이 `172.30.0.1`이다.
- export 옵션은 `rw,sync,no_subtree_check,no_root_squash`다(ANF 기본 규칙의 `hasRootAccess: true`에 맞춤). 마운트는 `vers=3,nolock`과 `vers=4.1`이다.
- 크기: 볼륨 256 MiB, 초과 쓰기 300 MiB. A는 2 GiB btrfs 하나에 qgroup 256M, B는 256 MiB 루프 파일마다 btrfs, C는 루프 PV 위 씬 풀에 256 MiB thin LV + `mkfs.ext4 -m 0`.
- 같은 시간에 다른 세션이 S2를 같은 WSL에서 돌렸다. 중간부터 S1은 `exportfs -ra`를 쓰지 않고 `exportfs -o`/`-u`로 자기 export만 바꿨다. 그 전 후보 A·C 1차 시험은 `/etc/exports.d/anf-spike-s1.exports`와 `exportfs -ra`를 썼다.

### 판정에 쓴 출력

후보 A, 스냅샷 수정 (5번):

```text
$ btrfs property get …/vol1/.snapshot/snap1 ro
ro=true
client$ echo y >> /mnt/v3/.snapshot/snap1/d/f2; echo rc_append=$?
rc_append=0
$ cat …/vol1/.snapshot/snap1/d/f2      # 서버
x
y
client$ echo z >> /mnt/v4/.snapshot/snap1/d/f2
sh: can't create /mnt/v4/.snapshot/snap1/d/f2: Read-only file system
```

후보 A, inode (6번):

```text
client$ stat -c '%n ino=%i dev=%d' /mnt/v4 /mnt/v4/.snapshot/snap1
/mnt/v4 ino=256 dev=151
/mnt/v4/.snapshot/snap1 ino=256 dev=151
```

후보 C, 스냅샷 (4~6번):

```text
client$ echo y >> /mnt/v3/.snapshot/snap1/d/f2
sh: can't create /mnt/v3/.snapshot/snap1/d/f2: Read-only file system
client$ stat -c '%n ino=%i dev=%d' /mnt/v3 /mnt/v3/.snapshot/snap1
/mnt/v3 ino=2 dev=87
/mnt/v3/.snapshot/snap1 ino=2 dev=88
```

후보 C, 크기 초과 (2번, `dd` 출력 전체와 종료 코드):

```text
client$ dd if=/tmp/src of=/mnt/v4/big bs=1M conv=fsync 2>/tmp/dd.err; echo dd_exit=$?
dd_exit=1
dd: fsync failed for '/mnt/v4/big': No space left on device
```

### 측정 실수와 정정

1차 측정(후보 A·C, 첫 ENOSPC 시험)은 `dd … | tail -2`, `tail -3`으로 출력을 잘랐다. GNU `dd`는 `fsync failed` 줄을 통계 줄보다 먼저 쓸 때가 있어서, 오류 줄이 잘려 "오류 없이 성공"처럼 보였다. 이것을 "버퍼 쓰기에서 ENOSPC가 조용히 사라진다"로 잘못 읽었다. `dd`의 stderr 전체와 종료 코드를 따로 받아 다시 재니, 모든 경우에 클라이언트가 오류(종료 코드 1)를 받았다 (위 2번 행). 이후 검증 스크립트는 명령의 종료 코드와 stderr 전체로 판정한다.

## 추가 관찰

- **knfsd가 파일시스템을 붙잡는다.** 클라이언트 컨테이너를 지우고 export를 내린 뒤에도 `umount`가 `target is busy`였다. NFSv4 상태(open, lease)와 nfsd 파일 캐시가 남아 있기 때문으로 보인다 [추론]. `echo <경로> > /proc/fs/nfsd/unlock_filesystem`을 쓰면 바로 언마운트됐다. 볼륨 삭제와 되돌리기는 이 순서(`exportfs -u` → `unlock_filesystem` → `umount`)가 필요하다.
- **같은 파일시스템 UUID.** thin 스냅샷과 그로 만든 새 볼륨은 ext4 UUID가 원본과 같다. knfsd는 기본적으로 UUID로 export의 fsid를 만들므로, export마다 `fsid=<UUID>`를 명시해야 충돌하지 않는다. 시험에서는 볼륨마다 다른 UUID를 `fsid=`로 줬다.
- **ext4 `lost+found`.** `mkfs.ext4`가 만드는 `lost+found`가 볼륨 루트에 보인다. 시험에서는 만든 직후 `rmdir`했다.
- **마운트 경로 `/<creationToken>`** (§7.4 사전 확인). 실제 경로 `/var/lib/anf-clone/spike-s1/path/vols/s1tok`를 export하고 `/anf-s1tok` 심볼릭 링크를 두면 v3 `mount 172.30.0.1:/anf-s1tok`은 성공하지만 v4.1은 `No such file or directory`다. v4 pseudo-fs가 심볼릭 링크를 따라가지 않기 때문이다 [추론]. `fsid=0` pseudo-root는 같은 시간에 돌던 S2 세션의 v4 경로를 바꿀 수 있어서 시험하지 않았다.
- LVM 명령마다 `File descriptor N (/dev/ptmx) leaked` 경고가 나온다. 동작에는 영향이 없다 (`LVM_SUPPRESS_FD_WARNINGS=1`로 끌 수 있다).

## 설계에 주는 영향

- **D-11은 C를 추천한다.** 근거: (1) 스냅샷 불변성이 프로토콜과 관계없이 지켜진다 (A는 FR-05 수락 기준 "스냅샷 안의 파일은 바꿀 수 없다"를 v3에서 어긴다). (2) 클라이언트 `df`가 볼륨 크기를 보여 준다. (3) 스냅샷이 다른 장치로 보여 R-02가 없다. (4) 새 볼륨 복원이 즉시다 (FR-07, FR-18). (5) 볼륨마다 블록 장치가 있어 S2 T2와 볼륨별 블록 I/O 메트릭에 쓸 수 있다.
- **C의 조건.**
  - export마다 `fsid=<볼륨 UUID>`를 명시한다.
  - 스냅샷은 thin 스냅샷 LV를 `.snapshot/<이름>`에 `ro,noload`로 마운트하고 자기 `fsid`로 `ro` export한다. 부모 export에는 `crossmnt`를 붙인다 (FR-05 설계에서 확정).
  - 볼륨 삭제·되돌리기 전에 `exportfs -u` → `unlock_filesystem` → `umount` 순서를 지킨다.
  - ext4는 `nodelalloc`으로 마운트하는 것을 기본 후보로 둔다. 둘 다 클라이언트가 오류를 받지만, `nodelalloc`일 때만 오류 뒤 남은 데이터가 원본의 prefix였다. ONTAP과의 차이와 함께 볼륨 설계에서 정한다.
- **ANF와의 차이 (개념 문서 후보).**
  - 클론의 스냅샷 공간은 씬 풀에서 나가고 볼륨 `df`에 잡히지 않는다. ANF는 스냅샷이 볼륨 할당량에 포함된다 (볼륨 브리프). FR-05 설계에서 다룬다.
  - 클론은 볼륨 크기(`usageThreshold`)를 블록 장치 크기로 강제한다. ANF 스펙은 `usageThreshold`를 "soft quota"라고 쓰지만 Learn 문서는 볼륨 용량 제한이라고 쓴다 (볼륨 브리프의 출처 충돌).
  - ext4 오버헤드 때문에 256 MiB 볼륨의 `df` 크기는 224 MiB다. 데모 크기(ANF 최소 50 GiB)에서는 비율이 작다.
- **되돌리기(R-03).** C의 merge는 마운트가 열려 있으면 미뤄진다. FR-06 설계에서 언마운트 절차와 클라이언트 영향(같은 `fsid`면 핸들이 유지되는지)을 다시 잰다.
- **ext4 대신 XFS**는 시험하지 않았다. 필요하면 볼륨 설계에서 비교한다.

## 정리

시험마다 자기 자원만 지웠다: 컨테이너 `s1-c1`, S1이 만든 export(`exportfs -u`), 마운트, VG `anfs1`·`anfs1e`·`anfs1f`, 루프 장치(`losetup -d <장치>`), `/var/lib/anf-clone/spike-s1`. 남긴 것: 패키지 `lvm2`·`thin-provisioning-tools`, 이미지 `anf-nfs-client:spike`, Docker 네트워크 `anf-vnet`. S2 세션의 자원(VG `anfs2`, `/var/lib/anf-clone/spike-s2`, 네트워크 `s2-net`)은 건드리지 않았다.
