## R: 클라이언트가 마운트를 유지한 채 되돌리기

시나리오 (`run.sh <방식> <버전>`): 클라이언트가 `A=a1, B=b1, C=c1, d/E=e1`을 쓴다 → 스냅샷 S1 → `B=b2`(같은 inode에 덮어쓰기), `C` 삭제, `D=d1`과 `n/F=f1` 생성 → 스냅샷 S2(더 새 스냅샷) → 클라이언트가 `B`를 읽어 캐시에 올린다. 되돌리기 전에 클라이언트 안에서 띄워 두는 것: `cat /m/A`를 0.2 s마다 하는 탐침, `B`(두 개)와 `D`의 열린 fd, cwd가 `/m/d`인 셸, cwd가 `/m/n`인 셸.

되돌리기 (모든 방식 공통 LVM 절차): 창 열기(방식별) → S2·S1·볼륨 `umount`(재시도) → S2 `lvremove`(더 새 스냅샷 삭제) → `lvconvert --merge S1` → S1을 되돌린 볼륨에서 다시 `lvcreate -s -kn -p r` → 볼륨 마운트 → `.snapshot/S1` 만들기(`chattr -i`/`+i`)·S1 마운트 → export 파일(볼륨 + S1) → 창 닫기(방식별).

| 방식 | 창 열기 | 창 닫기 |
| --- | --- | --- |
| `export` | export 파일을 비우고 `exportfs -ra` → 인스턴스 안 `unlock_filesystem`(S2, S1, 볼륨) | 파일 다시 쓰기 + `exportfs -ra` |
| `block` | 인스턴스 netns에서 `iptables -I INPUT -i eth0 -j DROP`(호스트에서 `nsenter -t <pid> -n`) → 인스턴스 안 `exportfs -f`(커널 export 캐시 비우기) → `unlock_filesystem`(S2, S1, 볼륨) | 파일 다시 쓰기 + `exportfs -ra` → DROP 규칙 삭제 |
| `stop` | `docker stop -t 30`(진입점이 잠금 해제·`rpc.nfsd 0`) | 파일 쓰기 → `docker start` → 준비 표시 대기 |

- 서버 쪽은 모든 방식에서 같았다: `B=b1`, `C=c1`, `D` 없음, `B`의 inode 번호 13 그대로, `.snapshot`은 되돌린 내용 그대로 빈 디렉터리(+i 유지). S1이 `.snapshot/S1`을 만들기 전에 찍혔기 때문이다.
- **파일 핸들이 유지되는 이유** [추론]: NFS 파일 핸들은 export의 `fsid`(볼륨 UUID, 그대로) + inode 번호 + inode 세대(generation)다. merge 뒤의 파일시스템은 스냅샷 시점의 inode 표 그대로라서, 그때 있던 파일은 같은 핸들로 찾아진다. 스냅샷 뒤에 만든 파일의 inode는 되돌린 파일시스템에 없거나 세대가 달라 `ESTALE`이다. WAFL의 SnapRestore가 inode 표를 스냅샷 것으로 바꾸는 것과 같은 모양이다 (브리프 문서 7).
- **export 방식의 `Permission denied`**: export 줄이 없는 동안 mountd가 그 `fsid`를 거절해 v3 요청이 `NFS3ERR_ACCES`로 돌아간 것으로 본다 [추론]. v4.1은 같은 창에서 실패가 없었다. `A`를 위임(delegation)으로 캐시해 서버에 묻지 않았을 수 있다 [추론]. B2에서 v4.1 클라이언트가 위임을 갖고 있음을 확인했다.
- **stop v4.1의 옛 내용**: 재시작한 knfsd의 유예 기간에 클라이언트가 열린 파일과 읽기 위임을 되찾았다(reclaim). 핸들이 유효하니 서버는 되찾기를 받아 주고, 클라이언트는 위임을 믿고 캐시(b2)를 계속 쓴다. 새 `cat`(OPEN)도 위임 아래에서는 캐시를 쓴다 [추론]. 위임이 있다는 것은 B2에서 확인했다. 65 s 뒤에도 b2였으므로 오래 간다. 그래서 인스턴스 재시작은 데이터를 틀리게 보여 주는 방식이다.
- **block v4.1의 T+1 s 옛 내용**: 위임은 `unlock_filesystem`이 서버에서 회수(revoke)했지만, 클라이언트는 다음 SEQUENCE 응답의 상태 플래그로 늦게 알아챈다 [추론]. 그사이 열린 fd 읽기가 캐시를 썼다. 새 `cat`은 T+1 s에 이미 b1이었고, fd도 T+65 s에는 b1이었다. 걸린 시간은 B2에서 쟀다(16~32 s).

## B2: block 방식의 위임과 열린 fd

`run2.sh <버전>`: 클라이언트가 `B=b1` → S1 → `B=b2`를 쓰고 읽은 뒤, `B`의 fd 7개를 열어 두고 block 방식으로 S1에 되돌린다. fd를 되돌리기 뒤 1·2·4·8·16·32·64 s에 하나씩 읽는다(모두 클라이언트의 같은 페이지 캐시를 쓴다). 인스턴스 안 `/proc/fs/nfsd/clients/*/states`로 서버의 NFSv4 상태를 본다.

- 되돌리기 시간은 1.58 s(v4.1), 4.93 s(v3), 2.95 s(v4.1, 위임 끔). v3의 4.93 s는 R의 2.42 s보다 길다. 원인은 따로 보지 않았다(umount 재시도 추정) [추론].
- **원인.** knfsd는 기본으로 NFSv4 위임을 준다. 위임을 가진 클라이언트는 서버에 묻지 않고 캐시를 믿는다. `unlock_filesystem`은 위임을 서버에서 회수(revoke)할 뿐 클라이언트에 알리지(recall) 않으므로, 클라이언트는 다음 lease 갱신 즈음(lease 30 s)에 회수를 알아채고 캐시를 버린다 [추론: 16~32 s 사이에 바뀌었다]. stop 방식에서는 재시작한 서버가 위임 되찾기를 받아 줘서 캐시가 계속 옳다고 믿는다(R의 65 s 뒤 b2).
- **위임을 끄면 v4.1도 v3처럼 바로 맞는다.** knfsd에는 인스턴스(netns)별 위임 설정이 없다. `/proc/fs/nfsd`에도, debugfs `nfsd/`(`disable-splice-read`, `io_cache_read`, `io_cache_write`)에도, 모듈 인자에도 없다. 그래서 전역 `fs.leases-enable`을 0으로 시험했다: knfsd 위임은 VFS lease 위에서 돌아서 lease를 끄면 위임도 나가지 않는다. 이 값은 WSL VM 커널 전체(모든 배포판)의 파일 lease를 끈다. 시험 뒤 1로 되돌렸다.
- **ONTAP 기본값은 위임 꺼짐이다.** NFS 서비스 POST의 기본값이 `protocol.v41_features.read_delegation_enabled` false, `write_delegation_enabled` false다 (`_workspace/snapshot/sources/ontap/nfs_service.py.txt` 519~523행). ANF가 위임을 켜는지는 [미확인].

## 설계에 주는 영향

- **창 방식은 block이다.** 인스턴스는 그대로 두고, 인스턴스 netns 입력 DROP → `exportfs -f` → `unlock_filesystem`(볼륨, 스냅샷마다) → umount → LVM → mount → export 파일 + `exportfs -ra` → DROP 해제. 클라이언트는 hard 마운트의 재전송으로 2~5 s 멈췄다가 이어 간다(오류 0). export 방식은 v3에 `Permission denied`를 주고, stop 방식은 v4.1에 23 s 멈춤과 틀린 캐시를 준다.
- **LVM은 merge + 고른 스냅샷 다시 만들기다.** (구현 중 뒤집혔다: 아래 "스파이크 뒤 발견".) 모두 언마운트한 뒤의 `lvconvert --merge`는 즉시(0.4~0.6 s)이고, 볼륨 LV의 이름·태그가 그대로라 agent의 볼륨 식별(LVM 태그)이 바뀌지 않는다. merge가 고른 스냅샷 LV를 소비하므로, 되돌린 볼륨에서 같은 태그(uuid, 이름, 만든 시각)로 다시 만든다. ANF처럼 고른 스냅샷이 남는다(브리프 녹화 4). 교체 방식(L2)은 `lvrename` 두 번이 3 s이고 태그를 옮겨야 한다. **merge 전에 반드시 모두 언마운트한다.** 열린 채 merge하면 "다음 활성화"로 미뤄지고, 그 사이 WSL 재시작의 `vgchange -ay`가 merge를 끝내 버린다(L1a).
- **merge와 다시 만들기 사이에 멈추면 고른 스냅샷의 태그가 사라진다.** 다시 만들 정보(uuid, 이름, 시각)를 merge 전에 볼륨 LV 태그에 적어 두어야 재시도가 이어서 끝낼 수 있다 [추론, 시험 안 함].
- **더 새 스냅샷은 dm-thin 장치 id로 고를 수 있다.** id는 남은 것 중 최댓값 + 1이라 남은 스냅샷의 id 순서가 만든 순서다(L3). `anf_snap_time`은 초 단위라 같은 초에 만든 스냅샷을 가르지 못한다.
- **`.snapshot`은 되돌린 내용 그대로다.** 고른 스냅샷을 찍던 때의 `.snapshot` 디렉터리(+i, 그때 있던 스냅샷 이름의 빈 마운트 지점)가 돌아온다. agent가 남은 스냅샷에 맞춰 마운트 지점을 만들고, 없는 스냅샷의 빈 디렉터리를 지워야 한다.
- **클라이언트에서 보이는 것 (FR-06 수락 기준의 "기록").** 다시 마운트할 필요가 없다. 스냅샷에 있던 파일·디렉터리는 열린 fd와 cwd까지 그대로 이어지고 스냅샷 시점 내용을 읽는다. 스냅샷 뒤에 만든 파일·디렉터리를 잡고 있던 fd·cwd는 `Stale file handle`이고, 경로로 찾으면 `No such file or directory`다. NFSv4.1은 위임이 켜져 있으면 열린 fd가 최대 약 30 s 동안 되돌리기 전 캐시를 읽는다.
- **(설계에서 정할 것) NFSv4 위임.** 위임을 끄면(ONTAP 기본값) v4.1도 바로 맞는다. 대신 knfsd에 인스턴스별 설정이 없어 WSL 커널 전역 `fs.leases-enable = 0`이 필요하다.

## 스파이크 뒤 발견 (되돌리기 구현 중, 2026-11-08)

- **merge 방식은 두 번째 되돌리기를 못 한다.** 통합 테스트에서 s1·s2·s3를 만들고 s2로 되돌린 뒤 s1로 다시 되돌리자 `lvconvert --merge anf/snap_<s1>`이 `anf/snap_<s1> is not a mergeable logical volume`(rc 5)였다. L3에서 본 대로 merge 뒤 남은 스냅샷은 `origin` 표시를 잃고, LVM은 원본이 지금 볼륨인 thin 스냅샷만 merge한다. 그래서 첫 되돌리기 전부터 있던 스냅샷으로는 다시 되돌릴 수 없다. 위 "LVM은 merge + 고른 스냅샷 다시 만들기다"는 이 발견으로 뒤집혔다.
- **구현은 L2의 교체 방식이다.** 쓰기 가능 스냅샷(`lvcreate -s -kn -p rw`)은 원본 관계와 상관없이 어느 thin 스냅샷에서나 만들 수 있다. L2의 비용은 이렇게 덜었다: 새 LV에 볼륨 태그를 만들 때 붙이고, 옛 LV를 지운 뒤 `lvrename`은 한 번만 하며, 둘 다 차단을 푼 뒤에 한다. 창 안에는 언마운트·마운트·export만 남는다. 볼륨 export의 `fsid`는 볼륨 UUID로 고정이고 새 LV의 ext4는 고른 스냅샷의 inode 표 그대로라서, R의 핸들 결과(스냅샷에 있던 것은 이어지고 뒤에 만든 것만 ESTALE)는 같은 이유로 성립한다. 통합 테스트 `test_restore_reverts_under_a_mounted_client[nfs3/nfs4.1]`이 hard 마운트 클라이언트로 두 번째 되돌리기까지 다시 마운트 없이 통과했다. 설계 기록: `_workspace/snapshot-revert/02_main_design.md` §9-1.
