# S4 — 볼륨 인스턴스 구조에서 `.snapshot` 노출 (FR-05, FR-06·FR-07 참고)

| 항목 | 내용 |
| --- | --- |
| 실행일 | 2026-11-08 |
| 실행 | 메인 세션 (`wsl -d Ubuntu -u root -e bash <스크립트>`). 스크립트는 세션 scratchpad `s4/`(`lib.sh`, `e1.sh`~`e5.sh`, `g1.sh`~`g3.sh`, `f1.sh`)에 두었고, 판정에 쓴 출력은 아래에 옮겼다 |
| 왜 | S1은 호스트 knfsd에서 `.snapshot`을 시험했다. D-12로 export가 볼륨 인스턴스(컨테이너 netns의 knfsd) 안으로 옮겨졌고, 볼륨 구현 중 "v3 클라이언트가 볼륨 안의 하위 마운트로 넘어가면 Stale file handle"이 관찰됐다 (`_workspace/volume/02_main_design.md` "S2 미확인 해결" 2) |
| 전체 판정 | **조건부 통과.** 스냅샷을 인스턴스 안에서 **자기 `fsid`로 따로 export**하면 v3·v4.1 모두 `.snapshot/<이름>/`이 읽기 전용으로 읽힌다. 조건 셋: (1) 스냅샷마다 export 줄, (2) `.snapshot` 디렉터리에 `chattr +i`, (3) 인스턴스가 재시작해도 스냅샷 export가 남도록 export 표를 파일로 둔다. **볼륨 기능의 결함 하나를 찾았다**: NFSv4.1 클라이언트 기록이 남은 인스턴스는 재시작하지 못한다 (G1~G3) |

## 환경

- 커널 `6.18.54.1-microsoft-standard-WSL2`. 볼륨 코드 `8a4002d`의 이미지 `anf-nfs-server`(진입점 그대로), 클라이언트 이미지 `anf-nfs-client`.
- 스파이크 전용 자원: VG `anfs4`(8 GiB 희소 파일), 루트 `/var/lib/anf-clone/spike-s4`(`ns`를 rshared로 바인드), 볼륨 두 개(1 GiB thin LV + ext4 `nodelalloc`, `mkfs -U <uuid>`): `s4v3`(NFSv3, IP .250), `s4v4`(NFSv4.1, IP .251). 인스턴스 `s4-nfs-*`는 agent의 `docker run` 인자와 같다. 클라이언트 `s4-c1`~`s4-c3`(privileged, `anf-vnet`).
- 스냅샷: `lvcreate -s -kn -p r -n snapN_<tok> anfs4/vol_<tok>`(읽기 전용, activation skip 끔) → `ns/<tok>/.snapshot/snapN`에 `mount -t ext4 -o ro,noload`.
- **주의 (환경).** WSL 배포판은 wsl.exe 세션이 없으면 잠시 뒤 종료된다. 첫 시험에서 컨테이너·마운트가 사라졌다(커널 VM은 남아 루프 장치와 LV는 그대로였다). 이후 `wsl -d Ubuntu -u root -e sleep 86400`을 백그라운드로 띄워 두고 시험했다.

### G: NFSv4.1 인스턴스 재시작 결함 (볼륨 기능, FR-04)

- **증상 (E5).** NFSv4.1 클라이언트가 마운트를 유지한 채 인스턴스를 `docker stop`·`docker start`하면, 진입점이 "NFSv4 client tracking did not start"를 5번 찍고 끝난다(exit 1). 그 볼륨은 서비스되지 않는다.
- **원인.** 인스턴스의 nfsdcld DB(`/var/lib/nfs/nfsdcld/main.sqlite`)에 이전 부팅의 클라이언트 2개가 남아 있었다(`rec-0000000000000002` 2행, `grace` = `3|2`). 커널은 이 클라이언트들이 상태를 되찾도록 **정상적인 유예 기간**을 돈다(dmesg "starting 90-second grace period"). 진입점은 `v4_end_grace`가 `N`이면 모두 "추적 실패"로 보고 1초 뒤 knfsd를 다시 띄우므로, 클라이언트가 되찾을 틈이 없다. 볼륨 검증 AC-12(c)는 클라이언트가 마운트를 풀고 끝난 뒤(`one_shot`) 재시작해서 이 경우를 만나지 않았다.
- **현실 시나리오.** WSL 재시작(노트북 재부팅, `wsl --shutdown`)에서 클라이언트는 깔끔히 언마운트하지 못한다. 그러면 기록이 남고, 다음 agent 시작의 복구에서 그 NFSv4.1 볼륨이 살아나지 않는다 [추론, G3이 같은 조건을 만든다].
- **시제품 진입점** (scratchpad `s4/img/`, 이미지 `anf-nfs-server:s4test`, 이미지에 `sqlite` 추가). `rpc.nfsd` 뒤 `v4_end_grace`가 `N`일 때 nfsdcld DB의 `grace.recovery` 시대(epoch) 기록 표에 행이 있으면 정상 유예 기간으로 보고 `Y`가 될 때까지 기다린다. 행이 없을 때만 지금처럼 knfsd를 다시 띄운다.

## 설계에 주는 영향

- **스냅샷마다 export 줄이 필요하다.** `fsid`는 스냅샷 UUID. 볼륨 export의 `crossmnt`는 그대로 둔다(클라이언트가 하위 마운트로 넘어가는 데 쓴다).
- **export 표는 파일로 둔다 (권장).** agent가 LVM 태그(볼륨 + 스냅샷)에서 표를 다시 만들어 쓰고 `exportfs -ra`. 진입점은 시작 때 파일을 읽는다. 그러면 인스턴스가 어떤 이유로 재시작해도 스냅샷 export가 처음부터 있다. 대안: 스냅샷마다 `docker exec exportfs -o`, 인스턴스 시작 뒤 agent가 다시 export (재시작 직후 짧은 틈에 ELOOP/ESTALE).
- **`.snapshot`은 `chattr +i`로 보호한다.** agent만 `-i`/`+i`로 마운트 지점을 바꾼다.
- **삭제 순서**: export 줄 제거(`exportfs -ra`) → 인스턴스 안 `unlock_filesystem` → `umount` 재시도 → 마운트 지점 제거 → `lvremove`.
- **복구 순서**: aggregate → `ns` 공유 → 볼륨 마운트 → 스냅샷 마운트 → export 표 쓰기 → 인스턴스 시작.
- **G 결함은 볼륨 코드(진입점, 준비 대기 시간)를 고쳐야 한다.** 스냅샷 복구와 FR-06(되돌리기 때 인스턴스 재시작 가능성)이 이 경로를 쓴다.
- **ANF와의 차이 (개념 문서 후보).**
  - NFSv4.1에서도 `.snapshot`이 목록에 보인다. ANF는 v4.1 목록에서 숨기고 이름으로만 들어가게 한다 (`_workspace/snapshot/01_researcher_brief.md`).
  - `.snapshot`은 볼륨 루트에만 있다. ONTAP은 모든 디렉터리에서 접근된다.
  - 스냅샷 안에 `.snapshot`이 빈 디렉터리로 보이고, 그 안에 그때 있던 스냅샷 이름의 빈 디렉터리가 보인다.
  - 스냅샷 공간은 씬 풀에서 나가고 볼륨 할당량에 들어가지 않는다 (S1 #7). ANF는 할당량에 넣는다.

## 정리

컨테이너 `s4-*`, 마운트, VG `anfs4`, 루프 장치, `/var/lib/anf-clone/spike-s4`, 이미지 `anf-nfs-server:s4test`, `/tmp/s4cld`를 지웠다. 이미지 `anf-nfs-server`·`anf-nfs-client`, 네트워크 `anf-vnet`은 그대로다. VG `anf`는 이번에 만들지 않았다.
