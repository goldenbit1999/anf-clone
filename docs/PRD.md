## 1. 배경

Azure NetApp Files(ANF)는 Azure가 직접 판매하고 지원하는 완전 관리형 NAS 서비스다. 볼륨은 Azure 데이터센터 안에 있는, ONTAP으로 동작하는 베어메탈 장비에서 제공된다 [S1].

이 프로젝트는 NetApp의 "Entry Level Software Engineer - ANF" 지원용 포트폴리오다.
- 이 직무는 ANF **데이터 플레인**을 맡는다.
- 공고는 Python 테스트 자동화, REST API, Kubernetes, 컨테이너, CI/CD, 관측성을 강조한다.
- 결과물은 NetApp 사람에게만 보여 준다. 제품으로 만들 계획은 없다.

## 2. 해결할 문제

면접관은 ONTAP을 깊이 아는 엔지니어다. 이들에게 두 가지를 보여 줘야 한다.

1. **개념 이해.** 작성자가 ANF와 ONTAP의 데이터 플레인 개념을 이해한다. 동작만이 아니라 그렇게 동작하는 이유와 한계까지 설명할 수 있다.
2. **엔지니어링 역량.** 공고가 요구하는 일을 실제로 해낼 수 있다. REST API, 비동기 제어, 테스트 자동화, CI, 관측성, 컨테이너가 여기에 해당한다.

상태 값만 바꾸는 모의 구현으로는 1번을 증명할 수 없다. 그래서 이 클론은 **실제 데이터에 효과를 내야 한다.**

## 3. 목표와 비목표

### 목표

| ID | 목표 |
| --- | --- |
| G1 | 핵심 데이터 플레인 기능 몇 개를 실제로 동작하게 만든다. 클라이언트가 마운트하는 NFS 볼륨, 데이터에 효과가 있는 스냅샷, 측정할 수 있는 처리량 제한이 여기에 해당한다. |
| G2 | 각 기능을 실제 ANF·ONTAP과 대조해 설명할 수 있게 한다. 클론이 실제와 다른 지점(예: dm-thin 스냅샷과 WAFL 스냅샷의 차이)도 설명한다. |
| G3 | ARM 스타일의 비동기 컨트롤 플레인을 제공한다. 비동기 작업은 완료를 기다리지 않고 응답하고, 클라이언트가 추적 URL을 폴링해 완료를 확인한다. 응답 형식은 작업별 ANF REST 계약을 따른다 (FR-01). |
| G4 | 공고가 요구하는 기술을 결과물에서 직접 보여 준다. pytest 통합 테스트, GitHub Actions CI, 메트릭, 컨테이너가 해당하고, 최소한의 CSI 드라이버는 선택이다. |
| G5 | 기능마다 개념 문서를 남겨, Claude가 쓴 코드를 작성자가 면접에서 설명할 수 있게 한다. |

### 비목표

- ANF 전체 기능을 만드는 것. 넓이보다 깊이를 택한다.
- ANF 포털을 재현하는 것. 대시보드는 최소 범위로 만들고 Microsoft 로고와 자산은 쓰지 않는다.
- 운영 환경 수준의 가용성, 확장성, 멀티테넌트 격리.
- SMB와 이중 프로토콜. 이번 범위에서는 빼고 나중 후보로 둔다.
- 구독, 리소스 그룹, VNet, 위임 서브넷, RBAC의 실제 구현. 경로와 속성에는 나타나지만, 기능이 필요로 할 때만 동작을 넣는다.
- 실제 Azure와의 연동과 과금.

| 자동화 클라이언트 | curl, 스크립트, pytest, (선택) CSI 드라이버가 API를 호출한다 | 실제 ANF와 같은 모양의 안정적인 REST 계약 |

## 5. 대표 시나리오 (데모 대본)

요청은 ARM 스타일 API나 대시보드로 보내고, 효과는 NFS 클라이언트 컨테이너에서 확인한다.

1. NetApp 계정, 용량 풀(서비스 수준 포함), 볼륨을 차례로 만든다. 요청마다 즉시 응답이 오고, `provisioningState`가 `Succeeded`가 될 때까지 폴링한다.
2. 클라이언트 컨테이너가 볼륨의 마운트 대상 IP와 경로로 마운트하고 파일을 쓴다. NFSv3와 NFSv4.1을 각각 시험한다.
3. 스냅샷을 만든 뒤 파일을 지운다. 클라이언트에서 `.snapshot/<스냅샷 이름>/`을 열어 지운 파일을 읽는다.
4. 볼륨을 그 스냅샷으로 되돌린다(revert). 지운 파일이 다시 보인다.
5. 스냅샷으로 새 볼륨을 만들고 다른 클라이언트 컨테이너에서 마운트한다. 새 볼륨에 써도 원본은 바뀌지 않는다.
6. 처리량 제한을 걸고 클라이언트에서 쓰기 처리량을 잰다. 제한을 바꾸면 잰 값도 따라 바뀐다.
7. 대시보드에서 리소스 목록, 프로비저닝 상태, 처리량과 사용량 메트릭을 본다.

## 6. 기능 요구사항

### 공통 규칙

- **수락 기준은 클라이언트에서 관찰할 수 있는 효과로 쓴다.** 데이터 효과가 없는 기능(예: 계정)은 API 계약과 상태 전이로 판정한다.
- **ARM 경로, 속성 이름, 응답 코드는 실제 ANF REST API를 따른다.** 기준 api-version은 `2026-08-01`(최신 stable)이다 (`_workspace/netapp-account/01_researcher_brief.md`). 실제와 다르게 만든 부분은 개념 문서에 이유와 함께 적는다.
- **아래 수락 기준은 출발점이다.** 세부 계약과 검증 기준은 기능마다 설계 단계(`_workspace/{feature}/02_main_design.md`)에서 확정한다.

### 6.1 1단계: 코어

| ID | 기능 | 요구사항 | 수락 기준 (출발점) |
| --- | --- | --- | --- |
| FR-01 | 비동기 작업 (LRO) | 변경 요청은 해당 ANF 작업의 REST 계약을 따른다. 비동기 작업은 초기 응답에 정의된 추적 헤더(`Azure-AsyncOperation` 또는 `Location`)를 제공하고, 클라이언트는 그 URL을 폴링해 완료 또는 실패를 확인한다 [S2]. 본문이 있는 리소스 응답에는 작업 계약에 따라 `provisioningState`를 제공한다. 동기 완료 응답(예: tags만 바꾼 계정 PATCH의 `200`)과 본문 없는 응답(예: 없는 리소스 DELETE의 `204`)은 작업별 계약을 따른다. POST 액션의 비동기 여부도 개별 계약에 명시한다. 작업별 응답 표는 [ADR §6.1](ADR.md#61-api-계약-원칙)을 출발점으로 기능 설계에서 확정한다. | 비동기 작업의 응답이 작업 완료 전에 온다. 추적 URL을 폴링하면 종결 상태(`Succeeded`, `Failed`, `Canceled`)에 도달한다 [S2]. 실패하면 리소스가 `Failed`가 되고 오류 코드와 메시지를 보여 준다. 동기 `200`, 본문 없는 `204`, 비동기 `202`를 공통 규칙이 잘못 거절하지 않는다. 폴링 간격(`Retry-After`)과 제한 시간, 실패 시나리오는 계정 설계에서 정한다. |
| FR-02 | NetApp 계정 | 생성, 조회, 목록, 수정(PATCH), 삭제 | 상태 전이가 FR-01을 따른다. 자식 용량 풀이 남아 있으면 삭제가 409로 거절되고 풀은 그대로 남는다. 이 409 기준의 실환경 검증은 용량 풀 사이클에서 한다. 검사 로직은 계정 사이클에서 구현하고 계약 테스트로 확인한다 (`_workspace/netapp-account/02_main_design.md` 결정 8). |
| FR-03 | 용량 풀 | 크기, 서비스 수준, QoS 유형(Auto 또는 Manual)을 가진다. | 볼륨 할당량의 합이 풀 크기를 넘게 되는 볼륨 생성은 거절된다. 볼륨이 남은 풀의 삭제는 거절된다. 볼륨이 필요한 이 기준들과 풀 축소 하한의 실환경 검증은 볼륨 사이클에서 한다. 풀 쪽 검사는 풀 사이클에서 구현하고 계약 테스트로 확인한다 (`_workspace/capacity-pool/02_main_design.md` 결정 3, §8). |
| FR-04 | 볼륨 (NFS) | `creationToken`(export 경로), `usageThreshold`(할당량), `protocolTypes`(NFSv3 또는 NFSv4.1), `mountTargets`(마운트 IP)를 가진다. 실제 NFS export를 만든다. | 클라이언트 컨테이너가 `<마운트 IP>:/<creationToken>`을 지정한 NFS 버전으로 마운트하고 읽고 쓸 수 있다. 할당량을 넘는 쓰기는 실패한다. 볼륨을 지우면 더 이상 마운트되지 않는다. |
| FR-05 | 스냅샷 | 생성, 조회, 목록, 삭제. NFS 클라이언트에 `.snapshot` 디렉터리를 보여 준다. | 스냅샷을 만든 뒤 지운 파일을 `.snapshot/<이름>/`에서 읽을 수 있다. 스냅샷 안의 파일은 바꿀 수 없다. |
| FR-06 | 스냅샷으로 되돌리기 | 볼륨을 스냅샷 시점의 상태로 되돌린다. | 되돌린 뒤 볼륨 내용이 스냅샷 시점과 같다. 되돌리기 전에 마운트한 클라이언트가 어떻게 보이는지(다시 마운트가 필요한지)를 기록한다. |
| FR-07 | 스냅샷에서 새 볼륨으로 복원 | 스냅샷을 원본으로 새 볼륨을 만든다. | 새 볼륨이 스냅샷 시점의 내용을 갖는다. 새 볼륨에 써도 원본 볼륨과 스냅샷은 바뀌지 않는다. |
| FR-08 | 처리량 제한 | Auto QoS(서비스 수준 × 할당량) 또는 Manual QoS(볼륨별로 지정한 MiB/s)로 제한한다. | 클라이언트에서 잰 처리량이 제한 이하다(허용 오차는 설계 단계에서 정한다). 제한을 바꾸면 잰 값도 바뀐다. 제한이 없는 볼륨과의 차이가 측정으로 드러난다. |
| FR-09 | 대시보드 (리소스) | 계정, 풀, 볼륨, 스냅샷을 계층으로 보여 주고 `provisioningState`를 표시한다. | 생성 중인 리소스가 완료 상태로 바뀌는 과정이 새로 고침 없이 보인다. |

### 6.2 2단계: 공고가 요구하는 기술

| ID | 기능 | 요구사항 | 수락 기준 (출발점) |
| --- | --- | --- | --- |
| FR-10 | 테스트 자동화 | pytest로 단위, API 계약, 통합, E2E 테스트를 만든다. | 실제 커널 위에서 마운트, 스냅샷, 처리량 효과를 확인하는 테스트가 있고 통과한다. |
| FR-11 | CI | GitHub Actions | 푸시와 PR마다 단위·계약 테스트, 프론트엔드 빌드와 타입 검사가 돈다. 실제 커널을 쓰는 통합 테스트는 GitHub 러너에서 가능한지 확인한 뒤 넣는다 ([ADR 스파이크 S3](ADR.md#10-위험과-스파이크)). |
| FR-12 | 메트릭 | 볼륨 사용량, 처리량, 가능하면 IOPS를 수집한다. API 요청과 비동기 작업의 지표도 수집한다. | Prometheus에서 조회할 수 있다. 대시보드가 차트로 보여 준다. 클라이언트에서 부하를 걸면 그래프에 나타난다. |
| FR-13 | 컨테이너 | 구성요소를 컨테이너로 묶고 docker compose로 띄운다. | 문서에 적힌 명령 하나로 전체를 띄울 수 있다. |
| FR-14 | (선택) CSI 드라이버 | PVC 요청으로 볼륨을 프로비저닝하는 최소한의 CSI 드라이버. NetApp Trident가 Kubernetes를 ANF에 연결하는 방식과 같은 자리에 놓인다. | PVC가 `Bound`가 되고 파드가 그 볼륨을 마운트해 쓸 수 있다. |

### 6.3 3단계: 데이터 플레인 확장

| ID | 기능 | 수락 기준 (출발점) |
| --- | --- | --- |
| FR-15 | export policy | IP가 다른 클라이언트 컨테이너 두 개로 시험한다. 허용된 클라이언트만 마운트되고, 읽기 전용 규칙이면 쓰기가 실패하며, root 접근 규칙이 지켜진다. |
| FR-16 | 볼륨 크기 변경 | 할당량을 늘리면 이전 한도를 넘는 쓰기가 성공하고, 클라이언트가 보는 크기도 바뀐다. |
| FR-17 | 스냅샷 정책 | 일정에 따라 스냅샷이 자동으로 만들어지고, 보존 개수를 넘는 스냅샷은 지워진다. |
| FR-18 | 클론 | 기존 볼륨이나 스냅샷으로 쓰기 가능한 사본 볼륨을 즉시 만들고, 원본과 독립적으로 쓸 수 있다. |

## 7. 비기능 요구사항 (제품 수준)

기술 세부는 [ADR §3](ADR.md#3-아키텍처-요구사항)에 있다.

| ID | 요구사항 |
| --- | --- |
| NFR-01 실제성 | 모의 구현이나 상태만 바꾸는 시뮬레이션은 완료로 치지 않는다. |
| NFR-02 API 충실도 | ARM 경로, 속성, 응답 코드는 실제 ANF를 따른다. 다르게 만든 곳은 이유와 함께 문서로 남긴다. |
| NFR-03 재현성 | 깨끗한 저장소에서 문서대로 따라 하면 WSL2 Ubuntu 24.04와 Docker로 전체를 띄울 수 있다. |
| NFR-04 설명 가능성 | 기능마다 개념 문서를 쓴다. 본문은 한국어, 면접 Q&A는 영어다. |
| NFR-05 테스트 우선 | 구현은 테스트를 먼저 쓴다. TDD 훅(`.claude/hooks/tdd_guard.py`)은 짝 테스트가 지금 내용 그대로 수집·실행된 근거(RED 또는 GREEN)가 있을 때만 구현 파일 수정을 허용하고, GREEN으로 확인되기 전에는 종료를 막는다. 테스트가 올바른 동작을 검사하는지와 새 동작이 RED에서 시작했는지는 훅이 보장하지 않으므로 리뷰와 기능 사이클의 절차로 지킨다. 보장 범위는 `CLAUDE.md`의 TDD hook 절에 있다. |
| NFR-06 자원 제약 | 데모 전체가 WSL 메모리(약 7GB) 안에서 돈다. |
| NFR-07 로컬 전용 | 서비스는 로컬에서만 접근할 수 있게 띄운다. |
| NFR-08 추적성 | API 요청부터 데이터 플레인 작업까지 같은 상관 ID로 추적할 수 있다. |

## 8. 기능 완료 정의

기능 하나는 `anf-feature-cycle` 하네스에서 아래 표가 정한 단계를 모두 마쳐야 `done`이다.

1. 조사 브리프: `_workspace/{feature}/01_researcher_brief.md` (아래 표에서 조사를 생략하는 FR은 제외)
2. 설계 기록: `_workspace/{feature}/02_main_design.md`. 사용자가 확인한 범위, 결정, 검증 기준, 관련 FR·AR·D·S ID와 스파이크 결과 링크가 들어 있다.
3. 테스트를 먼저 쓴 구현
4. 실환경 검증 보고서의 모든 수락 기준이 최신 결과 기준으로 PASS. UNVERIFIED와 skip은 PASS로 세지 않는다.
5. 개념 문서: `docs/concepts/{feature}.md`
6. `docs/feature-status.md`에 `done` 기록. 데이터 검증 PASS만으로는 `done`이 아니다.

## 9. 성공 기준

- 1단계와 2단계 기능(FR-01~FR-13)이 모두 `done`이다. FR-14(CSI 드라이버)는 선택이라 넣지 않는다. §5 대본 7번의 메트릭(FR-12)과 아래 CI(FR-11)가 2단계에 있기 때문이다.
- §5의 데모 대본을 스크립트 하나로 처음부터 끝까지 재현할 수 있다.
- `main` 브랜치의 CI가 통과 상태다.
- 조사 단계를 거친 기능(§8 표)의 개념 문서는 실제 ANF·ONTAP과 다른 점을 하나 이상 설명한다. 조사를 생략한 FR-09~FR-11, FR-13은 ANF·ONTAP 절이 "해당 없음"이다.

## 10. 제약

- **호스트:** Windows 11 Home, RAM 15.7GB, i5-1235U. Windows 11 Home에는 NFS 서버도 NFS 클라이언트도 없다. 그래서 데이터 플레인은 WSL2 Ubuntu 24.04(커널 6.18)에서 돌리고, 클라이언트는 Docker 컨테이너로 둔다.
- **WSL 메모리:** 약 7GB.
- **커널:** `nfsd`, `btrfs`, `dm-thin`은 모듈이고, blk-cgroup I/O 제한(`CONFIG_BLK_DEV_THROTTLING=y`)은 커널 내장이다 (`/proc/config.gz`). 모듈 로드와 NFS 서버 기동은 [ADR 스파이크 S0](ADR.md#10-위험과-스파이크)에서 확인했다 (`_workspace/spikes/S0.md`).
- **작업 방식:** 구현 코드는 Claude가 쓰고, 작성자는 개념 문서를 바탕으로 설명한다.
