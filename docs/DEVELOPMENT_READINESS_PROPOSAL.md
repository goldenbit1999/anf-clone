## 1. 점검 결론과 범위

프로젝트의 목표, 실제 데이터 효과 중심의 수락 기준, 조사·설계·검증·개념 설명의 역할 분리는 잘 잡혀 있다. 다만 TDD 훅, 테스트 실행 위치, API 계약에 개발 전에 해결해야 할 문제가 있다. 아키텍처의 일부 결정과 데이터 플레인 실험도 남아 있다.

현재 ADR·Architecture에 해당하는 내용은 `docs/ADR.md` 한 파일에 아키텍처 요구사항, 구성도, 결정 기록으로 통합되어 있다. 이 제안서는 그 문서를 기준으로 작성했다. 문서 분리는 우선 작업에 포함하지 않는다.

이 문서는 두 차례 점검의 정적 분석, 임시 폴더 재현, 공식 문서 확인 결과를 합친 최종 제안이다. 두 번째 점검에서 더한 것은 R-08~R-10과, 기존 항목에 덧붙인 내용(R-01의 skip 보고와 서브에이전트 훅, R-02의 WSL 가상환경 위치, R-03의 409 거절과 `Patching`, R-05의 스파이크·대응표·FR별 단계, R-06의 FR 열)이다. 제품 코드나 기존 하네스를 수정한 결과 보고서는 아니다. 애플리케이션은 아직 구현되지 않았으며, NFS·스냅샷·QoS의 실동작은 검증되지 않았다.

## 3. R-01 — TDD 훅의 허점 보완

### 확인한 문제

대상은 [tdd_guard.py](../.claude/hooks/tdd_guard.py)의 `pre`, `run_pytest`, `stop`과 [PRD](PRD.md) NFR-05, [CLAUDE.md](../CLAUDE.md)의 TDD 설명이다.

`pre`는 짝이 되는 테스트 파일의 존재만 확인한다. 테스트가 실제로 있는지, 구현할 동작 때문에 실패했는지는 확인하지 않는다. `stop`은 pytest의 테스트 미수집 결과를 허용하고, pytest 미설치·시간 초과에서는 메시지만 남긴다.

임시 폴더에서 다음 결과를 확인했다. 프로젝트 파일은 변경하지 않았다.

| 사례 | 관찰 결과 | 의미 |
| --- | --- | --- |
| 테스트 파일 없음 | 구현 파일 수정 거절 | 기본 차단은 동작함 |
| 빈 `test_volume.py` 존재 | 구현 파일 수정 허용 | 파일 존재만으로 차단을 통과함 |
| 빈 테스트 파일을 pytest로 실행 | `no-tests` | 실제로 실행할 테스트가 없음 |
| 위 상태에서 dirty 표시 후 Stop 호출 | 차단 응답 없음 | 테스트가 없어도 종료를 허용함 |
| `assert True`만 있는 짝 테스트 | 구현 허용, pytest GREEN | 파일 연결과 GREEN만으로 동작 검증을 보장하지 못함 |
| 모든 테스트가 skip | pytest GREEN, Stop 차단 없음 | skip과 실제 검증 성공의 구분이 별도로 필요함 |

pytest 미설치와 시간 초과는 훅의 반환값을 각각 `no-pytest`, `timeout`으로 대체해 종료 분기를 확인했다. 실제 패키지를 제거하거나 240초 시간 초과를 기다린 실험은 아니다. 두 경우 모두 `systemMessage`만 반환했고 차단 결정은 없었다.

모든 테스트가 skip되면 PostToolUse는 `GREEN`이라고 알린다. pytest가 종료 코드 0을 돌려주고, 훅이 0을 GREEN으로 바꾸기 때문이다(`tdd_guard.py:78`). 그래서 Windows에서 skip되는 Linux 전용 테스트는 RED를 볼 수 없다. ADR §9.1의 "건너뛴 테스트를 통과로 보고하지 않는다"와도 어긋난다.

훅은 서브에이전트의 도구 호출에도 실행된다. 공식 문서는 `settings.json`의 PreToolUse·PostToolUse가 서브에이전트 안에서도 같은 방식으로 실행된다고 쓴다. [real-env-verify](../.claude/skills/real-env-verify/SKILL.md) 68줄은 테스트 디렉터리가 정해지지 않았으면 검증 스크립트를 `scripts/verify/`에 두라고 한다. 그런데 이 위치의 `.py` 파일은 짝 테스트가 없으면 훅에 막힌다.

### 권장 변경

1. 파일 존재, 테스트 수집, 실행 성공, 검증 미실행을 서로 다른 상태로 관리한다. 구현 파일과 연결된 테스트가 비어 있거나 수집되지 않으면 수정 허용 조건을 충족하지 못한 것으로 처리한다.
2. 새 동작에 대한 RED 실행 근거를 남긴다. 테스트 식별자, 테스트 내용 해시, 명령, 실행 결과를 기록하고 테스트가 바뀌면 이전 근거를 무효화한다. 관련 RED 근거 없이 구현을 시작하지 않는 절차를 명시한다.
3. 환경 오류·잘못된 테스트 문법·의존성 누락을 정상적인 동작 검증 RED와 구분한다. 구현할 모듈이 아직 없어 발생하는 import 실패는 예상한 RED인지 확인하고 기록한다. 단순 종료 코드만으로 의미 있는 RED를 판정하지 않는다.
4. 기존 동작을 유지하는 리팩터링에는 기존 테스트와 직전 GREEN을 사용할 수 있게 한다. 모든 편집에 새 실패를 요구하는 방식은 피한다.
5. 코드가 바뀐 턴의 `no-tests`, `no-pytest`, `timeout`을 검증 완료로 처리하지 않는다. 종료 훅의 첫 확인에서는 해결 또는 미검증 보고를 요구하고, 반복 호출에서는 무한 차단을 피하면서 미해결 상태를 보존한다.
6. dirty 표시와 검증 실패 결과를 검사 전에 지우지 않는다. 정상 확인 뒤 정리하고, 확인 불가로 종료하면 다음 실행에서 다시 확인할 수 있게 남긴다.
7. 단위·계약 테스트의 GREEN과 데이터 플레인의 PASS를 분리한다. Windows에서 Linux 테스트를 skip하는 것은 허용하되, skip을 실환경 PASS로 세지 않는다.
   - PostToolUse는 수집된 테스트가 모두 skip이면 GREEN 대신 SKIPPED로 알린다. pytest에 `-rs`를 붙여 skip 이유를 출력에 남긴다.
8. 문서에 훅의 보장 범위를 정확히 쓴다. 테스트 의미와 품질에는 리뷰가 필요하며, 현재 Bash 쓰기·비Python 파일은 훅 대상 밖이다. 기존 TDD 요구사항은 유지한다.
9. 훅이 서브에이전트에도 걸린다는 점을 문서에 쓴다. real-env-verify의 검증 스크립트 위치를 테스트 폴더(예: `backend/tests/e2e/`)로 바꾼다. 이 폴더의 보조 파일은 훅의 면제 대상이다.

### 완료 기준

- 빈 테스트, 테스트 미수집, pytest 미설치, 시간 초과, 정상 RED→GREEN에 대한 훅 검증 사례가 있다.
- 예상한 RED를 확인한 뒤 최소 구현을 추가하고 GREEN에 도달할 수 있다.
- 검증이 실행되지 않은 결과로 기능을 `done` 처리하지 않는다.
- 종료 훅이 무한 반복하지 않으면서 실패·미검증 결과를 잃지 않는다.
- `CLAUDE.md`, PRD, 기능 사이클의 TDD 설명이 실제 훅 동작과 일치한다.
- 모든 테스트가 skip된 파일을 실행하면 훅이 GREEN이 아니라 SKIPPED로 보고한다.
- verifier가 검증 스크립트를 만들 때 훅에 막히지 않는다.

## 4. R-02 — 테스트 설정과 실행 위치 통일

### 확인한 문제

[ADR](ADR.md) §12는 `backend/pyproject.toml`을 제안하지만, 훅은 저장소 루트를 cwd로 사용하고 루트 `.venv`만 찾는다.

임시 프로젝트에 `backend/pyproject.toml`, `backend/anf_api/`, `backend/tests/`를 만들고 pyproject에 `pythonpath`를 설정했다. 저장소 루트에서 실행한 전체 테스트는 설정을 읽지 못해 `ModuleNotFoundError: No module named 'anf_api'`로 실패했고, backend에서 실행하면 같은 테스트가 통과했다. 이는 제안된 구조의 재현 결과이며, 아직 없는 제품 코드에서 발생한 장애는 아니다.

### 권장 변경

권장안은 Python 프로젝트 설정을 루트 `pyproject.toml`에 두고, 코드는 `backend/` 아래에 유지하는 것이다. 패키지 설치·테스트 탐색·마커 설정을 루트에서 관리한다. 기존 `backend/pyproject.toml` 구성을 유지하려면 훅이 backend를 cwd와 설정 기준으로 사용하도록 명시적으로 바꿔도 된다. 두 방식 중 하나를 채택해 전체 문서와 명령에 일관되게 적용한다.

가상환경은 Windows와 WSL에서 별도로 만든다. 예를 들어 `.venv-win/`, `.venv-wsl/`을 사용할 수 있다. 훅은 현재 OS에 맞는 Python만 선택하고, 사용할 인터프리터와 설정 파일·cwd를 결과에 표시한다. 경로가 정해지면 `.gitignore`도 함께 갱신한다. WSL 가상환경을 `/mnt/c` 아래 저장소에 두면 9P 파일시스템을 거쳐 설치와 import가 느리다(ADR R-06). 그래서 저장소 밖 경로(예: `~/.venvs/anf-clone`)도 후보로 둔다.

수정 대상은 `tdd_guard.py`, `.claude/settings.json`, `CLAUDE.md`의 Commands, ADR §9·§12다. pytest 실행 인자를 공통으로 정의해 훅·수동 실행·CI가 같은 설정을 사용하게 한다.

### 완료 기준

- 선택한 가상환경에서 문서에 적힌 명령으로 단위·계약 테스트가 실행된다.
- 관련 테스트를 실행하는 PostToolUse와 전체 테스트를 실행하는 Stop이 같은 설정·패키지 경로를 사용한다.
- Windows 훅이 WSL 가상환경을 선택하거나 그 반대가 발생하지 않는다.
- 프론트엔드 타입 검사·빌드 명령도 프로젝트 생성 시 별도로 추가한다. Python 훅의 GREEN으로 프론트엔드 검증을 대신하지 않는다.

## 5. R-03 — API 작업별 비동기 계약 정의

### 확인한 문제

[PRD](PRD.md) FR-01은 모든 PUT·PATCH·DELETE가 완료 전에 응답하고 본문에 `provisioningState`, 헤더에 작업 상태 URL을 제공하도록 요구한다.

하지만 계정 PATCH는 동기 완료 `200`을 허용하고(실서비스에서도 tags만 바꾼 PATCH가 `200`으로 바로 끝났다, 녹화 R2), 없는 계정의 DELETE는 본문 없는 `204`를 반환한다. DELETE `202` 역시 본문 없이 헤더로 작업을 추적할 수 있다. 기존 계정 조사 브리프에도 이 구분이 들어 있다.

### 권장 문구

FR-01을 다음 취지로 수정한다.

> 변경 요청은 해당 ANF 작업의 REST 계약을 따른다. 비동기 작업은 초기 응답에 정의된 추적 헤더를 제공하고, 클라이언트는 해당 URL을 폴링해 완료 또는 실패를 확인한다. 본문이 있는 리소스 응답에는 작업 계약에 따라 `provisioningState`를 제공한다. 동기 완료 응답과 본문 없는 응답은 작업별 계약을 따른다. POST 액션의 비동기 여부도 개별 계약에 명시한다.

아래 구분을 출발점으로 계정의 `02_main_design.md`에 최종 응답 표를 작성한다.

| 작업 | 설계에서 정할 항목 |
| --- | --- |
| PUT 신규 생성 | `201`, 리소스 본문, `Azure-AsyncOperation`, 초기·최종 상태 |
| PUT 기존 리소스 갱신 | `200`의 본문·상태·추적 헤더. 스펙과 녹화의 차이를 명시 |
| PATCH | 동기 `200`과 비동기 `202` 중 클론이 제공할 경우, 본문과 추적 헤더 |
| DELETE 기존 리소스 | `202`, 본문 유무, 추적 헤더, 완료 뒤 GET `404` |
| DELETE 없는 리소스 | `204`, 본문 없음, 작업 생성 여부 |
| DELETE 거절 (자식 리소스 있음) | 즉시 `409 CannotDeleteResource`, 작업을 만들지 않음. 실서비스에서는 ARM 게이트웨이가 거절했다(녹화 R4). 클론에서 이 검사를 어느 계층에 둘지 |
| 이후 POST 액션 | 스냅샷 되돌리기 등 각 액션의 초기 응답과 완료 조회 방식 |

외부 ARM 작업과 내부 storage job의 상태·헤더를 섞지 않는다. 실제 서비스와 다르게 선택한 동작은 설계와 개념 문서에 이유를 남긴다. preview 녹화의 관찰을 stable 계약으로 옮길 때는 버전 차이를 명시한다.

ADR §6.3의 진행 중 상태 후보는 `Creating`, `Updating`, `Deleting`뿐이다. 계정 브리프가 찾은 `Patching`(PATCH 202의 스펙 예시)을 더한다. PUT 갱신의 `Updating`은 녹화 R3에서 확인됐다.

### 완료 기준

- PRD·ADR·계정 설계·계약 테스트가 동일한 응답 표를 따른다.
- 동기 `200`, 본문 없는 `204`, 비동기 `202`를 공통 규칙이 잘못 거절하지 않는다.
- 비동기 요청은 실패·완료·폴링 간격과 제한 시간까지 검증 기준이 정해져 있다.

## 6. R-04 — 풀 용량 동시성 및 장애 복구 보완

### 확인한 문제

[ADR](ADR.md) §6.4에는 리소스당 진행 중 작업 하나와 재시작 후 대조 원칙이 있다. 서로 다른 볼륨이 같은 풀의 잔여 용량을 동시에 사용하는 경우와, agent가 일부 단계만 실행한 상태에서 재시작하는 경우의 세부 규칙은 없다.

### 권장 변경

SQLite와 storage agent 제안이 채택되는 경우 다음 규칙을 ADR과 해당 기능 설계에 반영한다. 다른 선택이 확정되면 같은 요구사항을 그 방식으로 만족시킨다.

- 풀 용량 확인·예약과 볼륨 리소스·작업 생성을 하나의 원자적 처리로 묶는다. 생성 중 예약도 할당량 합계에 포함한다.
- 생성 실패·취소·삭제 완료 시 예약과 사용량을 어떻게 정리할지 정한다. 커널 자원 정리가 실패한 경우의 용량 회수 시점도 명시한다.
- 부모 삭제와 자식 생성이 동시에 요청될 때 서로 모순되는 상태를 만들지 않도록 처리 순서와 충돌 응답을 정한다.
- storage job 제출에 안정적인 작업 식별자를 사용한다. job ID 저장 전후의 재시도에서도 자원을 중복 생성하지 않아야 한다.
- 파일시스템 생성, quota 적용, export 적용을 구분하고 재시작 후 실제 상태와 대조한다. 계속 진행할지, 보상 정리할지, `Failed`로 둘지 단계별로 정한다.

### 완료 기준

- 잔여 용량으로 두 요청을 모두 수용할 수 없는 풀에서 동시 볼륨 생성이 할당량을 초과하지 않는다.
- 부모 삭제와 자식 생성의 동시 요청이 고아 리소스를 만들지 않는다.
- agent 실행 중, job ID 저장 전후, 최종 상태 기록 전에 프로세스를 중단해도 재시작 후 작업이 종결된다.
- 실패 후 DB 예약과 실제 파일시스템·export 상태가 설명 가능한 상태로 일치한다.

## 7. R-05 — 문서와 스파이크를 기능 사이클에 연결

### 권장 변경

[anf-feature-cycle](../.claude/skills/anf-feature-cycle/SKILL.md)의 0단계에 다음 확인을 추가한다.

1. `CLAUDE.md`, PRD의 해당 FR·NFR, ADR의 관련 요구사항·결정·스파이크를 읽는다.
2. `02_main_design.md`에 관련 ID와 아직 확정되지 않은 선택을 적는다. 해당 기능이 의존하는 결정만 구현 전에 확정한다.
3. 스파이크 결과 파일과 판정을 확인한다. 결과가 없으면 선행 실험을 수행하고 기록한 뒤 관련 설계를 확정한다.
4. 결정이 바뀌면 ADR을 기준으로 PRD와 `CLAUDE.md`의 요약도 갱신한다. 지금 사이클은 결정을 `CLAUDE.md`에만 반영하라고 한다(0단계 1번).
5. 스파이크를 누가 실행하고 결과를 어디에 남길지 정한다. ADR §10은 결과를 기능의 `02_main_design.md`에 남기라고 한다. 그런데 S0처럼 여러 기능에 걸친 스파이크는 한 기능 폴더에 두기 어렵다. `_workspace/spikes/S0.md`처럼 기능 밖에 두고, 각 기능의 설계 기록이 링크하는 방식을 제안한다.
6. ADR §2.3 리소스 대응표는 "기능마다 조사 단계에서 고친다"고 돼 있지만 고칠 주체가 없다. 기능의 설계를 확정할 때 메인이 갱신한다고 사이클에 적는다.
7. PRD의 FR마다 거칠 사이클 단계를 정한다. PRD §8은 모든 기능에 조사 브리프를 요구한다. 그런데 FR-10·FR-11·FR-13(테스트 자동화, CI, 컨테이너)은 ANF 기능이 아니라서 ANF·ONTAP 조사가 맞지 않는다. FR-12(메트릭)는 Azure Monitor 메트릭 대응 조사가 있다(ADR §8). FR-01(LRO)은 별도 기능인지, 계정과 함께 구현·검증하는지 정해져 있지 않다.

| 진입할 기능 | 선행 확인 |
| --- | --- |
| 계정 | 상태 저장소(D-07)·워커 방식(D-09)·인증(D-13) 등 해당 구현에 필요한 선택. 인증은 첫 엔드포인트부터 영향을 준다. S0는 필수 아님 |
| 용량 풀 | 용량 계산과 동시성 규칙. S0는 필수 아님 |
| 볼륨 | S0 환경·NFS 마운트 확인, S1 스토리지 후보 비교, D-10·D-11 결정 |
| 처리량 제한 | S2 측정, D-12 결정. 선택한 볼륨·네트워크 구조와의 호환성 확인 |
| 데이터 플레인 CI | S3 결과와 사용할 러너 결정 |

[real-env-verify](../.claude/skills/real-env-verify/SKILL.md)의 환경 점검도 기능별로 적용한다. 순수 컨트롤 플레인 항목에 Docker·NFS 조건을 일괄 요구하지 않는다. 데이터 플레인 불변 검증을 못 했으면 그 항목은 UNVERIFIED로 남긴다.

### 완료 기준

- 각 기능 설계에서 관련 FR·AR·D·S 항목과 결과 파일을 찾을 수 있다.
- 선행 스파이크가 없는 상태에서 볼륨·QoS 구현을 완료로 선언하지 않는다.
- 계정·풀은 자신의 검증에 필요한 환경 조건을 명확히 구분한다.
- PRD의 FR마다 거칠 사이클 단계가 정해져 있다.
- 기능 밖 스파이크의 결과 위치가 정해져 있고, 기능 설계가 그 결과를 링크한다.

## 8. R-06 — 중간 상태와 재실행 기록 보완

### 권장 변경

기록을 6단계에만 두지 않고, 시작·단계 완료·검증 실패·중단 시점에도 갱신한다. `docs/feature-status.md`는 첫 사이클 시작 시 만들고, 각 기능의 상세 진행 기록은 작업 폴더에 둔다.

상태에 `in_progress`를 추가하고 기존 `partial`, `blocked`, `done`과 구분한다. `done`은 PRD의 완료 정의를 모두 충족한 경우에만 쓴다. 데이터 검증 PASS만으로 개념 문서까지 끝났다고 기록하지 않는다.

권장 표의 열은 다음과 같다.

```text
기능 | FR | 상태 | 마지막 완료 단계 | 검증 대상 코드 | 검증 보고서 | 갱신일 | 개념 문서
```

- 범위·제품 코드 변경으로 기존 검증이 무효가 되면 즉시 `done`을 해제하고 영향 범위를 기록한다.
- 문서 표현만 고치는 재실행은 기존 데이터 검증을 유지할 수 있다. 코드와 수락 기준이 그대로라는 근거를 남긴다.
- FAIL·UNVERIFIED로 멈출 때 먼저 상태와 원인, 재개할 단계를 저장한다.
- 부분 재검증에서는 전체 수락 기준 목록에 이전 PASS와 재검증 결과를 합쳐 각 기준의 최신 유효 결과를 표시한다. 변경 영향을 받는 이전 PASS는 다시 검증한다.
- 보고서에는 검증한 제품 코드의 커밋을 적는다. 미커밋 코드라면 변경 스냅샷 등 같은 대상을 식별할 수 있는 근거를 남긴다.

### 완료 기준

- 새 세션에서 기록 파일만 읽어 다음 단계를 결정할 수 있다.
- 검증 중단·실패 후에도 상태 파일이 갱신되어 있다.
- 범위가 바뀐 기능이 과거 결과만으로 `done` 상태를 유지하지 않는다.
- 부분 재검증 뒤에도 전체 수락 기준의 PASS·FAIL·UNVERIFIED를 확인할 수 있다.

## 9. R-07 — 조사 실행 상한과 종료 조건 추가

### 권장 변경

[anf-researcher](../.claude/agents/anf-researcher.md)와 [anf-research](../.claude/skills/anf-research/SKILL.md)에 제한과 종료 조건을 추가한다. 다음 수치는 초기 제안값이며 사용 결과로 조정한다.

- 에이전트 frontmatter에 `maxTurns: 30`을 둔다. 턴 제한은 토큰·요금의 고정 상한과 다르다는 점을 명시한다.
- 조사 시작 시 필수 질문을 API 계약, 비동기, 오류, 데이터 효과, ONTAP 대응으로 좁힌다.
- 공식 스펙·예시와 문서를 우선 확인한다. 녹화는 문서로 해결되지 않은 질문에 집중한다.
- 같은 접근 거부 출처를 반복 호출하지 않는다. 대체 출처도 확인하지 못하면 `[미확인]`과 시도 내역을 남긴다.
- 필수 질문의 답이 모였거나 실행 상한에 도달하면 브리프를 저장하고 반환한다. 한도 도달 결과를 조사 완료로 포장하지 않는다.
- 재조사는 변경된 질문만 다루고, 기존 원문과 브리프를 재사용한다. 설계에 영향이 없는 주변 기능은 후속 조사 목록으로 남긴다.

### 완료 기준

- 상한에 도달해도 사용 가능한 중간 브리프와 미확인 목록이 남는다.
- 메인은 미확인 항목이 설계를 막는지 판단할 수 있다.
- 같은 기능의 보완 조사에서 원문 전체와 기존 질문을 다시 조사하지 않는다.

## 10. R-08 — 검증 에이전트 재개 방식 수정

### 확인한 문제

[anf-feature-cycle](../.claude/skills/anf-feature-cycle/SKILL.md) 4단계(83줄)는 `Agent(name: "verifier-{feature}", ...)`로 검증 에이전트를 띄우고, 재검증할 때 `SendMessage({to: "verifier-{feature}"})`를 보낸다.

공식 문서에 따르면 Agent 도구의 `name` 인자는 에이전트 팀을 켠 세션에서 쓴다. 에이전트 팀이 켜진 대화형 세션에서는 `name`을 준 서브에이전트가 일반 서브에이전트가 아니라 팀원(teammate)으로 뜬다. 이번 점검 세션의 Agent 도구에는 `name` 인자가 없었다. 그래서 지금 설정에서는 4단계의 호출을 적힌 대로 실행할 수 없다.

`SendMessage`는 이름 대신 에이전트 ID로도 서브에이전트를 재개할 수 있다. 서브에이전트가 끝나면 메인이 ID를 받는다. 새 세션에서 이전 verifier를 같은 ID로 이어 갈 수 있는지는 확인하지 않았다.

### 권장 변경

1. 4단계를 에이전트 ID 기준으로 바꾼다. 처음 띄울 때 받은 ID를 기능 진행 기록(R-06)에 적고, 재검증은 그 ID로 `SendMessage`한다.
2. 에이전트 팀을 켜고 이름을 쓰는 방식을 택한다면, 팀원으로 뜨는 동작이 "리더에게만 보고한다"는 [real-env-verifier](../.claude/agents/real-env-verifier.md)의 통신 규칙과 맞는지 먼저 확인한다.
3. ID로 이어 갈 수 없으면(새 세션, 응답 없음) 새 verifier를 띄우고 이전 보고서 경로를 모두 넘긴다. 지금 오류 처리(119줄)에 있는 이 대안을 기본 경로로 올린다.
4. real-env-verifier의 통신 규칙과 사이클의 오류 흐름 예시도 같은 방식으로 맞춘다.

### 완료 기준

- 에이전트 팀을 켜지 않은 세션에서 4단계가 적힌 대로 실행된다.
- FAIL → 수정 → 재검증이 같은 verifier 맥락에서 이어진다. 이어 갈 수 없으면 새 verifier가 이전 보고서를 읽고 회차 번호를 이어 쓴다.

## 11. R-09 — 데이터 플레인 배치 위험을 ADR에 추가

### 확인한 문제

ADR §5와 §10에 다음 세 가지가 없다.

1. **스토리지 루트 위치.** storage agent가 쓰는 루트 디렉터리(루프 파일, btrfs, thin 풀)의 위치가 없다. 저장소처럼 `/mnt/c`(9P) 아래에 두면 느리고, 루프 장치 같은 커널 기능이 제대로 동작하는지 보장되지 않는다 [확인 필요].
2. **같은 커널을 쓰는 NFS.** 클라이언트 컨테이너와 knfsd가 같은 WSL 커널과 메모리를 쓴다. 실제 ANF의 클라이언트는 별도 VM이고 네트워크를 거친다. 그래서 처리량 측정, 페이지 캐시 효과, 메모리 압박 때의 동작이 실제와 다를 수 있다. 한 호스트에서 NFS 서버와 클라이언트를 함께 돌리면 메모리 압박 때 교착 위험이 있다고 알려져 있다 [확인 필요].
3. **NFS LOCALIO.** LOCALIO는 NFS 클라이언트와 서버가 같은 호스트에 있음을 확인하면 read, write, commit에서 네트워크 RPC를 건너뛰는 커널 기능이다. 커널 문서는 컨테이너 환경을 주요 사용처로 든다. 켜져 있으면 데이터 I/O가 네트워크를 거치지 않으므로, T1(tc 네트워크 제한)이 데이터 I/O에 걸리지 않을 수 있다. 지금 WSL 커널은 `# CONFIG_NFS_LOCALIO is not set`이라 해당하지 않는다. 다만 S0 실패 시의 대안이 커스텀 커널이고, 새 커널 설정에서 이 옵션이 켜질 수 있다.

### 권장 변경

- ADR §5에 스토리지 루트를 WSL ext4 안의 고정 경로(예: `/var/lib/anf-clone`)로 적는다. agent는 그 아래 경로만 받는다.
- ADR §10 위험표에 같은 커널을 쓰는 NFS의 위험을 새 항목(ADR R-08)으로 더한다. 처리량·스냅샷 개념 문서의 "실제 ANF와 다른 점"에도 적는다.
- S0에 `CONFIG_NFS_LOCALIO` 확인을 넣는다. 커스텀 커널에서 켜져 있으면 빌드에서 끄거나, `nfs` 모듈 파라미터 `localio_enabled`를 `N`으로 둔다.
- S2의 처리량 측정 조건에 페이지 캐시 효과를 줄이는 방법(예: `fio --direct=1`, 측정 전 캐시 비우기)과 반복 횟수를 정한다.

### 완료 기준

- ADR에 스토리지 루트 위치가 있고, agent가 그 밖의 경로를 거절한다.
- S0 결과에 LOCALIO 설정 값이 있다.
- 처리량 개념 문서가 "클라이언트와 서버가 같은 커널을 쓴다"는 차이를 설명한다.
