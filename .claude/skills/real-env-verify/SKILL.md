# 실환경 검증 절차

이 프로젝트의 핵심 주장은 "목업이 아니라 실제로 동작한다"이다. 검증은 그 주장을 뒷받침할 증거를 남기는 일이다. 그래서 API가 돌려준 상태 값이 아니라 **클라이언트에서 관찰한 효과**로 판정한다. 예를 들어 API가 `provisioningState: Succeeded`를 돌려줘도 클라이언트에서 마운트가 안 되면 FAIL이다.

## 0. 환경 사전 점검

검증을 시작하기 전에 먼저 실행하고, 결과를 보고서 맨 위에 적는다. 하나라도 실패하면 영향을 받는 항목을 UNVERIFIED로 두고 이유를 쓴다. 환경 문제를 기능 결함으로 잘못 판정하지 않기 위해서다.

점검은 이 기능의 검증 항목에 필요한 것만 한다. 순수 컨트롤 플레인 기능(계정, 용량 풀)에 Docker·NFS 조건을 일괄 요구하지 않는다. 다만 "데이터 플레인이 바뀌지 않았다"를 확인하는 항목에 필요한 조건이 없으면, 그 항목만 UNVERIFIED로 둔다.

| 점검 | 필요한 기능 | 방법 |
| --- | --- | --- |
| 컨트롤 플레인 서비스 | 모든 기능 | 서비스가 떠 있는지 확인한다. 명령은 아래 "스택별 명령"을 쓴다 |
| WSL 배포판 | WSL에서 실행하는 모든 항목 | `wsl -l -v`에서 Ubuntu가 실행 중인지 확인한다 |
| 커널 모듈 | 볼륨 이후의 데이터 플레인 기능 | 필요한 모듈(nfsd, btrfs 등)이 로드됐는지 `wsl -d Ubuntu -- lsmod`로 확인한다 |
| Docker | 클라이언트 컨테이너로 마운트하는 항목 | Ubuntu 안 Docker Engine을 쓴다 (ADR D-10). `wsl -d Ubuntu -- docker version`이 서버 버전과 `Os=linux`를 돌려주고, `wsl -d Ubuntu -- readlink /usr/bin/docker`가 비어 있는지(Docker Desktop 연동 링크가 아닌지) 확인한다. 엔진이 멈춰 있으면 `wsl -d Ubuntu -u root -- systemctl start docker`로 띄운다. 그래도 안 되거나 Desktop 연동이 다시 켜져 있으면 리더에게 보고한다 |
| 대시보드와 브라우저 | 대시보드 화면을 관찰하는 항목 | `frontend/`에서 `npm ci`가 끝나 있고, 대시보드 서버(`CLAUDE.md`의 명령)가 `http://127.0.0.1:5173`(dev) 또는 `4173`(preview)에서 `200`을 준다. Windows에서 `curl "http://127.0.0.1:8080/subscriptions/x/providers/Microsoft.NetApp/netAppAccounts?api-version=2026-08-01"`이 `200`이다(WSL의 anf-api가 Windows에 보이는지). 브라우저 도구(Claude in Chrome, `mcp__claude-in-chrome__*`)가 새 탭을 열고 페이지 글자를 읽을 수 있다. 브라우저 도구가 없으면 화면 항목은 UNVERIFIED다. 대신 curl로 API만 보고 PASS로 하지 않는다 |

## 1. 검증 항목 만들기

`02_main_design.md`의 검증 기준을 검증 항목으로 옮긴다. 설계의 기준 ID(`AC-01` 등)를 항목 이름에 그대로 쓴다. 리더가 회차별 결과를 이 ID로 합치기 때문이다. 각 항목은 다음 세 층 가운데 하나 이상에 속한다.

| 층 | 확인하는 것 | 예 |
| --- | --- | --- |
| API 계약 | 응답 코드, 헤더, 본문 속성이 브리프의 ANF 스펙과 설계대로인지 | PUT → 201 + `Azure-AsyncOperation` 헤더 |
| 상태 전이 | `provisioningState`가 설계한 순서로만 바뀌고 최종 상태에 도달하는지, 실패하면 `Failed`가 되는지 | Creating → Succeeded |
| 데이터 효과 | 클라이언트에서 관찰되는 실제 변화 | 마운트, 파일 읽기·쓰기, `.snapshot`, 용량, 처리량 |

데이터 플레인 기능이라면 데이터 효과 항목이 적어도 하나 있어야 한다. 없으면 "실제 동작"을 증명할 수 없으므로 리더에게 알린다.

회귀 항목은 바뀐 코드가 닿는 테스트 파일만 돌린다. 전체 데이터 플레인 묶음(약 100분)은 WSL에서 돌리지 않는다. 전체 회귀는 PR의 CI `data-plane` 작업이 맡고, 그 기준은 리더가 CI 실행 결과로 판정한다 (`anf-feature-cycle` 4단계 7번). 보고서에는 그 기준을 `대기`로 두고 "PR의 CI로 판정"이라고 적는다.

컨트롤 플레인 전용 기능(예: 계정)이라면 API 계약과 상태 전이 항목으로 검증한다. 여기에 데이터 플레인이 바뀌지 않았음을 확인하는 항목을 하나 넣는다(예: 작업 전후의 export 목록 비교).

## 2. 데이터 효과 검증 패턴

모든 확인은 볼륨을 마운트한 클라이언트에서 한다. 그래서 백엔드가 무엇이든 같은 방식으로 검증할 수 있다. 해당 기능이 구현돼 있을 때만 그 패턴을 쓴다.

| 기능 | 절차 | PASS 조건 |
| --- | --- | --- |
| 볼륨 생성·마운트 | 클라이언트 컨테이너에서 마운트하고 파일을 쓴다. 다시 마운트하거나 다른 클라이언트에서 그 파일을 읽는다. | 내용이 일치한다. |
| 스냅샷 | 파일 A를 만들고 스냅샷을 찍는다. A를 고치거나 지운 뒤 `.snapshot/{이름}/A`를 읽는다. 생성 시간과 추가로 쓴 공간도 기록한다. | 스냅샷 시점의 내용이 읽힌다. |
| 크기·쿼터 | 할당한 크기보다 많이 쓴다. | 공간 부족 오류(ENOSPC 또는 EDQUOT)로 실패한다. `df`의 크기가 할당량과 일치한다. |
| 처리량(QoS) | fio 같은 도구로 순차 쓰기·읽기를 여러 번 측정한다. | 측정값이 한도 이하다(허용 오차를 명시한다). 한도를 바꾸면 측정값도 바뀐다. |
| export policy | 허용한 IP와 허용하지 않은 IP의 클라이언트에서 각각 마운트한다. | 허용한 쪽만 성공한다. |
| 삭제 | 볼륨을 삭제한 뒤 마운트를 시도한다. | 마운트가 실패하고 저장 공간이 회수된다. |
| 대시보드 화면 | 브라우저 탭을 한 번 열고, 그 뒤로는 이동도 새로 고침도 하지 않는다. API로 상태를 바꾸면서(결함 주입의 지연으로 진행 중 상태를 길게 만든다) 같은 탭의 글자를 시각과 함께 여러 번 읽는다. 같은 순간의 API GET 응답도 함께 남긴다. | 화면의 계층·이름·`provisioningState`가 API와 같고, 설계의 제한 시간 안에 바뀐 상태가 보인다. 탭을 다시 읽지 않았다는 근거(같은 탭 ID, `performance.getEntriesByType("navigation")`이 하나이고 `type`이 `navigate`)를 남긴다. |

컨테이너 안에서 NFS를 마운트하려면 보통 `--privileged`나 `--cap-add SYS_ADMIN`이 필요하다.

## 3. 통합 정합성

구성 요소가 둘 이상이면 연결된 양쪽 코드를 함께 읽고 대조한다. 각각 따로 보면 맞아 보여도 연결 지점에서 깨지는 경우가 가장 흔하기 때문이다.

- **응답 구조**: API 응답 구조가 대시보드나 CLI가 기대하는 구조와 같은지 본다. 필드명 대소문자, 감싼 객체, 즉시 응답과 최종 응답의 차이를 확인한다.
- **상태 전이**: 상태 전이 정의와 실제로 상태를 바꾸는 코드를 대조한다. 빠진 전이와 정의되지 않은 전이를 찾는다.
- **호출 관계**: API 엔드포인트 목록과 그것을 호출하는 쪽의 목록을 대조한다.

## 4. 판정 규칙

- **PASS**: 실행한 명령과 출력으로 기준을 충족했음을 보였다. 증거 없는 PASS는 쓰지 않는다.
- **FAIL**: 기준을 충족하지 못했다. 재현 명령, 실제 출력, 기대값, 추정 원인 위치(파일:줄), 수정 제안을 쓴다.
- **UNVERIFIED**: 환경 문제나 도구 부족으로 확인하지 못했다. PASS로 세지 않는다. pytest가 skip한 테스트도 UNVERIFIED다.

판정을 흐리기 쉬운 두 경우는 다음 기준을 따른다.
- **거절을 기대하는 항목은 거절 이유까지 확인한다.** 명령이 실패했다는 사실(종료 코드가 0이 아님)만으로는 PASS가 아니다. 서버가 아직 안 떴거나, 시간이 초과됐거나, 경로가 틀려도 종료 코드는 0이 아니기 때문이다. 기대한 이유로 실패했음을 함께 보인다. 클라이언트 명령이면 stderr 문구나 errno(예: `Protocol not supported`, `Read-only file system`), API면 HTTP 상태 코드와 `error.code`다. e2e 테스트의 단언도 같은 기준으로 쓴다.
- **간헐 결함은 원래 실패율로 반복 횟수를 정한다.** 실패율 p로 관찰된 결함은, 수정 뒤 최소 n = ⌈3/p⌉번 반복해 실패가 한 번도 없어야 PASS다. n번 모두 성공하면 실패율 상한을 95% 신뢰로 약 3/n이라고 말할 수 있기 때문이다(3의 규칙). 예를 들어 p가 7.5%면 40번이다. 보고서에 p, n, 결과를 적는다. n번을 돌리지 못했으면 UNVERIFIED로 두고, 돌린 횟수와 그 횟수로 말할 수 있는 상한(3/돌린 횟수)을 적는다.

측정값은 숫자로 남기고 반복 횟수를 적는다. 처리량은 한 번 측정한 값으로 판정하지 않는다.

## 5. 제품 코드는 고치지 않는다

수정은 리더(메인 세션)가 한다. 검증자가 제품 코드를 고치면 무엇을 검증했는지가 흐려진다.

검증용 스크립트는 만들거나 고쳐도 된다. `backend/tests/e2e/`에 둔다. 재검증하거나 나중에 CI에 붙일 때 그대로 다시 쓰기 위해서다.

TDD 훅(`.claude/hooks/tdd_guard.py`)은 서브에이전트의 Write·Edit 호출에도 걸린다. `tests/` 폴더 아래의 보조 파일(`helpers.py` 등)과 `test_*.py`는 훅이 막지 않는다. 그 밖의 위치(예: `scripts/verify/`)에 `.py`를 쓰면 짝 테스트가 없어 거절된다. pytest 테스트에는 `e2e` 또는 `integration` 마커를 붙인다 (루트 `pyproject.toml`에 등록돼 있다).

## 6. 보고서 형식

**보고서는 시작할 때 저장하고, 판정할 때마다 갱신한다.** 환경 사전 점검 전에 골격을 저장한다. 골격에는 머리말, 이번 회차의 기준 ID 목록이 들어가고, 결과는 모두 `대기`다. 기준 하나를 판정하면 그 항목과 표를 바로 고치고, 맨 위의 진행 상태에 지금 하는 일과 시작 시각을 적는다. 검증은 30~80분 걸린다. 그동안 리더와 사용자가 이 파일만 보고 어디까지 왔는지 알 수 있어야 하고, 중간에 멈춰도 판정한 결과는 남아야 한다.

```markdown
# {기능} 검증 보고서 — {회차}회차

- 진행 상태: 진행 중 — {지금 하는 일} ({시작 시각}) | 완료
- 검증일:
- 검증 대상 코드: 제품 코드 내용 해시(검증 시작과 끝에 계산한 값), 커밋 SHA (`git rev-parse HEAD`), 미커밋 변경 파일 목록. 해시 명령은 아래와 같다. 줄 끝(CRLF/LF)과 새 파일에 상관없이 내용이 같으면 같은 값이 나온다 (`anf-feature-cycle` 3단계 4번):
  `git ls-files -co --exclude-standard -- pyproject.toml backend ':!backend/tests' | LC_ALL=C sort | while IFS= read -r f; do cat "$f"; done | tr -d '\r' | sha256sum`
- 이번 회차 범위: 전체 | 재검증(항목 ID 목록과, 수정의 영향을 받아 다시 실행한 항목)

## 환경 사전 점검
| 항목 | 결과 |

## 결과 요약
PASS n / FAIL n / UNVERIFIED n

## 수락 기준별 최신 결과
재검증 회차에도 전체 기준을 모두 적는다. 이번에 실행하지 않은 기준은 이전 회차의 결과와 그 보고서 이름을 적는다. 수정의 영향을 받을 수 있는 이전 PASS는 다시 실행한다. 아직 판정하지 않은 기준은 `대기`로 둔다.
| 기준 ID | 결과 (PASS, FAIL, UNVERIFIED, 대기) | 확인한 회차 |

## 항목별 결과
### [PASS|FAIL|UNVERIFIED] AC-nn 항목 이름 (층)
- 기준:
- 실행한 명령:
- 출력(핵심 부분):
- (FAIL일 때) 기대값 / 추정 원인 파일:줄 / 수정 제안

## 측정값 (해당할 때)
```

재검증할 때는 이전 보고서를 덮어쓰지 않는다. `04_verifier_report_r2.md`처럼 회차를 붙여 새로 쓴다. 실패에서 수정까지의 과정이 그대로 개발 기록이 되기 때문이다.

**실행 로그와 측정 원본은 실행 중에는 WSL 디스크에 쓰고, 끝나면 보관 위치로 옮긴다.** 실행 중에는 `/root/<회차 폴더>`처럼 WSL 안의 영구 경로에 쓴다. 판정을 마치면 리더가 알려 준 보관 위치(보통 세션 scratchpad, Windows 쪽)로 복사한다. sha256으로 같은지 확인한 뒤 WSL 쪽을 지우고, 보고서에는 보관 위치의 경로를 적는다. 이유는 둘이다.
- `/mnt/c`는 9P 파일 시스템이라 쓰기가 느리다. 로그를 그곳에 바로 쓰면 요청이 많은 시험이 3~4배 느려지고, 이전 회귀와의 시간 비교가 틀어진다(FR-08 1회차, venv를 `/mnt/c` 밖에 두는 것과 같은 이유).
- `/tmp`는 WSL이 다시 부팅되면 비워진다. WSL은 유휴 상태면 스스로 종료되므로, 판정 근거가 된 원본 로그를 잃는다(FR-08 3단계).

## 스택별 명령

기술 스택은 정해졌다(ADR D-01~D-04: FastAPI 백엔드, React + TypeScript 대시보드, NFSv3·NFSv4.1, Docker 클라이언트). 서비스 실행(anf-api, storage agent), WSL 데이터 플레인 setup, 테스트, lint 명령은 `CLAUDE.md`의 "Commands and architecture" 절을 그대로 쓴다. 여기에 옮겨 적지 않는다. 두 곳에 두면 한쪽이 낡기 때문이다.

e2e 검증 코드는 기존 도우미를 먼저 재사용하고, 새 기능에 필요한 것만 기능별 도우미로 더한다. `snapshot_live.py`와 `revert_live.py`가 그렇게 만들어졌다.
- `backend/tests/e2e/live_api.py`: anf-api를 실제 uvicorn 프로세스로 띄우고 멈추며 HTTP로 부른다. 결함 주입과 재시작 시험에 쓴다.
- `backend/tests/e2e/dataplane_live.py`: storage agent(root), 일반 사용자 권한의 anf-api, `anf-vnet`의 클라이언트 컨테이너를 다루는 픽스처(`agent`, `api`, `clients`)와 데이터 플레인 관찰 도구다. 픽스처는 `conftest.py`가 등록한다.
- `backend/tests/e2e/snapshot_live.py`, `revert_live.py`: 스냅샷·되돌리기 경로와 그 관찰 도구다.
