# ANF 로드맵 총괄

사용자가 FR마다 새 세션을 열지 않아도, 이 세션 하나가 남은 FR을 순서대로 완성한다. 각 FR은 `anf-feature-cycle`의 단계(조사 → 설계 → 구현 → 검증 → 개념 문서 → 기록)를 그대로 거친다. 이 스킬은 그 사이클과 다른 점만 정한다.

원칙은 그대로다. 면접에서 "왜 이렇게 했나"에 답하는 사람은 사용자다. 그래서 되돌리기 어려운 결정은 사용자에게 묻고, 나머지는 추천안을 채택하되 사용자가 나중에 검토할 수 있게 기록한다.

## 구성

| 역할 | 담당 | 실행 모드 |
| --- | --- | --- |
| 순서, 설계 상의, 기록, 출하 | 메인(이 세션) | 직접 |
| 조사 | `anf-researcher` | 서브에이전트 위임 |
| 스파이크, TDD 구현, FAIL 수정 | `feature-implementer` | 서브에이전트. FR마다 하나 띄우고 ID로 이어 간다 |
| 실환경 검증 | `real-env-verifier` | 서브에이전트. ID로 이어 간다 |
| 개념 문서 | `concept-explainer` | 서브에이전트 위임 |

- **에이전트는 모두 메인이 직접 띄운다.** 서브에이전트가 다른 서브에이전트를 띄우게 하지 않는다. 메인이 에이전트 ID와 결과를 받아 기록해야, 세션이 끊겨도 이어 갈 수 있기 때문이다.
- **메인은 제품 코드를 쓰지 않는다.** 기능 하나만 진행하던 세션도 컨텍스트가 2~3번 압축됐다. 이 세션은 여러 FR을 돌리므로 코드 작업은 `feature-implementer`의 컨텍스트에 둔다. 메인이 고치는 것은 기록과 문서뿐이다: `_workspace/`, `docs/feature-status.md`, 결정이 바뀔 때의 ADR·PRD·`CLAUDE.md`.
- **FR의 구현은 하나씩 순서대로 진행한다.** WSL 데이터 플레인이 기기에 하나뿐이고, 뒤 FR이 앞 FR의 코드 위에 쌓이기 때문이다 (`CLAUDE.md` "Parallel sessions"). 다만 검증과 CI를 기다리는 동안에는 다음 FR의 조사와 설계를 먼저 한다 (아래 "기다리는 동안").

## 0단계: 로드맵 준비

1. **진행 기록을 읽는다.** `_workspace/roadmap.md`가 있으면 재개다. "현재 FR"의 `00_progress.md`에서 재개할 단계를 찾아 1단계로 간다. 없으면 아래 2~4번으로 만든다.
2. **남은 FR을 모은다.** 범위는 PRD §9의 완료 기준인 FR-01~FR-13이다. FR-14(선택)와 FR-15 이후는 넣지 않는다. `docs/feature-status.md`에서 `done`이 아닌 FR을 모은다. 행이 없는 FR과 `partial`인 FR도 넣는다.
3. **순서를 정한다.** 의존이 먼저다. 의존을 만족한 FR끼리는 `CLAUDE.md` "Confirmed requirements"의 순서를 따른다. 먼저 데이터 플레인 핵심(FR-07, FR-08), 다음 공고 역량(FR-10 통합 테스트, FR-11 CI, FR-12 메트릭, FR-13 컨테이너) 순서다. 대시보드(FR-09)는 그 목록에 없으므로, 그것을 필요로 하는 FR(FR-11의 frontend 작업, FR-12의 차트) 바로 앞에 넣는다. 아래 의존은 PRD의 수락 기준에서 읽은 것이니, 시작할 때 PRD §6·§8로 다시 확인한다.

   | FR | 슬러그(예) | 먼저 끝나야 하는 것 | 이유 |
   | --- | --- | --- | --- |
   | FR-07 새 볼륨으로 복원 | `restore-new-volume` | FR-05 | 스냅샷을 원본으로 쓴다 |
   | FR-08 처리량 제한 | `throughput-limit` | FR-04, S2, D-12 | 볼륨 인스턴스의 veth에 제한을 건다 |
   | FR-10 테스트 자동화 | `test-automation` | FR-08 | 처리량 효과를 확인하는 테스트가 수락 기준이다 |
   | FR-09 대시보드 | `dashboard` | FR-02~FR-05 API | 리소스 계층과 상태를 보여 준다 |
   | FR-11 CI 나머지 | `ci` | FR-09(frontend 작업), S3(data-plane 작업) | 기존 `partial`의 남은 범위다 |
   | FR-12 메트릭 | `metrics` | FR-08, FR-09 | 처리량을 수집하고 대시보드 차트로 보여 준다 |
   | FR-13 컨테이너 | `containers` | 나머지 전부 | 모든 구성요소를 compose로 묶는다 |

4. **`_workspace/roadmap.md`를 만든다** (형식은 아래 "기록"). 이 파일은 git에 넣지 않는다(`.gitignore`). 브랜치를 바꿔도 남아야 하고, 막혀서 merge하지 않는 브랜치에 갇히면 안 되기 때문이다. 공개 상태는 `docs/feature-status.md`와 각 FR의 설계 기록에 남는다.
5. **순서를 사용자에게 알리고 바로 시작한다.** 기다리지 않는다. 사용자는 중간에 끼어들 수 있다. FR 하나에 지금까지 $35~55가 들었다는 것도 함께 알린다.

## 1단계: FR 하나 돌리기

`anf-feature-cycle`의 0~6단계를 따른다. 다른 점은 아래뿐이다.

| 사이클 단계 | 이 스킬에서 다른 점 |
| --- | --- |
| 0. 맥락 | 최신 `main`에서 `feature/{feature}` 브랜치를 만든다. `roadmap.md`의 "현재 FR"을 갱신한다. 앞 FR을 기다리는 동안 먼저 만든 산출물이 있으면 이때 커밋하고, 끝난 단계는 다시 하지 않는다 |
| 1. 조사 | 같다. 사용자에게 보내는 요약은 짧게 알리고 기다리지 않는다 |
| 2. 설계 상의 | 메인이 설계를 쓴다. 설계를 확정하기 전에 스파이크가 필요하면(사이클 0단계 5번) `feature-implementer`를 띄워 맡기고, 그 ID를 `00_progress.md`에 "implementer 에이전트 ID"로 적는다. 결정은 아래 "설계 결정 규칙"을 따른다 |
| 3. 구현 | 메인이 아니라 `feature-implementer`가 한다. 스파이크를 맡긴 에이전트가 있으면 같은 ID로 `SendMessage`하고, 없으면 새로 띄운다. 돌아오면 메인이 3단계 4번의 내용 해시를 계산해 `00_progress.md`에 적는다 |
| 4. 검증 | FAIL이면 `feature-implementer`에게 ID로 수정을 맡기고(보고서 경로와 FAIL 항목 ID), 돌아오면 verifier에게 ID로 재검증을 맡긴다. 최대 3회다. UNVERIFIED는 사용자에게 묻지 않고 기록한 뒤 "막혔을 때"를 따른다 |
| 5. 개념 문서 | 같다 |
| 6. 기록 | 같다. 끝나면 아래 "출하"로 간다 |

**구현이 백그라운드에서 도는 동안의 Stop 훅:** 메인이 에이전트를 기다리며 응답을 마치면, TDD 훅의 Stop이 전체 테스트를 돌린다. 이때 `feature-implementer`가 RED 단계에 있으면 Stop이 한 번 막힌다. 메인은 코드를 고치지 않고 다시 기다린다(두 번째 Stop은 막히지 않는다). 테스트 판정은 implementer가 돌아와 보고한 전체 실행 결과와, 그 뒤 메인의 Stop 결과로 한다.

### 기다리는 동안

긴 실행을 기다리기만 하지 않는다. 사용자가 정한 방식은 "도는 동안 다른 작업을 한다"이다.

| 기다리는 것 | 그동안 비는 것 | 그동안 하는 일 |
| --- | --- | --- |
| verifier의 WSL 검증 (30~80분) | 웹, 문서 | 다음 FR의 1단계(조사). `anf-researcher`를 함께 띄운다 |
| PR의 CI (약 45분) | WSL 데이터 플레인까지 | 다음 FR의 1~2단계(조사, 스파이크, 설계) |

- **먼저 하는 것은 바로 다음 FR 하나의 0~2단계까지다.** 제품 코드 구현(3단계)은 앞 FR이 merge된 뒤 최신 `main`에서 만든 브랜치에서 시작한다. 작업 트리가 하나이고, 뒤 FR이 앞 FR의 코드 위에 쌓이기 때문이다.
- **먼저 만드는 것은 새 파일뿐이다.** `_workspace/{다음 기능}/`과 `_workspace/spikes/S{n}.md`만 쓴다. 커밋하지 않은 새 파일은 브랜치를 바꿔도 남는다. 추적 중인 파일(ADR, PRD, `CLAUDE.md`, `docs/feature-status.md`)에 반영할 것은 `00_progress.md`의 미해결에 적어 두고, 다음 FR의 브랜치를 만든 뒤에 고친다. `roadmap.md`의 "현재 FR"은 앞 FR이 출하될 때까지 바꾸지 않고, 이력에 먼저 한 단계를 적는다.
- **스파이크는 데이터 플레인이 빌 때만 돌린다.** verifier가 도는 동안에는 돌리지 않는다.
- **앞 FR이 먼저다.** verifier나 CI가 돌아오면 그 결과(FAIL 수정, merge)를 먼저 처리한다. 앞 FR의 수정이 다음 FR의 설계가 기대는 코드를 바꿨으면 설계의 그 부분을 다시 확인한다. 앞 FR이 `blocked`가 되고 다음 FR이 거기에 의존하면, 먼저 한 산출물은 그대로 두고 건너뛴다.
- **긴 실행은 GitHub 러너로 보낸다.** 전체 회귀나 간헐 결함의 반복 실행처럼 수십 분이 넘는 데이터 플레인 실행은 `data-plane` 작업의 수동 실행(`gh workflow run`)으로 돌리고, `gh run watch <실행 번호> --exit-status`를 백그라운드로 걸어 끝나면 알림을 받는다. 같은 ref의 새 실행은 돌던 실행을 취소하므로(`concurrency`), 반복은 앞 실행이 끝난 뒤에 다시 띄운다. WSL에서는 그 기능의 검증만 돌린다 (`anf-feature-cycle` 4단계 7번).

### 설계 결정 규칙

사용자가 정한 방식은 "큰 결정만 묻는다"이다.

**사용자에게 묻고 기다리는 결정:** 되돌리기 어렵거나 이미 합의한 것을 바꾸는 결정이다.
- 확정된 ADR 결정(D-nn)이나 `CLAUDE.md` "Decided"와 `.claude/rules/`의 결정 내용을 바꾼다.
- PRD의 FR이나 수락 기준을 빼거나 줄인다. 또는 비목표를 범위에 넣는다.
- 사용자 기기, 계정, 저장소 설정을 바꾼다. 예: self-hosted 러너, GitHub 설정, 새 소프트웨어 설치, 유료 자원.
- 스파이크가 실패해서 ADR §10 "실패하면" 열의 방향을 골라야 한다.

한 FR의 질문은 `AskUserQuestion` 한 번에 모은다. 답을 받을 때까지 그 FR은 멈춘다. 다른 FR로 먼저 넘어가지 않는다. 뒤 FR이 이 결정에 기댈 수 있기 때문이다.

**추천안을 자동 채택하는 결정:** 위에 해당하지 않는 나머지다. 예: API 계약의 세부, 상태 전이, 확정된 구조 안에서의 구현 방식, 검증 기준의 세부.
- `02_main_design.md`의 결정 항목에 `자동 채택`이라고 표시하고, 버린 대안과 이유를 적는다.
- `roadmap.md`의 "검토할 자동 채택 결정" 표에 한 줄을 더한다.
- 수락 기준에는 PRD의 수락 기준을 빠짐없이 넣는다. 빼려면 위의 "묻는 결정"이다.

이렇게 나누는 이유: 자동으로 정한 결정은 나중에 후속 사이클에서 바꿀 수 있다. 사용자는 검토 목록과 개념 문서의 설계 결정 표로 이유를 익힌다. 구현 중에 `feature-implementer`가 "묻는 결정"을 만나 돌아오면, 메인이 같은 방식으로 사용자에게 묻는다.

### 출하

FR마다 `main`까지 넣고 나서 다음 FR의 구현으로 간다. 다음 FR의 코드가 merge된 코드 위에서 시작해야 하기 때문이다.

1. **커밋한다.** 코드는 `feature-implementer`가 하위 기능마다 커밋한다. 메인은 기록과 문서를 단계마다 커밋한다. `main`에는 커밋하지 않는다. 자기 파일만 stage한다(예: `docs/ai-readiness-*`처럼 내 것이 아닌 파일은 두고 간다).
2. 5단계(개념 문서)와 6단계(기록)가 끝나면 push하고 PR을 연다. PR 본문 끝에는 시스템이 알려 준 attribution 줄을 붙인다.
3. CI를 기다린다(`gh pr checks <번호> --watch`를 백그라운드로 실행). 그동안 "기다리는 동안"의 일을 한다. 실패하면 원인이 제품 코드면 `feature-implementer`에게 맡기고, 기록·설정이면 메인이 고친다. 두 번 고쳐도 실패하면 "막혔을 때"를 따른다.
4. 통과하면 squash merge하고 브랜치를 지운 뒤 `main`을 받는다. merge 뒤 내용 해시가 검증한 값과 같은지 확인한다.
5. `roadmap.md`의 그 FR 행을 갱신하고 다음 FR로 간다.

### 막혔을 때

사용자가 정한 방식은 "건너뛰고 계속"이다.

| 상황 | 처리 |
| --- | --- |
| 3회 재검증 뒤에도 FAIL, 고치지 못한 CI 실패, 풀지 못한 merge 충돌 | `blocked`로 기록한다. 브랜치는 push하고 draft PR로 남긴다(merge하지 않는다) |
| 그 FR의 일부 항목만 환경 때문에 UNVERIFIED | `partial`로 기록한다. CI가 통과하면 출하한다 |
| 에이전트 호출이 두 번 실패 | `blocked`로 기록한다 |

막힌 FR은 `roadmap.md`의 "막힌 FR" 표에 원인, 남은 브랜치, 필요한 조치와 함께 적는다. 막힌 FR의 `docs/feature-status.md` 행은 다음 FR 브랜치에서 갱신해 커밋한다. 막힌 브랜치는 `main`에 들어가지 않으므로, 그래야 `main`에 상태가 남는다. 그다음 막힌 FR에 의존하지 않는 다음 FR로 간다(0단계 3번의 표). 의존하는 FR도 같은 이유로 건너뛴다.

**전체를 멈추는 경우:** 건너뛰어도 다음 FR이 같은 이유로 막힐 때다.
- 사용량 한도, 인증 만료, 권한 거부: 다시 시도하지 않는다. 한도라면 풀리는 시각을 함께 보고한다.
- WSL·Docker·커널 모듈처럼 모든 데이터 플레인 FR이 기대는 환경이 고장 났다.
- 두 FR이 연달아 같은 원인으로 막혔다.

멈출 때는 `roadmap.md`의 상태를 `멈춤`으로 바꾸고 이유와 재개할 지점을 적은 뒤 보고한다.

## 2단계: 마무리 보고

순서가 모두 끝났거나 멈췄으면 사용자에게 보고한다.
- FR별 결과: 상태, PR, 개념 문서
- 검토할 자동 채택 결정 목록 (`roadmap.md`)

## 기록: `_workspace/roadmap.md`

FR을 시작할 때, 단계를 마칠 때, 막힐 때, 출하할 때 갱신한다. 새 세션이 이 파일과 각 FR의 `00_progress.md`만 읽고 이어 갈 수 있어야 한다.

```markdown
# 로드맵 진행 기록

- 범위: FR-13까지 (PRD §9)
- 상태: 진행 중 | 멈춤 (이유, 재개할 지점) | 완료
- 현재 FR: {feature} (FR-nn), 단계 n

## 순서
| 순서 | FR | 슬러그 | 의존 | 상태 | PR |

## 검토할 자동 채택 결정
| FR | 결정 | 고른 것 | 버린 대안 | 위치 (`02_main_design.md` 절) |

## 막힌 FR
| FR | 상태 | 원인 | 남은 브랜치·PR | 필요한 조치 |

## 이력
- YYYY-MM-DD HH:MM — 한 줄
```

## 재개와 후속 요청

- **"로드맵 이어서", "로드맵 멈춘 데서 계속"**: `roadmap.md`의 "현재 FR"과 그 `00_progress.md`에서 이어 간다. 이전 세션의 에이전트 ID로는 이어 갈 수 없다. 그래서 새 `feature-implementer`와 새 verifier를 띄우고 이전 기록(설계, 보고서, 브랜치 `git log`)을 넘긴다.
- **"자동 채택한 결정 보여줘"**: "검토할 자동 채택 결정" 표를 보여 준다. 사용자가 바꾸라고 하면, 그 FR을 `anf-feature-cycle`의 무효화 규칙에 따라 다시 연다.
- **이전 세션의 기억에 기대지 않는다.** 다음 FR을 시작할 때마다 기록 파일에서 다시 읽는다. 이 세션은 길어서 대화 앞부분이 압축되기 때문이다.

## 오류 처리

- 에이전트 호출이 실패하면 한 번 다시 시도한다. 또 실패하면 그 FR을 `blocked`로 기록하고 "막혔을 때"를 따른다.
- 멈춘 에이전트가 남긴 빈자리는 메인이 직접 확인한 사실로만 채운다. 에이전트의 판단을 추측해 쓰지 않는다.
- 사이클 안의 오류(조사 충돌, verifier 무응답 등)는 `anf-feature-cycle`의 "오류 처리"를 따른다.

## 테스트 시나리오

**정상 흐름: "남은 기능 끝까지 진행해"** (FR-01~06 done, FR-11 partial)
1. 0단계: `roadmap.md`가 없다. 순서를 FR-07 → FR-08 → FR-10 → FR-09 → FR-11 → FR-12 → FR-13으로 정해 알리고 바로 시작한다.
2. FR-07: `feature/restore-new-volume`. 조사 → `feature-implementer`가 스파이크 S6(볼륨 인스턴스 구조에서 쓰기 가능한 thin 스냅샷 볼륨) → 설계 선택지 4개 중 3개 자동 채택, 1개(PRD 수락 기준을 바꾸는 것)는 사용자에게 묻는다 → 같은 implementer가 구현 → 검증 1회차 FAIL → implementer 수정 → 2회차 PASS → 개념 문서 → push, PR, CI, squash merge.
3. FR-08부터 같은 방식으로 이어 가고, 끝나면 마무리 보고를 한다.

**오류 흐름: FR-08이 3회 재검증 뒤에도 FAIL**
1. FR-08을 `blocked`로 기록한다. 브랜치는 push하고 draft PR로 둔다.
2. FR-10은 FR-08에 의존하므로 건너뛴다. FR-09로 간다. FR-09 브랜치에서 FR-08의 `feature-status.md` 행을 `blocked`로 커밋한다.
3. FR-12도 FR-08에 의존하므로 건너뛴다. 마무리 보고에 막힌 FR 셋과 필요한 조치를 적는다.

**재개 흐름: FR-09의 검증 중 사용량 한도로 멈춤**
1. 상태를 `멈춤`으로 기록하고, 한도가 풀리는 시각과 함께 보고한다.
2. 새 세션에서 "로드맵 이어서" → `roadmap.md`와 `_workspace/dashboard/00_progress.md`를 읽는다. 새 verifier에게 이전 보고서를 넘겨 다음 회차로 이어 간다.
