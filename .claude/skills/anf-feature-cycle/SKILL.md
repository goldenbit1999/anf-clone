# ANF 기능 사이클 오케스트레이터

기능 하나를 "조사 → 설계 → 구현 → 검증 → 개념 정리" 순서로 완성한다. 메인 세션이 조율, 설계 상의, 구현을 맡는다. 전문 에이전트 세 명이 조사, 검증, 문서화를 맡는다.

이 순서를 지키는 이유가 있다. 이 프로젝트의 목적은 면접에서 "ANF가 실제로 어떻게 동작하고, 나는 그것을 어떻게 재현했는가"를 설명하는 것이다.
- 조사 없이 구현하면 ANF와 다른 것을 만든다.
- 검증 없이 넘어가면 "실제로 동작한다"는 주장을 증명할 수 없다.
- 개념 문서가 없으면 사용자가 Claude가 쓴 코드를 설명할 수 없다.

## 구성

| 단계 | 담당 | 실행 모드 | 산출물 |
| --- | --- | --- | --- |
| 1. 조사 | `anf-researcher` | 서브에이전트 위임 | `_workspace/{feature}/01_researcher_brief.md` |
| 2. 설계 상의 | 메인 + 사용자 | 대화 | `_workspace/{feature}/02_main_design.md` |
| 3. 구현 | 메인 | 직접 | 코드 |
| 4. 검증 | `real-env-verifier` (이름: `verifier-{feature}`) | 지속형 에이전트 | `_workspace/{feature}/04_verifier_report.md` |
| 5. 개념 정리 | `concept-explainer` | 서브에이전트 위임 | `docs/concepts/{feature}.md` |
| 6. 기록 | 메인 | 직접 | `docs/feature-status.md` |

`{feature}`는 영어 kebab-case 슬러그로 쓴다. 예: `netapp-account`, `capacity-pool`, `snapshot`, `export-policy`.

## 0단계: 맥락 확인

1. `CLAUDE.md`의 "Not decided yet"를 확인한다. 기술 스택이나 스토리지 백엔드가 정해지지 않은 채로 구현에 들어가야 한다면, 2단계에서 사용자와 먼저 정한다. 정한 내용은 `CLAUDE.md`에 반영한다.
2. `docs/feature-status.md`를 읽어 끝난 기능을 확인한다. 파일이 없으면 6단계에서 만든다.
   - ANF 리소스는 계정 → 용량 풀 → 볼륨 → 스냅샷 순서로 의존한다. 상위 리소스가 아직 없으면 그것부터 진행하자고 제안한다.
3. `_workspace/{feature}/`의 상태를 보고 실행 범위를 정한다.
   - 폴더가 없으면 1단계부터 실행한다.
   - 폴더가 있고 일부만 다시 해 달라는 요청이면 해당 단계만 실행한다. 예: "재검증"은 4단계, "개념 문서만"은 5단계.
   - 폴더가 있고 기능 범위가 바뀌었으면, 기존 폴더를 `_workspace/{feature}_{YYYYMMDD-HHMM}/`으로 옮긴 뒤 1단계부터 실행한다.

## 1단계: 조사

**실행 모드:** 서브에이전트 위임

1. `Agent(subagent_type: "anf-researcher")`를 호출한다. 프롬프트에는 다음을 넣는다.
   - 기능 이름과 슬러그
   - 사용자가 말한 범위
   - 출력 경로
   - 기존 브리프가 있으면 그 경로와 보완할 점
2. 브리프가 나오면 읽고 사용자에게 5줄 이내로 요약한다.
   - 핵심 동작
   - 대응하는 ONTAP 개념
   - 이번에 재현할 범위 후보
   - 설계에 영향을 주는, 아직 확인되지 않은 추론
   - 사용자가 정해야 할 선택지 (2단계에서 함께 정한다)

## 2단계: 설계 상의

**실행 모드:** 메인 세션이 사용자와 대화

면접에서 "왜 이렇게 했나"에 답하는 사람은 사용자다. 그래서 설계는 사용자 확인 없이 확정하지 않는다.

1. 브리프를 바탕으로 이번 범위를 제안한다. 재현할 것과 생략할 것을 나눈다.
2. 구현 방식에 선택지가 있으면 2~3개를 장단점과 함께 보여 주고 하나를 추천한다. 선택지가 생기는 곳은 주로 다음과 같다.
   - API 계약: ARM 경로, 속성, 비동기 응답
   - 상태 전이: `provisioningState`
   - 데이터 플레인 구현 방식
3. 검증 기준을 사용자와 함께 정한다. 기준은 "클라이언트에서 관찰할 수 있는 효과"로 쓴다. 예: "스냅샷을 만든 뒤 지운 파일을 `.snapshot/{name}/`에서 읽을 수 있다."
4. 사용자가 확인하면 `02_main_design.md`에 다음을 쓴다.
   - 범위
   - 결정과 버린 대안, 그 이유
   - API 계약
   - 상태 전이
   - 검증 기준

## 3단계: 구현

1. 메인이 `02_main_design.md`대로 구현한다.
2. 구현하다가 설계를 바꿔야 하면, 이유를 `02_main_design.md`의 "구현 중 변경" 절에 적는다. 개념 문서가 이 기록을 근거로 설명하기 때문이다.
3. 테스트를 먼저 쓴다. 동작 하나마다 실패하는 테스트를 쓰고(RED), 통과시키는 최소한의 코드를 쓴 뒤(GREEN) 정리한다. `.claude/hooks/tdd_guard.py` 훅이 테스트 없는 구현 파일 수정을 막고, 수정할 때마다 관련 테스트 결과를 돌려준다.

## 4단계: 실환경 검증

**실행 모드:** 지속형 에이전트. 수정한 뒤 같은 맥락에서 재검증을 이어 가기 위해서다.

1. `Agent(name: "verifier-{feature}", subagent_type: "real-env-verifier")`를 호출한다. 프롬프트에는 01 브리프 경로, 02 설계 경로, 변경된 코드 위치, 출력 경로를 넣는다.
2. 보고서의 판정에 따라 처리한다.
   - **모두 PASS**: 5단계로 넘어간다.
   - **FAIL**: 메인이 원인을 고친다. 그다음 `SendMessage({to: "verifier-{feature}"})`로 실패한 항목만 재검증해 달라고 요청한다. 최대 3회까지 반복한다.
   - **3회 뒤에도 FAIL**: 멈추고 사용자에게 실패 항목, 시도한 수정, 추정 원인을 보고한 뒤 방향을 묻는다.
   - **UNVERIFIED**(환경 문제로 확인하지 못함): PASS로 세지 않는다. 이유를 사용자에게 알리고, 환경을 고칠지 범위에서 뺄지 묻는다.

## 5단계: 개념 정리

**실행 모드:** 서브에이전트 위임

1. `Agent(subagent_type: "concept-explainer")`를 호출한다. 프롬프트에는 다음을 넣는다.
   - 01, 02, 04 산출물 경로. 재검증 보고서(`_r2` 등)도 포함한다.
   - 변경된 코드 파일 목록
   - 출력 경로 `docs/concepts/{feature}.md`
   - 사용자 피드백이 있으면 그 내용
2. 완료되면 문서 경로와 면접 Q&A 개수를 사용자에게 알린다.

## 6단계: 기록

`docs/feature-status.md`의 표를 갱신한다. 열은 `기능 | 상태 | 검증일 | 개념 문서`다. 상태 값은 세 가지다.
- `done`: 모든 항목 PASS
- `partial`: UNVERIFIED 항목이 남아 있음
- `blocked`: 3회 재검증 뒤에도 FAIL이거나 사용자가 보류함

## 데이터 전달

모든 단계는 파일로 결과를 넘긴다.
- 중간 산출물은 `_workspace/{feature}/{단계번호}_{담당}_{산출물}.md`에 저장하고 지우지 않는다. 나중에 개발 과정을 설명하는 자료가 된다.
- 최종 산출물은 코드, `docs/concepts/{feature}.md`, `docs/feature-status.md` 세 가지다.

## 오류 처리

- **에이전트 호출이 실패하면** 한 번 다시 시도한다. 또 실패하면 그 단계를 건너뛰지 말고 사용자에게 보고한다. 이 사이클은 단계 순서에 의존하므로, 한 단계가 빠진 채로 진행하지 않는다.
- **사용량 한도, 인증 만료, 권한 거부는 다시 시도하지 않는다.** 남은 산출물을 직접 열어 어디까지 진행됐는지 확인하고 사용자에게 보고한다. 한도 문제라면 풀리는 시각도 함께 알린다.
- **멈춘 에이전트의 빈자리를 메인이 채울 때는** 직접 확인한 사실만 쓴다. 에이전트의 판단(예: 어떤 출처를 왜 뺐는지)은 추측해서 채우지 않는다.
- **verifier가 응답하지 않으면** `SendMessage`로 상태를 묻는다. 그래도 응답이 없으면 같은 유형을 `verifier-{feature}-2`라는 새 이름으로 실행하고 이전 보고서 경로를 넘긴다.
- **조사 결과끼리 충돌하면**(예: 문서와 스펙이 다름) 어느 쪽도 지우지 않는다. 두 내용을 출처와 함께 브리프에 남긴다.

## 테스트 시나리오

**정상 흐름: "스냅샷 기능 만들어줘"** (볼륨 기능은 이미 done)
1. 0단계: `_workspace/snapshot/`이 없고 볼륨이 done인지 확인한다.
2. 1단계: 브리프를 만든다. Snapshot 리소스 경로, 속성, 비동기 동작, 대응하는 ONTAP 개념(Snapshot copy, WAFL)이 들어간다.
3. 2단계: 범위를 생성·목록·삭제·`.snapshot` 접근으로 정하고, 복원은 다음 기능으로 미룬다. 사용자가 확인한다.
4. 3단계: 구현한다.
5. 4단계: 1회차 FAIL(`.snapshot`이 NFS 클라이언트에 보이지 않음) → 수정 → 2회차 PASS.
6. 5단계: `docs/concepts/snapshot.md`를 쓴다.
7. 6단계: snapshot을 done으로 기록한다.

**오류 흐름: "QoS 구현해줘"인데 Docker Desktop이 꺼져 있음**
1. 4단계에서 verifier의 환경 사전 점검이 실패하고, 처리량 항목이 UNVERIFIED가 된다.
2. 메인은 이를 PASS로 처리하지 않고, 사용자에게 Docker Desktop을 켜 달라고 요청한다.
3. 켜진 뒤 `SendMessage`로 그 항목만 재검증한다.

**부분 재실행: "스냅샷 개념 문서만 다시 써줘, 면접 질문은 더 어렵게"**
1. 0단계: `_workspace/snapshot/`이 있고 일부만 요청했으므로 5단계만 실행한다.
2. 사용자 피드백을 concept-explainer 프롬프트에 넣는다.
