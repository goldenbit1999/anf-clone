# ANF 기능 사이클 오케스트레이터

기능 하나를 "조사 → 설계 → 구현 → 검증 → 개념 정리" 순서로 완성한다. 메인 세션이 조율, 설계 상의, 구현, 기록을 맡는다. 전문 에이전트 세 명이 조사, 검증, 문서화를 맡는다.

이 순서를 지키는 이유가 있다. 이 프로젝트의 목적은 면접에서 "ANF가 실제로 어떻게 동작하고, 나는 그것을 어떻게 재현했는가"를 설명하는 것이다.
- 조사 없이 구현하면 ANF와 다른 것을 만든다.
- 검증 없이 넘어가면 "실제로 동작한다"는 주장을 증명할 수 없다.
- 개념 문서가 없으면 사용자가 Claude가 쓴 코드를 설명할 수 없다.

## 구성

| 단계 | 담당 | 실행 모드 | 산출물 |
| --- | --- | --- | --- |
| 0. 맥락 확인 | 메인 | 직접 | `_workspace/{feature}/00_progress.md`, 필요하면 `_workspace/spikes/S{n}.md` |
| 1. 조사 | `anf-researcher` | 서브에이전트 위임 | `_workspace/{feature}/01_researcher_brief.md` |
| 2. 설계 상의 | 메인 + 사용자 | 대화 | `_workspace/{feature}/02_main_design.md` |
| 3. 구현 | 메인 | 직접 | 코드 |
| 4. 검증 | `real-env-verifier` | 서브에이전트. 재검증은 에이전트 ID로 이어 간다 | `_workspace/{feature}/04_verifier_report.md` |
| 5. 개념 정리 | `concept-explainer` | 서브에이전트 위임 | `docs/concepts/{feature}.md` |
| 6. 기록 | 메인 | 단계마다 직접 | `00_progress.md`, `docs/feature-status.md` |

FR마다 거칠 단계는 PRD §8의 "FR별 사이클 단계" 표를 따른다. 예를 들어 FR-01(비동기 작업)은 계정 사이클에 포함되고, FR-10·FR-11·FR-13은 1단계를 생략한다.

`{feature}`는 영어 kebab-case 슬러그로 쓴다. 예: `netapp-account`, `capacity-pool`, `snapshot`, `export-policy`.

## 0단계: 맥락 확인

1. **문서를 읽는다.** `CLAUDE.md`, PRD의 해당 FR·NFR과 §8 표, ADR의 관련 요구사항(AR)·결정(D)·스파이크(S)·위험(R)을 읽는다. 기술 스택(D-01~D-04)과 Python 설정(D-14)은 이미 정해졌으므로 다시 묻지 않는다. 아래 "기능별 선행 확인" 표에서 이 기능의 행을 찾는다.
2. **진행 기록을 읽는다.** `docs/feature-status.md`와 `_workspace/{feature}/00_progress.md`를 읽는다.
   - `docs/feature-status.md`가 없으면 첫 사이클이므로 지금 만든다 (아래 "진행 기록").
   - ANF 리소스는 계정 → 용량 풀 → 볼륨 → 스냅샷 순서로 의존한다. 상위 리소스가 아직 `done`이 아니면 그것부터 진행하자고 제안한다.
3. **실행 범위를 정한다.**
   - 폴더가 없으면 1단계부터 실행한다.
   - `00_progress.md`에 재개할 단계가 적혀 있으면 거기서 이어 간다.
   - 폴더가 있고 일부만 다시 해 달라는 요청이면 해당 단계만 실행한다. 예: "재검증"은 4단계, "개념 문서만"은 5단계.
   - 폴더가 있고 기능 범위가 바뀌었으면, 기존 폴더를 `_workspace/{feature}_{YYYYMMDD-HHMM}/`으로 옮긴 뒤 1단계부터 실행한다. `done`이었다면 즉시 해제한다 (아래 "무효화 규칙").
4. **작업 위치를 확인한다.** `git branch --show-current`, `git status --short`, `git worktree list`를 본다. `main`이면 `feature/{feature}` 브랜치를 만든다. 이 브랜치나 worktree를 다른 세션이 쓰고 있을 수 있거나, 다른 세션이 WSL 데이터 플레인을 쓰고 있을 수 있으면 사용자에게 묻는다. 데이터 플레인은 기기에 하나뿐이라 스파이크, 통합 테스트, 검증은 한 번에 한 세션만 한다 (`CLAUDE.md` Environment의 "Parallel sessions").
5. **선행 결정과 스파이크를 확인한다.** 표의 항목마다 상태를 본다.
   - 결정(D-nn)이 제안·미정이면 2단계에서 사용자와 정한다. 이 기능이 의존하는 결정만 구현 전에 확정한다.
   - 스파이크는 `_workspace/spikes/S{n}.md`의 판정을 확인한다. 파일이 없으면 메인이 설계를 확정하기 전에 실행하고 그 파일에 명령, 출력, 판정을 기록한다. root가 필요한 명령은 `wsl -d Ubuntu -u root -- <명령>`으로 실행한다. 실패하면 ADR §10의 "실패하면" 열을 근거로 사용자와 방향을 정한다.
   - 표에 스파이크가 없더라도, 설계가 기대는 데이터 플레인 동작(커널, NFS, LVM, 네트워크가 실제로 어떻게 반응하는지)을 지금 구조에서 실측한 적이 없으면 설계를 확정하기 전에 스파이크로 확인한다. 번호는 ADR §10 스파이크 표의 다음 번호를 쓰고 그 표에 행을 더한다. 지금까지 데이터 플레인 기능은 모두 스파이크가 필요했다(S1 볼륨, S2 처리량, S4 스냅샷, S5 되돌리기). S4와 S5는 이 표에 없어서 사이클 중간에 생겼다.
6. **시작을 기록한다.** `00_progress.md`를 만들거나 갱신하고, `docs/feature-status.md`의 이 기능 행을 `in_progress`로 둔다.

### 기능별 선행 확인

| 진입할 기능 | 선행 확인 |
| --- | --- |
| 계정 (FR-01 포함) | 상태 저장소(D-07), 워커 방식(D-09), 인증(D-13) 등 계정 구현에 필요한 선택. 인증은 첫 엔드포인트부터 영향을 준다. ADR §6.1의 작업별 응답 표. S0는 필수 아님 |
| 용량 풀 | 용량 계산과 동시성·예약 규칙 (ADR §6.4 "풀·볼륨 설계 전에 확정할 규칙"). S0는 필수 아님 |
| 볼륨 | S0(환경, NFS 마운트, LOCALIO), S1(저장 방식 후보 비교), D-06·D-10·D-11 결정, 스토리지 루트(ADR §5), ADR §6.4의 복구 규칙 |
| 스냅샷에서 새 볼륨으로 복원 (FR-07) | S1 #9(쓰기 가능한 thin 스냅샷으로 즉시 생성)는 볼륨 인스턴스 구조(D-12) 전의 측정이다. S1의 "같은 파일시스템 UUID" 주의(새 볼륨의 ext4 UUID가 원본과 같다)와 export `fsid`, 원본 스냅샷이나 볼륨을 지운 뒤에도 새 볼륨이 남는지, ADR R-09(스냅샷·클론 공간은 씬 풀에서 나간다) |
| 처리량 제한 | S2 측정(측정 조건 포함), D-12 결정, 선택한 볼륨·네트워크 구조와의 호환성, ADR R-08 |
| 대시보드 (FR-09) | Python TDD 훅 밖이다. 프론트엔드 타입 검사·빌드 명령을 `CLAUDE.md` Commands에 더하고 CI frontend 작업(ADR §9.3)을 연다. 검증은 브라우저에서 상태 변화를 관찰하므로, 쓸 수 있는 브라우저 도구를 확인하고 `real-env-verify`의 환경 점검과 검증 패턴에 브라우저 항목을 더한다 |
| 데이터 플레인 CI | S3 결과와 사용할 러너 결정 |

선행 스파이크 결과가 없는 상태에서 데이터 플레인 기능을 완료로 선언하지 않는다.

## 1단계: 조사

**실행 모드:** 서브에이전트 위임. PRD §8 표에서 조사를 생략하는 FR이면 건너뛴다.

1. `Agent(subagent_type: "anf-researcher")`를 호출한다. 프롬프트에는 다음을 넣는다.
   - 기능 이름과 슬러그
   - 사용자가 말한 범위
   - 출력 경로
   - 기존 브리프가 있으면 그 경로와, 다시 조사할 질문만. 기존 원문(`sources/`)과 브리프는 재사용하게 한다.
2. 브리프 맨 위의 "조사 상태"를 확인한다. `한도 도달`이면 조사가 끝난 것으로 보지 않는다. 미확인 목록이 이 기능의 설계를 막는지 판단한다. 막으면 그 질문만 보완 조사를 맡기고, 막지 않으면 2단계에서 사용자에게 알린다. 설계를 막지 않더라도 ONTAP 대응(필수 질문 다섯째)을 비우는 미확인은, 늦어도 5단계 전에 그 질문만 보완 조사를 맡긴다. 개념 문서의 ONTAP 절이 면접 설명의 중심이기 때문이다. 맡길 질문은 `00_progress.md`의 미해결에 적어 두고, 보완 조사로도 답이 없으면 개념 문서의 "쓰지 못한 것"에 남긴다. 에이전트가 상한에 걸려 브리프 없이 멈췄으면 질문을 좁혀 다시 맡긴다.
3. 사용자에게 5줄 이내로 요약한다.
   - 핵심 동작
   - 대응하는 ONTAP 개념
   - 이번에 재현할 범위 후보
   - 설계에 영향을 주는, 아직 확인되지 않은 추론
   - 사용자가 정해야 할 선택지 (2단계에서 함께 정한다)
4. `00_progress.md`에 1단계 완료(또는 한도 도달과 남은 질문)를 적는다.

## 2단계: 설계 상의

**실행 모드:** 메인 세션이 사용자와 대화

면접에서 "왜 이렇게 했나"에 답하는 사람은 사용자다. 그래서 설계는 사용자 확인 없이 확정하지 않는다. `anf-roadmap`이 총괄하는 동안에는 그 스킬의 "설계 결정 규칙"을 따른다. 되돌리기 어려운 결정만 묻고, 나머지는 추천안을 채택해 검토 목록에 남긴다.

1. 브리프를 바탕으로 이번 범위를 제안한다. 재현할 것과 생략할 것을 나눈다.
2. 구현 방식에 선택지가 있으면 2~3개를 장단점과 함께 보여 주고 하나를 추천한다. 선택지가 생기는 곳은 주로 다음과 같다.
   - API 계약: ARM 경로, 속성, 작업별 응답(동기 `200`, 비동기 `201`·`202`, 본문 없는 `204`, 즉시 거절 `409`)
   - 상태 전이: `provisioningState`
   - 데이터 플레인 구현 방식
3. 검증 기준을 사용자와 함께 정한다. 기준은 "클라이언트에서 관찰할 수 있는 효과"로 쓰고, 기준마다 ID(`AC-01` 등)를 붙인다. 진행 기록과 검증 보고서가 이 ID로 결과를 합친다. 비동기 작업이면 완료·실패 시나리오, 폴링 간격, 제한 시간도 정한다. 예: "스냅샷을 만든 뒤 지운 파일을 `.snapshot/{name}/`에서 읽을 수 있다."
4. 사용자가 확인하면 `02_main_design.md`에 다음을 쓴다.
   - 범위
   - 관련 ID: PRD의 FR·NFR, ADR의 AR·D·S, 스파이크 결과 파일 링크
   - 결정과 버린 대안, 그 이유. 아직 확정하지 않은 선택과 그 이유
   - API 계약: ADR §6.1의 작업별 응답 표를 이 기능에 맞게 확정한 표
   - 상태 전이
   - 검증 기준 (ID 포함)
5. **결정을 문서에 반영한다.** 결정(D-nn)이 정해지거나 바뀌면 ADR §11을 기준으로 고치고, PRD와 `CLAUDE.md`의 요약도 같이 맞춘다. ADR §2.3 리소스 대응표의 이 기능 행도 이때 고친다.
6. `00_progress.md`에 2단계 완료를 적는다.

## 3단계: 구현

1. 메인이 `02_main_design.md`대로 구현한다. `anf-roadmap`이 총괄하는 동안에는 메인 대신 `feature-implementer`가 이 단계의 절차대로 구현한다.
2. 구현하다가 설계를 바꿔야 하면, 이유를 `02_main_design.md`의 "구현 중 변경" 절에 적는다. 개념 문서가 이 기록을 근거로 설명하기 때문이다.
3. **테스트를 먼저 쓴다.** 동작 하나마다 다음 순서를 지킨다.
   1. 실패하는 테스트를 쓴다. TDD 훅이 그 테스트를 실행해 결과를 돌려준다.
   2. RED의 이유가 "아직 구현되지 않음"인지 확인한다. 훅이 ERROR(테스트 문법, fixture, 의존성)나 SKIPPED를 알리면 RED가 아니다. 테스트를 먼저 고친다.
   3. 예상한 RED를 확인한 뒤에 구현을 쓴다. 훅은 짝 테스트에 지금 내용의 실행 근거가 없으면 구현 파일 수정을 거절한다. 다만 GREEN인 테스트로도 수정을 허용하므로(리팩터링을 위해), 새 동작을 RED 없이 구현하지 않는 것은 이 절차로 지킨다.
   4. 통과시키는 최소한의 코드를 쓰고(GREEN) 정리한다. 동작을 바꾸지 않는 리팩터링은 기존 테스트와 직전 GREEN으로 진행한다.
   - 훅의 보장 범위와 한계는 `CLAUDE.md`의 TDD hook 절에 있다. Linux 전용 테스트가 Windows에서 skip되는 것은 허용하지만, skip은 실환경 PASS가 아니다.
4. 구현을 마치면 검증 대상 코드를 `00_progress.md`에 적는다. 제품 코드(`pyproject.toml`과 `backend/`에서 `backend/tests/`를 뺀 것)의 내용 해시를 아래 명령으로 계산해 쓴다. 커밋했으면 커밋 SHA를, 미커밋이면 변경 파일 목록을 함께 쓴다.
   ```bash
   # 작업 트리 (미커밋 변경과 새 파일 포함)
   git ls-files -co --exclude-standard -- pyproject.toml backend ':!backend/tests' | LC_ALL=C sort | while IFS= read -r f; do cat "$f"; done | tr -d '\r' | sha256sum
   # 커밋 (SHA=<커밋>)
   git ls-tree -r --name-only "$SHA" -- pyproject.toml backend | grep -v '^backend/tests/' | LC_ALL=C sort | while IFS= read -r f; do git show "$SHA:$f"; done | tr -d '\r' | sha256sum
   ```
   - 내용이 같으면 두 명령의 값이 같다. 그래서 미커밋 상태에서 검증한 해시를 merge 뒤의 커밋과 비교할 수 있다. Git Bash와 WSL에서도 같은 값이 나온다.
   - CR을 지우는 이유: `core.autocrlf=true`라서 git이 체크아웃한 파일은 CRLF이고 도구로 새로 쓴 파일은 LF다. 그대로 계산하면 같은 코드도 줄 끝 때문에 해시가 달라진다. 용량 풀 merge 뒤에 실제로 그랬다.
   - `git diff HEAD`를 쓰지 않는 이유: 새 파일(untracked)을 잡지 못하고, 값이 HEAD에 따라 달라 merge 뒤에 다시 계산할 수 없다.

## 4단계: 실환경 검증

**실행 모드:** 서브에이전트. 처음 띄울 때 받은 에이전트 ID로 재검증을 이어 간다. 수정한 뒤 같은 맥락에서 재검증하기 위해서다.

Agent 도구의 `name` 인자는 에이전트 팀을 켠 세션에서만 쓸 수 있고, 그때는 이름을 준 에이전트가 팀원(teammate)으로 뜬다. 이 프로젝트는 에이전트 팀을 쓰지 않으므로 이름이 아니라 ID로 이어 간다.

1. `Agent(subagent_type: "real-env-verifier")`를 호출한다. 프롬프트에는 01 브리프 경로, 02 설계 경로, 검증 대상 코드(3단계 4번의 값), 변경된 코드 위치, 출력 경로, 이전 보고서 경로(있으면)를 넣는다.
2. 반환된 에이전트 ID를 `00_progress.md`에 적는다.
3. 보고서의 판정에 따라 처리한다.
   - **모두 PASS**: 5단계로 넘어간다.
   - **FAIL**: 먼저 `00_progress.md`에 실패 항목, 원인, 재개할 단계를 적는다. 메인이 원인을 고친다. 그다음 기록한 ID로 `SendMessage({to: "<에이전트 ID>"})`를 보내, 실패한 항목과 수정의 영향을 받을 수 있는 항목을 재검증해 달라고 요청한다. 최대 3회까지 반복한다.
   - **ID로 이어 갈 수 없으면**(새 세션, 응답 없음, 에이전트 종료) 새 `real-env-verifier`를 띄우고 이전 보고서 경로를 모두 넘긴다. 새 verifier는 이전 보고서를 읽고 회차 번호를 이어 쓴다(예: `_r3`). 새 ID를 `00_progress.md`에 적는다.
   - **3회 뒤에도 FAIL**: 멈추고 상태를 `blocked`로 기록한 뒤, 사용자에게 실패 항목, 시도한 수정, 추정 원인을 보고하고 방향을 묻는다.
   - **UNVERIFIED**(환경 문제로 확인하지 못함): PASS로 세지 않는다. 먼저 `00_progress.md`에 원인과 재개할 단계를 적는다. 이유를 사용자에게 알리고, 환경을 고칠지 범위에서 뺄지 묻는다. 범위에서 빼고 사이클을 마치면 상태는 `partial`이다.
4. 환경 점검은 기능에 필요한 것만 요구한다. 순수 컨트롤 플레인 기능(계정, 용량 풀)에 Docker·NFS 조건을 일괄 요구하지 않는다. 데이터 플레인이 바뀌지 않았음을 확인하는 항목을 실행하지 못했으면 그 항목만 UNVERIFIED로 남긴다.
5. 보고서를 받을 때마다 `00_progress.md`의 "수락 기준별 최신 결과" 표를 갱신한다.
6. 검증이 도는 동안 사용자가 진행을 물으면, 보고서 파일의 진행 상태와 수락 기준 표를 읽고 답한다. 테스트 코드를 읽고 추정해서 답하지 않는다.
7. **회귀 범위를 좁힌다.** verifier는 WSL에서 이 기능의 수락 기준과, 바뀐 코드가 닿는 테스트 파일만 돌린다. 전체 데이터 플레인 묶음(`scripts/run-dataplane-tests.sh`를 인자 없이, 약 100분)은 WSL에서 돌리지 않는다. "기존 기능이 깨지지 않았다"는 기준의 근거는 PR의 CI `data-plane` 작업이다(두 조각 병렬, 약 40분, 기기를 쓰지 않는다). 설계의 그 기준에 "PR의 CI로 판정"이라고 적고, CI가 통과한 뒤 실행 번호와 함께 PASS로 기록한다. 그 전에는 `대기`다. 예외는 러너와 WSL의 차이 자체가 의심될 때뿐이고, 돌리기 전에 사용자에게 묻는다.

## 5단계: 개념 정리

**실행 모드:** 서브에이전트 위임

1. `Agent(subagent_type: "concept-explainer")`를 호출한다. 프롬프트에는 다음을 넣는다.
   - 01, 02, 04 산출물 경로. 재검증 보고서(`_r2` 등)와 `00_progress.md`도 포함한다.
   - 02 설계가 근거로 쓴 스파이크 결과(`_workspace/spikes/S{n}.md`). 데이터 플레인의 실제 반응(errno, 지연, 측정값)은 보고서와 스파이크에 나뉘어 있다.
   - 코드 인용 기준: 검증 대상 코드의 커밋 SHA와 내용 해시. 맡기기 전에 작업 트리의 내용 해시(3단계 4번의 명령)가 이 값과 같은지 확인한다. 다르면 개념 문서가 검증하지 않은 코드를 설명하게 된다.
   - 변경된 코드 파일 목록
   - 출력 경로 `docs/concepts/{feature}.md`
   - 사용자 피드백이 있으면 그 내용
   - PRD §8 표에서 조사를 생략한 FR이면, 브리프가 없다는 사실과 ANF·ONTAP 절을 "해당 없음"으로 두라는 지시
2. 완료되면 문서 경로와 면접 Q&A 개수를 사용자에게 알리고 `00_progress.md`에 적는다.

## 6단계: 기록

기록은 마지막에 한 번만 하지 않는다. 시작, 단계 완료, 검증 실패, 중단 때마다 아래 두 파일을 갱신한다. 새 세션이 기록 파일만 읽고 다음 단계를 정할 수 있어야 한다. 사이클을 마칠 때 `docs/feature-status.md`의 최종 상태를 쓴다.

### `_workspace/{feature}/00_progress.md`: 기능의 상세 진행 기록

```markdown
# {feature} 진행 기록

- 상태: in_progress | partial | blocked | done
- FR: FR-nn
- 마지막 완료 단계: n
- 재개할 단계: n (이유)
- 검증 대상 코드: 제품 코드 내용 해시 (3단계 4번의 명령)와 커밋 SHA. 미커밋이면 커밋 SHA 대신 변경 파일 목록
- verifier 에이전트 ID:
- 미해결: (멈춘 원인, 사용자에게 물은 것)

## 수락 기준별 최신 결과
| 기준 ID | 기준 | 최신 결과 | 근거 보고서 | 검증 대상 코드 |

## 이력
- YYYY-MM-DD HH:MM 단계 n 시작 | 완료 | FAIL | 중단 — 한 줄 설명
```

부분 재검증 뒤에는 "수락 기준별 최신 결과" 표에 이전 PASS와 이번 결과를 합친다. 기준마다 가장 최근의 유효한 결과만 둔다. 수정의 영향을 받는 이전 PASS는 다시 검증하기 전까지 유효하지 않다.

### `docs/feature-status.md`: 전체 현황

첫 사이클을 시작할 때 만든다. 열은 다음과 같다.

```text
기능 | FR | 상태 | 마지막 완료 단계 | 검증 대상 코드 | 검증 보고서 | 갱신일 | 개념 문서
```

상태 값은 네 가지다.
- `in_progress`: 사이클 진행 중
- `partial`: 사이클은 끝났지만 UNVERIFIED 항목이 남아 있음
- `blocked`: 3회 재검증 뒤에도 FAIL이거나 사용자가 보류함
- `done`: PRD §8의 완료 정의를 모두 충족함. 데이터 검증 PASS만으로 개념 문서까지 끝났다고 기록하지 않는다

### 무효화 규칙

- 범위나 제품 코드가 바뀌어 기존 검증이 무효가 되면 즉시 `done`을 해제하고(`in_progress`), 영향을 받는 수락 기준을 `00_progress.md`에 적는다.
- 문서 표현만 고치는 재실행(예: 개념 문서만 다시 쓰기)은 기존 데이터 검증을 유지할 수 있다. 이때 검증 대상 코드와 수락 기준이 그대로라는 근거(같은 커밋 SHA, 바뀌지 않은 검증 기준)를 `00_progress.md`에 남긴다.

## 데이터 전달

모든 단계는 파일로 결과를 넘긴다.
- 중간 산출물은 `_workspace/{feature}/{단계번호}_{담당}_{산출물}.md`에 저장하고 지우지 않는다. 나중에 개발 과정을 설명하는 자료가 된다. 진행 기록은 `00_progress.md`, 기능 밖 스파이크 결과는 `_workspace/spikes/S{n}.md`다.
- 조사 원문(`_workspace/{feature}/sources/`)은 커밋하지 않는다. 브리프의 출처에 URL과 커밋 SHA·태그를 남겨 다시 받을 수 있게 한다.
- 최종 산출물은 코드, `docs/concepts/{feature}.md`, `docs/feature-status.md` 세 가지다.

## 오류 처리

- **에이전트 호출이 실패하면** 한 번 다시 시도한다. 또 실패하면 그 단계를 건너뛰지 말고 사용자에게 보고한다. 이 사이클은 단계 순서에 의존하므로, 한 단계가 빠진 채로 진행하지 않는다.
- **사용량 한도, 인증 만료, 권한 거부는 다시 시도하지 않는다.** 남은 산출물을 직접 열어 어디까지 진행됐는지 확인하고, `00_progress.md`에 중단 지점을 적은 뒤 사용자에게 보고한다. 한도 문제라면 풀리는 시각도 함께 알린다.
- **멈춘 에이전트의 빈자리를 메인이 채울 때는** 직접 확인한 사실만 쓴다. 에이전트의 판단(예: 어떤 출처를 왜 뺐는지)은 추측해서 채우지 않는다.
- **verifier가 응답하지 않으면** 4단계 3번의 "ID로 이어 갈 수 없으면"을 따른다.
- **조사 결과끼리 충돌하면**(예: 문서와 스펙이 다름) 어느 쪽도 지우지 않는다. 두 내용을 출처와 함께 브리프에 남긴다.

## 테스트 시나리오

**정상 흐름: "스냅샷 기능 만들어줘"** (볼륨 기능은 이미 done)
1. 0단계: 관련 FR(FR-05)과 ADR 항목을 읽는다. `_workspace/snapshot/`이 없고 볼륨이 done인지 확인한다. S1 결과 파일을 확인한다. `00_progress.md`를 만들고 `in_progress`로 기록한다.
2. 1단계: 브리프를 만든다. Snapshot 리소스 경로, 속성, 비동기 동작, 대응하는 ONTAP 개념(Snapshot copy, WAFL)이 들어간다.
3. 2단계: 범위를 생성·목록·삭제·`.snapshot` 접근으로 정하고, 복원은 다음 기능으로 미룬다. 사용자가 확인한다.
4. 3단계: 테스트를 먼저 쓰고(RED 확인) 구현한다. 검증 대상 커밋을 기록한다.
5. 4단계: verifier를 띄우고 ID를 기록한다. 1회차 FAIL(`.snapshot`이 NFS 클라이언트에 보이지 않음) → 기록 → 수정 → 기록한 ID로 재검증 → 2회차 PASS. 수락 기준 표를 갱신한다.
6. 5단계: `docs/concepts/snapshot.md`를 쓴다.
7. 6단계: snapshot을 done으로 기록한다.

**오류 흐름: "QoS 구현해줘"인데 Ubuntu의 Docker Engine을 띄울 수 없음**
1. 4단계에서 verifier의 환경 사전 점검이 실패하고, 처리량 항목이 UNVERIFIED가 된다.
2. 메인은 이를 PASS로 처리하지 않는다. `00_progress.md`에 원인과 재개할 단계(4단계)를 적고, 원인(예: Docker Desktop의 Ubuntu 연동이 다시 켜짐)과 필요한 조치를 사용자에게 알린다.
3. 켜진 뒤 기록한 ID로 `SendMessage`해 그 항목만 재검증한다. 세션이 바뀌어 ID로 이어 갈 수 없으면 새 verifier에게 이전 보고서를 넘긴다.

**부분 재실행: "스냅샷 개념 문서만 다시 써줘, 면접 질문은 더 어렵게"**
1. 0단계: `_workspace/snapshot/`이 있고 일부만 요청했으므로 5단계만 실행한다.
2. 사용자 피드백을 concept-explainer 프롬프트에 넣는다.
3. 문서만 바뀌었으므로 기존 검증을 유지하고, 같은 커밋 SHA라는 근거를 `00_progress.md`에 남긴다.
