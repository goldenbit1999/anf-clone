# 개념 문서 작성 절차

구현은 Claude가 했지만 면접에서 설명하는 사람은 사용자다. 이 문서는 그 간극을 메운다. 사용자가 이 문서만 읽고도 네 가지를 말할 수 있어야 한다.
- ANF에서는 어떻게 동작하는가
- ONTAP의 무엇에 해당하는가
- 이 프로젝트에서는 어떻게 만들었는가
- 왜 그렇게 만들었는가

사용자는 AI를 활용해 개발한 과정도 설명해야 하므로 개발 과정도 짧게 남긴다.

## 입력

- `01_researcher_brief.md`: ANF·ONTAP에 대한 사실과 근거 표시
- `02_main_design.md`: 결정, 버린 대안, 구현 중 변경
- `04_verifier_report*.md`: 검증 결과, 실패와 수정 과정
- `_workspace/spikes/S{n}.md`: 이 기능이 근거로 쓴 스파이크(02 설계의 관련 ID에 있다). 데이터 플레인이 실제로 어떻게 반응했는지에 대한 관찰이 있다
- 변경된 코드 파일

## 작성 원칙

- **ANF·ONTAP 사실은 브리프에서만 가져온다.** 브리프의 `[녹화]`, `[추론]`, `[미확인]` 표시는 문서에도 그대로 남긴다. `[녹화]`는 실서비스에서 관찰했지만 문서로 보장되지 않은 동작이라는 뜻이다. 사용자가 면접에서 추측을 사실처럼 말하지 않게 하기 위해서다.
- **코드는 실제로 읽고 설명한다.** 설명할 때는 `파일:줄`로 위치를 가리킨다. 설계 문서만 보고 쓰지 않는다. 구현하면서 바뀐 부분이 있을 수 있기 때문이다.
- **코드 인용은 기준 커밋에 묶는다.** 문서 맨 위에 코드 인용 기준을 적는다. 기준은 검증 대상 코드의 커밋 SHA와 제품 코드 내용 해시이고, `00_progress.md`에 있다. `파일:줄`에는 함수 이름도 함께 써서 지금 코드에서도 찾을 수 있게 한다. 뒤의 기능이 같은 파일을 바꿔 줄 번호만 어긋난 인용은 고치지 않는다. 설명한 동작이 바뀌어 문서를 고칠 때만, 고친 부분의 인용에 새 커밋을 붙인다(`파일:줄 @커밋`). 공통 코드가 옮겨질 때마다 다른 기능 문서의 줄 번호 수십 곳을 다시 맞추지 않기 위해서다.
- **관찰한 동작은 관찰한 조건과 함께 쓴다.** 검증 보고서와 스파이크에서 가져온 동작(errno, 지연 시간, 측정값)에는 어떤 클라이언트, 프로토콜 버전, 연산 순서에서 관찰했는지를 붙이고, 시험하지 않은 경우로 넓히지 않는다. 보고서와 스파이크의 관찰이 서로 다르면 둘 다 조건과 함께 쓴다. 스냅샷 문서가 한 테스트의 접근 순서에서 본 EROFS를 모든 쓰기로 일반화했는데, 스파이크 S4는 다른 순서에서 이미 EACCES를 봤던 일이 있다.
- **실제 ANF와 다른 점을 숨기지 않는다.** 면접관은 차이를 물어볼 것이고, 차이를 정확히 아는 것이 이해했다는 증거다.
- **본문은 한국어, 면접 Q&A는 영어로 쓴다.** 용어에는 영어 원어를 함께 적는다. 예: 용량 풀(capacity pool). 영어 면접에서 그대로 써야 하기 때문이다.

## 문서 형식

```markdown
# {기능}

> 한 줄 요약

코드 인용 기준: 커밋 `{SHA}` (제품 코드 내용 해시 `{해시}…`)

## 1. ANF에서는
사용자에게 보이는 동작, API, 제약 (근거 표시를 유지한다)

## 2. ONTAP에서는
대응하는 ONTAP 개념과 그 원리 (예: 스냅샷이 즉시 만들어지는 이유)

## 3. 이 프로젝트에서는
### 구조
요청이 어떤 구성 요소를 거쳐 데이터 플레인에 반영되는지 (짧은 다이어그램을 넣어도 된다)
### 코드 따라가기
핵심 흐름을 순서대로 설명하고 파일:줄을 붙인다
### 설계 결정
| 결정 | 버린 대안 | 이유 |

## 4. 실제 ANF와 다른 점
| 항목 | 실제 ANF | 이 프로젝트 | 이유 |

## 5. 검증
무엇을 어떻게 증명했는지 (검증 보고서 요약, 측정값)

## 6. 개발 과정
조사 → 설계 → 구현 → 검증 순서로, 검증 회차, 실패와 수정, 사람이 내린 결정을 요약한다

## 7. Interview Q&A
### Q1. ...
**A.** ...
```

## 면접 Q&A 작성 기준

- **개수와 구성**: 최소 6개를 쓴다. 개념 2개, 구현·설계 결정 2개, 트레이드오프·한계 1개, 장애·디버깅 1개로 구성한다.
- **공고와 연결**: 지원하는 직무의 업무와 연결한다. 데이터 플레인 담당, REST API, 테스트 자동화, 관측성(observability), 장애 원인 분석이 해당한다.
- **답변 길이**: 30~60초 분량, 영어로 80~150단어로 쓰고 결론을 먼저 말한다.
- **질문 유형**: "왜 그렇게 했나", "다시 한다면 어떻게 하겠나"를 묻는 질문을 넣는다.

## 다시 쓸 때

기존 문서가 있으면 먼저 읽고, 사용자가 피드백한 부분만 고친다. 전체를 새로 써 달라는 요청일 때만 처음부터 쓴다.
