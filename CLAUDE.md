# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project purpose

A working local clone of **Azure NetApp Files (ANF)**. It is a portfolio project for NetApp's "Entry Level Software Engineer - ANF" role and will be shown only to NetApp. It is not meant to become a product.

That role owns the ANF **data plane**. Its posting stresses Python test automation, REST APIs, Kubernetes, containers, CI/CD, and observability.

## Confirmed requirements

- **It must really work.** Volumes are real NFS exports that clients can mount (SMB comes later, `docs/ADR.md` D-03). Snapshots and throughput limits must have real effects on data. Mocks or state-only simulation do not count as done.
- **NetApp/ONTAP data-plane features come first, in depth rather than breadth.** The goal is not all of ANF. It is a few features done for real, each explainable against real ONTAP, including where the clone differs (for example, dm-thin snapshots vs. WAFL snapshots). Order:
  1. Core: account → capacity pool → volume (real NFS export) → snapshot (create, revert, restore to a new volume) → throughput limit (real I/O limit).
  2. On top of the core, show the posting's skills: integration tests in pytest, GitHub Actions CI, metrics, and containers. A minimal Kubernetes CSI driver that provisions volumes from a PVC is optional; NetApp Trident connects Kubernetes to ANF this way.
  3. Later, data-plane features first: export policy, volume resize, snapshot policy, clone. Cross-region replication comes last.
- **Learning goes with each feature.** Each feature should help the author understand and explain the matching ANF/ONTAP concept, not only reproduce its behavior.
- **The control plane is asynchronous.** It follows the ARM long-running-operation style: an asynchronous operation responds before the work finishes, with a tracking header the client polls until a terminal state. Each operation follows its own ANF REST contract, so a synchronous `200` (for example, a tags-only PATCH) and a bodyless `204` (DELETE of a missing resource) are valid too. See `docs/PRD.md` FR-01 and `docs/ADR.md` §6.1.
- **Azure-side concepts are secondary.** Add subscriptions, resource groups, VNet, delegated subnets, and RBAC only when a feature needs them.
- **The dashboard stays minimal.** It shows resource lists, provisioning state, and metrics. It does not need to mirror the ANF portal. Leave out Microsoft logos and assets.
- **Claude writes the implementation code.** The user must still explain that code in interviews, so every feature gets a concept doc. It walks through the code and the reasons behind each design choice. The body is in Korean and the interview Q&A is in English.

## Decided (2026-11-07)

- Backend: Python 3.12 (CI too) with FastAPI. Dashboard: React + TypeScript, built with Vite. The TDD hook assumes Python + pytest.
- Protocols: NFSv3 and NFSv4.1. SMB comes later.
- Verification clients mount from Docker containers.
- Storage layer (D-06): a storage agent on Linux primitives that serves a subset of the ONTAP REST API. The ONTAP Simulator is an optional later target. State store SQLite (D-07), metrics Prometheus (D-08), LRO worker inside the anf-api process (D-09).
- Volume storage (D-11, spike S1 `_workspace/spikes/S1.md`): one dm-thin pool acts as the ONTAP aggregate (sparse file `/var/lib/anf-clone/aggr0.img`, VG `anf`, thin pool `aggr0`); each volume is a thin LV with ext4 mounted `nodelalloc` at `/var/lib/anf-clone/ns/<creationToken>`. btrfs subvolumes were rejected: over NFSv3 a file owner could modify a read-only snapshot.
- NFS serving and throughput limit (D-12, spike S2 `_workspace/spikes/S2.md`): each volume has its own knfsd instance in its own network namespace (privileged container `anf-nfs-<uuid>`, image `anf-nfs-server`) with its own IP on `anf-vnet`, picked by the storage agent from 172.30.0.128/25. The instance binds `ns` (made an rshared mount) as `/export`, uses `[exports] rootdir=/export`, exports only `/<creationToken>`, and enables only the volume's NFS version. Clients mount `<volume ip>:/<creationToken>`. The host knfsd serves nothing. FR-08 limits throughput with one tc HTB class per instance (both directions through one IFB, so reads and writes share the limit; see the FR-08 bullet below for where it sits). One shared knfsd was rejected: NFSv4.1 clients merge mounts of different IPs on one server into one connection, so per-IP limits cannot tell volumes apart. cgroup `io.max` was rejected: knfsd threads are invisible inside the WSL distro, and `io.max` counts reads and writes separately and skips cache hits. Details: `docs/ADR.md` §7.3–7.4, volume design decisions 17–18.
- Snapshots (FR-05, spike S4 `_workspace/spikes/S4.md`): each snapshot is a read-only thin snapshot LV mounted `ro,noload` at `ns/<creationToken>/.snapshot/<name>` and exported inside the volume's instance with its own `fsid`; a `crossmnt`-only submount gives Stale file handle. The agent writes each instance's export table to a file (`/var/lib/anf-clone/exports/<uuid>/volume.exports`, bound read-only to `/etc/exports.d`) and runs `exportfs -ra`, so exports survive instance restarts. `.snapshot` is `chattr +i` so root clients cannot change it. Deleting a volume deletes its snapshots. Instances use ONTAP's NFSv4 lease/grace (30/45 s), and the entrypoint waits out a grace period when nfsdcld has clients to reclaim. Design: `_workspace/snapshot/02_main_design.md`.
- Snapshot revert (FR-06, spike S5 `_workspace/spikes/S5.md`): `POST .../volumes/{v}/revert` returns a bodyless `202` with both tracking headers; the volume and the operation are `Reverting` (`action: POST`). The agent takes ONTAP's `PATCH /api/storage/volumes/{uuid}?restore_to.snapshot.uuid=…` plus a clone extension `restore_to.request_uuid` (the operation ID, an idempotency key kept in LVM tags). It swaps the volume LV: it deletes newer snapshots (higher dm-thin id) and creates `vol_<uuid32>_new`, a writable snapshot of the chosen snapshot that carries the volume tags from the start; then it blocks the instance's netns input with iptables, flushes knfsd state, unmounts the old LV, mounts the new one with the snapshots, re-exports, and unblocks; outside that window it removes the old LV and renames the new one. Mounted clients stall a few seconds and need no remount. `lvconvert --merge` was rejected during implementation: after one merge the other snapshots lose their origin, so a second revert to an older snapshot fails (`not a mergeable logical volume`). While a restore is unfinished the agent refuses snapshot create/delete, and volume POST or startup recovery finishes it. NFSv4 delegations are off (`fs.leases-enable = 0`, set by the setup script; the agent refuses to start otherwise): with them on, v4.1 held fds read pre-revert cache for 16–32 s. Design: `_workspace/snapshot-revert/02_main_design.md`.
- Restore to a new volume (FR-07, spike S6 `_workspace/spikes/S6.md`): a volume PUT with `properties.snapshotId` (a snapshot ARM ID in the same NetApp account, any pool; create-only, later changes are `400`) returns `201` with both tracking headers and records `originatingResourceId` when done. The new volume's quota must be at least the source volume's; `protocolTypes` and `unixPermissions` default to the source's. The agent takes ONTAP's FlexClone fields on `POST /api/storage/volumes` (`clone.is_flexclone`, `clone.parent_volume.uuid`, `clone.parent_snapshot.uuid`) and makes the volume LV a writable thin snapshot of the snapshot LV (blocks shared, independent at once, so no `cloneProgress` or split). It grows the LV and ext4 online for a larger quota, removes the source's stale `.snapshot` mount points, then takes a base snapshot with the source snapshot's name and time (after the resize, so reverting to it keeps the size), applies `unixPermissions`, and clears its progress tags (`anf_cl_snap`, `anf_cl_name`, `anf_cl_time`); startup recovery skips a volume with those tags and the next POST finishes it. The ext4 UUID stays the source's; per-volume export `fsid` keeps NFS handles apart. Until the new volume first succeeds, the source snapshot DELETE and the source volume DELETE/revert are `409`. Design: `_workspace/restore-new-volume/02_main_design.md`.
- Throughput limits (FR-08, spike S7 `_workspace/spikes/S7.md`): an Auto QoS volume's limit is its quota (TiB) × the service level's MiB/s per TiB, rounded to 3 decimals with Python `round` (1 GiB Premium = 0.062; no clone floor), and the response shows the value tc enforces. In a Manual QoS pool `throughputMibps` is required (1–4,500, fractions allowed; an update that resends the stored value skips the range, so a GET body re-PUT works) and is checked synchronously against the pool budget (`400`); switching a pool Auto → Manual fills each volume with its previous limit. anf-api sends the limit on every volume ensure as ONTAP's `qos.policy.max_throughput_mbps` (read as MiB/s, fractional); the agent stores it in the LVM tag `anf_qos` and applies it inside the instance netns with the host `tc` via `nsenter`: `eth0` clsact → matchall mirred to `ifb0` → HTB class at limit ÷ 0.9564 (header correction) → fq_codel. A host-side veth + host IFB was rejected: the veth changes on every container start and host IFBs outlive the volume. Every instance start path (create, re-POST, startup recovery) applies tc between `start` and `wait_ready`, because a new container veth starts without it. The limit is a ceiling, not isolation: heavy writes by another volume on the same aggregate still slow a limited volume. Judge throughput on the guest monotonic clock (the WSL wall clock steps back). Design: `_workspace/throughput-limit/02_main_design.md`.
- No authentication (D-13): anf-api binds to localhost and does not check `Authorization`. In real Azure, ARM validates tokens and RBAC before a request reaches the ANF resource provider, so the clone skips it the same way it skips subscription checks.
- Done means FR-01 to FR-13 are `done` (`docs/PRD.md` §9); the CSI driver (FR-14) is optional. No target dates: work through the stages in order, as fast as possible.
- Python project layout (D-14): one `pyproject.toml` at the repo root holds dependencies and pytest settings; code lives under `backend/`. Virtual environments are per OS: `.venv-win/` in the repo for Windows, `~/.venvs/anf-clone` inside WSL (outside `/mnt/c` to avoid 9P slowness; override with `ANF_CLONE_VENV`).
- Requirements are in `docs/PRD.md`. Architecture and the decision log are in `docs/ADR.md` (Architecture Design Requirement; its decisions are numbered `D-nn`).

## Commands and architecture

- **Run anf-api (WSL)**: from the repo, `~/.venvs/anf-clone/bin/python -m uvicorn --factory anf_api.arm_app:create_app --app-dir backend --host 127.0.0.1 --port 8080`. State lives in SQLite at `ANF_API_DB` (default `~/.local/state/anf-clone/anf-api.db`; keep it off `/mnt/c`). `ANF_FAULT_INJECTION` (JSON, off by default) adds per-operation delays or forced failures for verification, e.g. `'{"netAppAccounts/create": {"delaySeconds": 5}}'`. `ANF_STORAGE_AGENT_URL` (default `http://127.0.0.1:8090`) points at the storage agent. `ANF_MIN_VOLUME_SIZE_GIB` lowers the 50 GiB volume minimum for verification only (it logs a warning).
- **Data plane (WSL, root)**: sudo asks for a password, so run root commands with `wsl -d Ubuntu -u root`. Once per machine, `MSYS_NO_PATHCONV=1 wsl -d Ubuntu -u root -e bash /mnt/c/Users/mkimh/Projects/ANF-clone/scripts/setup-wsl-dataplane.sh` loads `nfsd`, builds the images `anf-nfs-server` and `anf-nfs-client`, and creates the network `anf-vnet` (172.30.0.0/24, ip-range /25). Run the agent from the repo as root: `/home/mkimhome1/.venvs/anf-clone/bin/python -m uvicorn --factory storage_agent.agent_app:create_app --app-dir backend --host 127.0.0.1 --port 8090`. It refuses to start until setup is done, then recovers volumes (mount, snapshot mounts, exports, instance). Integration tests (`backend/tests/integration`, marker `dataplane`) also need root.
- **Architecture (`backend/anf_api/`)**: `arm_app.py` is the FastAPI app (ARM routes, operation status URL, error format, correlation headers; the lifespan runs the worker). `accounts.py` holds the account body rules and PUT/PATCH/DELETE flows (account PATCH is synchronous). `capacity_pools.py` holds the pool body rules, throughput math (Auto limit formula, `utilizedThroughputMibps`, the Auto → Manual fill), parent/child and capacity checks, and PUT/PATCH/DELETE flows (pool PATCH is asynchronous). `volumes.py` holds the volume body rules, path and capacity checks, Manual QoS rules and the pool throughput budget, flows (including the revert action and creating a volume from a snapshot), and the handlers that call the agent, record `mountTargets` (and, for a restored volume, `originatingResourceId` and the base snapshot row), and delete snapshot rows the agent no longer has (after a revert, and after a volume ensure that finished one). `snapshots.py` holds the snapshot body rules (no writable properties, no tags, so no PATCH), parent-state and 255-per-volume checks, flows (a re-PUT is an async UPDATE that re-ensures the agent snapshot; a source snapshot of a volume still being restored cannot be deleted), and the handlers that record `created`. `storage_client.py` calls the agent (urllib in a thread, 60 s connection retry, job polling, re-send when a job is gone; `revert_volume` and `snapshot_uuids` for the revert, `ensure_volume(clone=)` and `snapshot_records` for restoring to a new volume). `lro.py` is the shared LRO worker (asyncio, same process, D-09), fault injection (keys come from the registered handlers, e.g. `capacityPools/patch`), and operation status body. `state_store.py` is SQLite (`resources`, `operations`; one active operation per resource; `Tx.ensure_no_children` for nested-resource 409s; `Tx.delete_resource` also deletes child rows, so a volume DELETE removes its snapshots). `arm_rules.py` covers api-version, name rules, resource IDs, `ArmError`, and shared error builders. A write stores the resource state and the operation in one transaction, responds, and the worker finishes the operation; on restart it re-runs unfinished operations.
- **Architecture (`backend/storage_agent/`)**: a root process serving an ONTAP REST subset (`agent_app.py`: `/api/storage/volumes` including FlexClone `clone` fields and `qos.policy.max_throughput_mbps` on POST and the restore `PATCH`, `/api/storage/volumes/{uuid}/snapshots`, `/api/cluster/jobs`, input re-checks). `flexvol.py` turns a volume into a thin LV + ext4 mount under `ns/<creationToken>` and keeps path, uuid, IP, protocol, and throughput limit (`anf_qos`) in LVM tags (no DB); a snapshot is a read-only thin snapshot LV `snap_<uuid32>` with its own tags, mounted under `.snapshot/<name>`; `restore` swaps the volume LV and records progress in tags (`anf_rv_req`, `anf_rv_snap`, `anf_rv_new`, `anf_rv_done`); `create` with a clone parent makes the volume from a snapshot and records progress in `anf_cl_*` tags. `nfs_instance.py` runs one `anf-nfs-server` container per volume (`nfs_server/` holds its Dockerfile and entrypoint), writes its export table under `/var/lib/anf-clone/exports/<uuid>` and applies it with `exportfs -ra`, applies the volume's throughput limit in the instance netns between start and readiness, waits up to 150 s for the instance to be ready, and blocks/unblocks an instance's netns input for the revert window; `check_host` also requires `fs.leases-enable = 0`. `jobs.py` is the in-memory job table (one job at a time). `runner.py` runs commands without a shell. Every step checks real state first, so repeating a request resumes it.

### TDD hook

`.claude/hooks/tdd_guard.py`, registered in `.claude/settings.json`, makes Python work test-first. It runs on tool calls in the main session and in subagents.

- **Interpreter**: Windows uses `.venv-win/`; Linux uses `$ANF_CLONE_VENV` or `~/.venvs/anf-clone`. It never picks the other OS's venv. Without one it falls back to the Python running the hook and says so. Every message shows the interpreter, cwd (repo root), and config file.
- **Scope**: the hook skips non-`.py` files, `__init__.py`, `conftest.py`, files under `tests/` or `test/`, dot-folders, `_workspace/`, `docs/`, `venv/`, `node_modules/`, and `__pycache__/`. Pairing is by file name, not path: any `test_models.py` pairs with every `models.py`, and editing one `models.py` runs every `test_models.py`.
- **PreToolUse (Write|Edit)**: allows writing `foo.py` only when a paired `test_foo.py`/`foo_test.py` has evidence for its current content (sha256). Evidence means it was collected and ran to RED (a failure, or an import error because the module or name to implement does not exist yet) or to GREEN (refactoring). A missing, empty, uncollected, all-skipped, or erroring test (test syntax, fixture, missing dependency), no pytest, or a timeout means denied. If there is no evidence yet, pre runs the test once itself. Evidence, including the first RED and its command, lives in `.claude/tdd-guard-state/evidence.json` (gitignored).
- **PostToolUse (Write|Edit)**: runs the paired tests and reports GREEN, RED, SKIPPED (every collected test skipped, with reasons), ERROR, or no tests. SKIPPED is not GREEN, and a skip never counts as a real-environment PASS.
- **Stop**: after code changed, runs the full suite. Only GREEN clears the dirty marker. RED, errors, no tests, all skipped, no pytest, or a timeout block the stop once. A repeated stop is not blocked, but the marker stays, so the next stop checks again.
- **Not guaranteed**: that a test checks the right behavior (review covers that), or that new behavior started from RED (a GREEN test also unlocks edits so refactoring works; RED-first stays a cycle rule). The hook only sees the Write and Edit tools, so files written through Bash and non-Python files are unchecked. Write code with Write or Edit.
- Verification helpers go under a tests folder such as `backend/tests/e2e/`, which the hook exempts.
